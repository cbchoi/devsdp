# cevsim 실행기

작성일: 2026-11-14 (같은 날 cevsim의 main이 45e7fa9로 바뀌어 그 커밋에 맞춰 다시 썼다. 2026-11-15에 시각을 다루는 부분을 시간 단위의 계약에 맞춰 고쳤다. 17 문서)

cevsim(https://github.com/eventsim/cevsim)을 pyevsim과 같은 방식으로 붙인 기록이다. cevsim은 C++로 쓴 이산 사건 엔진이다. 계약과 합격 기준은 15 문서와 같다. 충실성(엔진에서 다시 읽은 구조가 계획과 같다)과, 참조 시뮬레이터와 사건 기록이 같다는 것이다.

구현은 ses_core/cevsim_executor.py와 ses_core/cevsim_bridge/(C++)이고 검증은 tests/test_cevsim.py다. cevsim은 main의 커밋 45e7fa9(Integrate deterministic execution, checkpointing and repair research, 2026-11-14)를 읽기 전용으로 받아서 확인했다. cevsim 저장소에는 아무것도 올리지 않았다. cevsim의 소스와 C++ 컴파일러가 없으면 시험은 건너뛴다.

이 문서의 첫 판은 그 앞의 커밋 a9886a6(Test Case Update)을 다뤘다. 그때의 실행기와 문서는 이 저장소의 커밋 5261f91에 있다. 두 커밋에서 엔진이 어떻게 달라졌는지는 2절의 표에 나란히 적었다.

## 0. 판정

| 기준 | 결과 |
|---|---|
| 계약 | 같다. Executor의 conventions, build, observe를 구현했고 attach, executable, plan, realize, exec_core, analyze가 고치지 않은 채로 동작한다 |
| 충실성 | 통과. 조건이 하나 붙는다. 공통 모델 기반을 올릴 때 엔진에 계획에 없는 모델 하나와 연결(공통 모델마다 둘)을 더 올린다. 그것을 뺀 나머지가 계획의 평탄화와 같고, 더 올린 것이 정확히 무엇인지도 엔진에서 읽어 확인한다. 무작위 구조 500개, 무작위 문서의 계획 346개, 두 예시의 변이 71개 |
| 사건 기록, 공통 모델베이스 | 통과. 출력 사건의 열이 순서까지 같고 모델의 마지막 상태도 같다. 무작위 구조 500개(사건 8,325개), 무작위 문서의 계획 346개(사건 820개), 처리 시스템 15개 변이와 센서 노드 56개 변이(사건 2,479개). 시간 단위가 이진수로 정확히 적히지 않는 경우도 같다(17 문서) |
| 사건 기록, cevsim 고유 모델 | 견줄 수 없다. 참조 시뮬레이터에는 cevsim의 의미(하나씩 차례로 처리)로 움직이는 모델이 없다. 고유 모델은 작은 시험용 모델로 올려 구조, 기록, 값 메시지의 전달을 확인했다 |
| cevsim 저장소의 자체 시험 | 이 환경(g++ 13.3, 리눅스 x86-64)에서 24개 가운데 16개가 통과한다. 5개는 컴파일되지 않아 돌리지 못했고 3개는 실패한다. 엔진의 핵심 시험(cevsim_tests, 124개의 경우)은 통과한다(2.1절) |

꼭 알아야 할 것 다섯.

- cevsim의 main이 바뀌었고, 첫 판에서 결함으로 알린 것이 그 커밋에서 고쳐졌다. 시각이 같은 모델이 일정에서 함께 빠지던 것(G2), 한 번의 출력에서 둘째 메시지가 사라지던 것(G3), 계층 실행이 평탄 실행과 달랐던 것(G1), 외부 입력에 대한 반응이 한 눈금 늦던 것(G10), 늦게 만든 모델이 만든 시각에 내던 것(G12), 모델의 소멸자가 불리지 않던 것(G13)이다. 작은 프로그램으로 다시 실행해 확인했다(2절).
- 첫 판에서 내가 낸 수정 제안(patches/cevsim_a9886a6_schedule_and_messages.patch)은 main에 맞지 않는다. main은 같은 문제를 다른 방법으로 고쳤다. cevsim 저장소도 그 제안을 검토한 글을 실었고 결론이 같다. 규칙은 옳지만 앞선 구현에만 맞으므로 지금의 코드에 그대로 넣지 말라는 것이다(7절의 U1).
- 첫 판의 실행기는 45e7fa9에서 컴파일은 되지만 실행하면 실패한다. 엔진의 결함을 피하려고 음수인 시간 전진을 쓰던 것이 이제 예외가 되기 때문이다. 그래서 실행기를 다시 썼다. 엔진의 결함을 피해 가던 우회 넷을 모두 없앴고, 병렬 DEVS의 규약을 지키는 장치(전이를 맡는 모델)만 남겼다. cevsim은 여전히 같은 시각의 모델을 하나씩 차례로 처리하는 엔진이고 README도 그렇게 적는다. 다시 쓴 실행기는 a9886a6에서는 돌지 않는다.
- 엔진에는 시간 격자가 없어졌다. 엔진은 사건 시각을 정확한 값으로 지키고 long double로 더한다. 공통 모델의 시각은 엔진의 덧셈에 맡기지 않고 시간 단위의 눈금으로 센다(17 문서). 참조 시뮬레이터도 같은 방법으로 세므로 두 기록은 시간 단위가 0.1이어도 끝자리까지 같다. 이 문서의 2026-11-14 판은 엔진의 시각을 그대로 썼고, 그때는 0.1마다 내는 모델의 기록이 참조와 달랐다. 시간 전진이 시간 단위의 정수배가 아니면 OffGrid다.
- cevsim의 자체 시험 가운데 일부가 g++와 리눅스에서 컴파일되지 않거나 실패한다. 원인의 대부분은 long double의 크기가 MSVC와 다른 데에 있고, 하나는 g++가 요구하는 template 키워드가 시험 코드에 빠진 것이다. 저장소가 적어 둔 검증 결과는 MSVC에서의 것이다(2.1절).

## 1. 계약과 쓰는 법

```python
from ses_core import executor as X
from ses_core.cevsim_executor import CevsimExecutor
from examples import processing_mb

cx = CevsimExecutor(cevsim_home="/path/to/cevsim")                    # 환경 변수 CEVSIM_HOME으로 주어도 된다
binding = X.load_binding("docs/ses-platform/examples/processing_system.binding.cevsim.yaml")      # 시간 단위는 여기 적혀 있다
L, ext = X.attach(L0, cx, binding, processing_mb.LIBRARY)             # L0는 구조와 속성이 얹힌 SES
sim = X.realize(L, ext, cx, V)                                        # V는 실행 가능한 변이
log = sim.run(20.0)
sim.close()
```

cevsim은 C++ 라이브러리이고 Python에서 부르는 길이 없다. 그래서 실행기는 세 가지를 하나의 공유 라이브러리로 컴파일해 ctypes로 부른다. cevsim의 소스, 다리(ses_core/cevsim_bridge/bridge.cpp), 고유 모델을 등록하는 C++ 소스다. 컴파일 설정은 cevsim의 것을 따른다(C++23, 정의 둘). cevsim의 소스는 고치지 않는다. 실행 가능성의 판정에는 컴파일이 필요 없다.

컴파일은 두 단계다. cevsim의 소스 36개를 파일마다 따로 컴파일해 두고, 다리와 고유 모델의 소스를 그것과 묶는다. 소스의 내용과 컴파일러가 같으면 앞서 만든 것을 다시 쓴다. 이 환경(코어 4개)에서 처음 한 번은 30초쯤 걸리고, 고유 모델의 소스만 바꾼 뒤에는 5초쯤 걸린다. cevsim의 소스가 a9886a6보다 열 배쯤 커져서(1,853줄에서 18,705줄) 한 번에 컴파일하면 77초가 걸린다.

| 계약의 자리 | cevsim 실행기가 하는 일 |
|---|---|
| 규약 (conventions) | V1 하나. 원자의 포트 이름이 실행기가 쓰는 두 이름(__wake__, __commit__)이면 안 된다 |
| 조립 (build) | 엔진을 하나 만들고 계획의 원자마다 모델을 하나 올린다. 경로의 순서로 올린다. 계획의 평탄화를 엔진의 결합으로 등록하되 길의 수만큼 등록한다. 뿌리의 포트는 엔진의 입력 포트와 출력 포트가 된다. 공통 모델 기반이 있으면 전이를 맡는 모델 하나와 그 연결을 맨 나중에 올린다(3절) |
| 관찰 (observe) | 엔진의 자료(대기 목록, 실행기 표, 세 종류의 결합 표)와 모델의 포트에서 한 층짜리 구조를 다시 읽는다. 더 올린 것은 빼고 읽으며, Simulation.infrastructure가 따로 내놓는다 |

산출물 Simulation의 쓰임은 pyevsim 실행기의 것과 같다(run, log, leaves, connections, close, tick). 다른 것은 넷이다.

| 이름 | 뜻 |
|---|---|
| now() | 엔진의 시각. 공통 모델의 사건에서는 눈금의 시각에서 배정밀도의 끝자리 하나 안에 있다. 고유 모델의 사건에서는 엔진이 그 모델의 시간 전진을 더해서 얻은 값이다. 눈금은 tick()으로 읽는다 |
| infrastructure() | 계획에 없는데 엔진에 올린 모델과 연결 |
| inject(port, at) | 뿌리의 입력 포트로 밖에서 입력을 넣는다. 값은 없다. 지난 시각에는 넣을 수 없다 |
| outputs() | 뿌리의 출력 포트로 나간 것을 나간 순서대로. (시각, 뿌리의 포트, 낸 원자의 경로)의 목록이다. 값은 없다 |

run(until)은 시각 until의 사건까지 처리한다. 공통 모델의 사건은 눈금으로 따진다. until이 어떤 눈금의 시각이면 그 눈금의 사건까지 처리한다. 이어서 부르면 그 자리에서 이어 간다. 지난 시각을 주면 아무것도 하지 않는다.

생성자의 인자는 cevsim_home, time_unit(시간 단위. 주지 않으면 계획에 실려 온 바인딩의 것을 쓰고 어디에도 없으면 1이다), sources(고유 모델의 C++ 소스), record(고유 모델의 출력도 기록하는가), max_rounds(한 눈금에 돌 수 있는 차례의 한도), cache(컴파일한 것을 둘 자리)다.

모듈의 본체는 둘 가운데 하나다.

| 본체 | 조립 | 행위의 의미 |
|---|---|---|
| cevsim 고유 모델 | 본체가 Native("이름") 또는 글자. ses_cevsim.hpp의 SES_MODULE로 등록한 C++ 공장을 그 이름으로 불러 CAtomicModel을 만든다. 만들어진 모델이 계획의 포트를 그 방향으로 가졌는지 확인한다. 매개변수는 글자로 넘기고 수는 배정밀도로 읽는다. 그래서 계획에 적힌 값 그대로 간다. 공장은 부를 때마다 새 모델을 내놓아야 한다 | cevsim의 것. 하나씩 차례로 처리하고, 입력을 받으면 다음 사건 시각을 다시 잡는다. log에는 낸 포트만 남고 값은 None이다 |
| 공통 모델 기반 | devs.Atomic의 하위 클래스. 모델은 Python에 남고 엔진에는 그것을 대신하는 모델이 오른다. 엔진이 일정과 전달을 맡고 전이는 Python에서 한다 | 병렬 DEVS의 것. 참조 시뮬레이터와 같다(3절) |

고유 모델을 등록하는 예(tests/cevsim_models.cpp).

```cpp
#include "ses_cevsim.hpp"

SES_MODULE(Tick, [](const std::string& name, const ses::Params& p) -> evsim::CAtomicModel* {
    return new CTick(name, p.time("period", 1), p.number("keep") != 0, p.number("twice") != 0);
});
```

```python
cx = CevsimExecutor(sources=["tests/cevsim_models.cpp"])
library = {"Tick": Module("Tick", ports, (), params, Native("Tick"))}
```

고유 모델끼리는 cevsim의 값 메시지(ValuePort)를 쓸 수 있다. 실행기는 그것을 그대로 전달하고 기록에는 포트만 남긴다. 값 포트를 공통 모델이나 뿌리의 포트에 이은 계획은 조립할 때 ValueError가 된다. 엔진이 그런 결합을 거절하기 때문이다.

## 2. cevsim에서 확인한 엔진의 성질

표의 값은 작은 C++ 프로그램으로 실행해 확인한 것이다. 그 프로그램이 tests/cevsim_facts.cpp이고, tests/test_cevsim.py의 test_fact_engine_properties가 컴파일해 돌려 45e7fa9의 값 39개를 견준다. 다른 커밋에서는 건너뛴다. a9886a6의 값은 첫 판에서 같은 프로그램으로 실행해 얻은 것이다. 실행하지 않고 소스나 README에서 읽기만 한 것은 그렇게 적었다.

읽은 범위. 45e7fa9의 엔진 소스는 85개 파일, 18,705줄이다. 그 가운데 실행기가 지나는 길을 읽었다. 엔진의 뿌리(system_executor), 원자 실행기, 모델과 메시지와 전달기, 결합 모델, 실행기 공장, 값 메시지, 설정이다. 계층 결합 실행기, 평탄 백엔드, 저장과 복원, 디버깅과 수리 연구의 코드는 읽지 않았다. a9886a6은 전체(1,853줄)를 읽었다.

| 번호 | 성질 | a9886a6 | 45e7fa9 | 실행기에 준 영향 |
|---|---|---|---|---|
| G1 | 결합 모델을 엔진에 올렸을 때의 계층 실행. 생성기 하나와 중계기 셋 | 평탄하게 올리면 경계로 나간 출력 30, 중계기가 낸 횟수 10, 10, 10. 결합 모델 안에 넣으면 12, 그리고 1, 1, 10 | 어느 쪽이나 30, 그리고 10, 10, 10 | 첫 판은 이 차이 때문에 평탄화했다. 지금은 전이를 맡는 모델이 모든 공통 모델에 바로 닿아야 해서 평탄화한다 |
| G2 | 메시지를 받는 모델을 일정 목록에서 뺄 때 | 그 시각과 같은 모든 항목이 함께 빠졌다. 주기 5인 모델 둘 가운데 받는 쪽은 2번, 옆의 모델은 0번 | 그 모델의 항목 하나만 뺀다. 2번과 2번. 일정의 순서가 (시각, 모델 번호, 소유자)가 되었고 모델마다 목록 안의 자리를 기억한다 | 다음 사건 시각을 모델마다 조금씩 다르게 주던 우회를 없앴다 |
| G3 | 전달을 마친 메시지를 묶음에서 뺄 때 | 예약 시각이 같은 나머지가 함께 사라졌다. 두 포트로 하나씩 내면 수신이 3과 0. 같은 시각의 외부 입력 둘 가운데 하나만 전달 | 그 메시지 하나만 뺀다. 3과 3. 외부 입력은 둘 다 전달 | 메시지와 외부 입력의 시각을 서로 다르게 주던 우회를 없앴다 |
| G4 | 메시지의 값 | 없다. 출처, 포트, 예약 시각뿐이다 | 종전의 메시지에는 그대로 없다. 따로 값 메시지가 생겼다. ValuePort로 내고 받으며, 값은 32바이트 이하이고 그대로 복사해도 되는 타입이어야 한다. 값 포트는 타입이 같은 값 포트에만 이을 수 있다 | 공통 모델 기반의 값은 그대로 Python에 둔다. 고유 모델끼리의 값 메시지는 그대로 전달한다. 공통 모델과 엔진의 경계는 값을 싣지 않는다 |
| G5 | 시간 격자 | 시각이 time_resolution씩 나아가고 격자 밖의 시각은 오류 없이 다음 눈금으로 올려졌다. 주기 0.5인 모델이 시각 6까지 6번 | 격자가 없다. 사건 시각을 정확한 값으로 지킨다. 12번. time_resolution은 값만 검사하고 쓰지 않는다 | 엔진의 격자에 기대지 않는다. 공통 모델의 시각은 실행기가 시간 단위의 눈금으로 센다(17 문서) |

첫 판에서 결함으로 본 G2, G3, G12, G13과 미완성으로 본 G1, 확인이 필요하다고 한 G10의 늦음이 모두 달라졌다. G6의 순서도 정해졌다. 남은 차이는 설계의 선택이다. cevsim은 같은 시각의 사건을 번호의 순서로 하나씩 처리하고, 입력을 받은 모델의 일정을 다시 잡는다. README는 이것이 병렬 DEVS의 겹친 전이를 구현한 것이 아니라고 적는다. 그래서 공통 모델 기반에는 3절의 장치가 여전히 필요하다.

실행기가 기대는 성질은 G6, G17, G18과, 모델이 메시지를 받거나 차례를 마칠 때마다 엔진이 그 모델의 시간 전진을 다시 묻는다는 것이다. 엔진에서 구조를 다시 읽을 때에는 보호 멤버 둘(대기 목록과 실행기 표)도 읽는다. 엔진이 이것을 바꾸면 사실 시험이 먼저 실패한다.

### 2.1 cevsim 저장소의 자체 시험

저장소의 CMake 빌드를 그대로 썼다(Release, 시험 포함). 시험이 GoogleTest를 깃허브에서 받아 오는데 이 세션의 권한 밖이라 배포판의 GoogleTest 1.14 소스를 쓰게 했다. 환경은 g++ 13.3, 리눅스 x86-64다. 저장소의 검증 기록(docs/PUBLICATION_20261114.md)은 Visual Studio의 Release 빌드에서 등록된 시험 24개가 모두 통과했다고 적는다(GoogleTest의 경우로는 641개).

| 대상 | 결과 | 보이는 원인 |
|---|---|---|
| 라이브러리 | 컴파일된다 | |
| cevsim_tests | 통과. 124개의 경우 | |
| 그 밖의 시험 15개 | 통과 | |
| cevsim_debugging_tests와 디버깅 데모 셋 | 컴파일되지 않는다 | tests/include/debugging_fixture.hpp의 122줄. 템플릿 매개변수에 딸린 이름 앞에 template 키워드가 없다. 경고를 오류로 다루는 설정이라 거기서 멈춘다 |
| cevsim_structural_effect_tests, cevsim_component_reuse_tests | 컴파일되지 않는다. 이 둘을 쓰는 시험 넷을 돌리지 못한다 | 시험의 Packet 구조체에 시각(long double)이 들어 있다. 이 환경에서 long double은 16바이트라 구조체가 48바이트가 되어 값 메시지의 한도 32바이트를 넘는다. long double이 8바이트인 MSVC에서는 32바이트다 |

## 3. 공통 모델 기반을 올리는 방법

규약은 pyevsim 실행기와 같다(15 문서의 3절). 출력은 전이하기 전의 상태에서 내고, 받은 것은 묶음에 모아 두기만 하고, 그 시각에 임박한 모델이 모두 출력한 뒤에 전이를 한꺼번에 한다. cevsim에서 모델이 정할 수 있는 것은 시간 전진과 일정을 지키겠다는 표시뿐이고, 엔진이 어떤 모델의 다음 사건 시각을 다시 계산하는 때는 그 모델이 차례를 마쳤거나 메시지를 받았을 때뿐이다. 그 위에서 순서를 지키게 한다.

| 필요한 것 | 방법 |
|---|---|
| 값의 전달 | 값은 Python에 둔다. 낸 모델이 방금 낸 값을 포트마다 적어 두고, 받는 쪽은 메시지의 출처와 포트로 그것을 찾아 읽는다 |
| 같은 시각의 처리 순서 | 모델을 경로의 순서로 올린다. 엔진은 같은 시각의 모델을 만든 순서로 처리한다(G6). 참조 시뮬레이터의 순서다 |
| 전이를 한꺼번에 | 전이를 맡는 모델 하나를 맨 나중에 올린다. 차례가 온 공통 모델은 숨은 포트로 그 모델을 먼저 깨우고 그다음에 출력을 낸다(G17). 깨어난 모델은 그 시각에 임박해지고, 번호가 가장 크므로 그 시각에 임박한 모델이 모두 차례를 마친 뒤에 차례가 온다(G18). 차례가 오면 모든 공통 모델에 전이 신호를 보내고, 신호를 받은 모델 가운데 출력했거나 받은 것이 있는 모델이 전이한다 |
| 시각 | 공통 모델의 시각은 시간 단위의 눈금으로 센다(17 문서). 엔진에는 다음 사건의 눈금의 시각에서 엔진의 지금 시각을 뺀 값을 시간 전진으로 내놓고, 지금이 어느 눈금인지는 엔진의 시각을 시간 단위로 나눠 읽는다. 낼 차례인지는 눈금의 정수를 견줘서 안다 |
| 같은 눈금의 모델이 엔진에서도 같은 시각에 | 전이 신호는 모든 공통 모델에 간다. 그래서 전이했든 아니든 모든 공통 모델의 다음 사건 시각이 그 시각을 기준으로 다시 잡힌다. 같은 기준에 같은 값을 더하므로 같은 눈금의 모델들은 엔진에서 정확히 같은 시각에 잡히고, 차례가 경로의 순서로 온다 |
| 다음 사건 시각 | 엔진은 공통 모델이 메시지를 받거나 차례를 마칠 때마다 시간 전진을 다시 묻는다. 그때마다 그 모델의 눈금에서 셈해 준다. 제 차례를 마쳤으면 무한대, 차례를 청했거나 이 눈금에 낼 차례이면 0, 그 밖에는 다음 사건의 눈금의 시각에서 엔진의 지금 시각을 뺀 값이다. 남은 눈금 수에 시간 단위를 곱한 값을 주지 않는 까닭은, 엔진이 그것을 더해 갈 때마다 끝자리의 오차가 쌓여 긴 실행에서 엔진의 시각이 눈금에서 멀어지기 때문이다(17 문서의 3절). 엔진에 일정을 지키게 하는 표시(G16)는 쓰지 않는다 |
| 아무도 깨우지 않은 시각의 입력 | 고유 모델이나 밖에서 온 입력을 받았는데 그 시각에 전이를 맡는 모델을 깨운 공통 모델이 아직 없으면, 받은 모델이 시간 전진 0을 돌려주어 그 시각에 차례를 청한다. 그 눈금이 낼 차례가 아니면 깨우기만 하고 내지 않는다 |
| 엔진이 아직 차례를 주지 않은 모델 | 전이를 맡는 모델은 차례가 왔을 때 그 눈금에 낼 차례인데 아직 내지 않은 공통 모델이 있으면, 전이 신호 대신 차례를 주는 신호를 먼저 보낸다. 그 모델들이 낸 뒤에 다시 차례를 받아 전이 신호를 보낸다. 고유 모델의 사건 시각이 공통 모델의 것과 끝자리만 다를 때 생기는 일이다 |

그래서 엔진에는 계획에 없는 것이 오른다. 전이를 맡는 모델 하나, 공통 모델마다 숨은 포트 둘과 연결 둘(깨우는 연결, 전이 신호의 연결)이다. pyevsim 실행기는 아무것도 더 올리지 않았다. pyevsim에서는 모델이 요청 시각을 직접 내놓을 수 있어 엔진을 거치지 않고 전이할 수 있었기 때문이다. 관찰은 더 올린 것을 빼고 읽고, 시험은 더 올린 것이 정확히 이것뿐임을 엔진에서 읽어 확인한다.

어긋남의 검사. 엔진이 공통 모델에 차례를 준 눈금이 그 모델이 낼 눈금과 다르거나(입력을 받아 청한 차례가 아닌데), 엔진의 시각이 그 모델이 낼 눈금을 지나쳤으면 RuntimeError로 알린다. 눈금과 엔진의 시각이 서로 어긋났다는 뜻이다.

명제. 계획의 원자가 모두 공통 모델 기반이고 모든 시간 전진이 시간 단위의 정수배라고 하자. cevsim 실행기가 만든 엔진을 시각 T까지 돌린 사건 기록과 원자들의 마지막 상태는 참조 시뮬레이터가 같은 계획의 모델을 T까지 돌린 것과 같다. 시간 단위가 이진수로 정확히 적히는지와 상관없다(17 문서의 명제).

논증. 한 눈금 안의 차례 하나를 놓고 본다. 공통 모델마다 다음 사건의 눈금은 마지막 전이의 눈금에 그때의 시간 전진의 눈금 수를 더한 정수이고, 참조 시뮬레이터가 적어 두는 값과 같다. 엔진의 일정에는 기준 시각에, 다음 사건의 눈금의 시각에서 기준 시각을 뺀 값을 더한 시각이 잡힌다. 눈금이 크면 그 시각도 크고, 같은 눈금의 모델은 같은 기준에서 같은 값을 받으므로 같은 시각에 잡힌다. 따라서 엔진이 고른 시각의 눈금과 그 눈금에 낼 모델의 집합이 참조와 같다. 낼 모델은 경로의 순서로 차례가 오고, 전이가 신호를 받을 때까지 미뤄져 있으므로 전이하기 전의 상태에서 낸다. 낸 값은 받는 모델의 묶음에 모이고, 묶음은 전이할 때 출처의 순서로 늘어놓는다. 전이를 맡는 모델의 차례는 그 눈금에 낼 모델이 모두 차례를 마친 뒤에 오고, 그때 출력했거나 받은 모델만 전이한다. 출력했고 받은 것이 있으면 겹친 전이, 출력만 했으면 내부 전이, 받기만 했으면 흐른 시간을 주는 외부 전이다. 전이한 뒤의 시간 전진이 0인 모델은 같은 눈금에 다시 낼 차례가 되어 다음 차례가 된다. 모델에 주는 시각과 흐른 시간은 참조 시뮬레이터와 같은 정수에 같은 시간 단위를 곱한 값이다. 참조 시뮬레이터의 한 걸음이 이와 같다. 손으로 쓴 논증이고 무작위 대조로 확인했다(4절, 17 문서의 5절).

섞인 계획. 고유 모델이 공통 모델에 보낸 메시지는 값이 None인 입력 하나가 된다. 같은 눈금에 온 것은 보낸 쪽이 공통 모델이든 고유 모델이든 한 묶음으로 받아 한 번 전이한다. 고유 모델의 사건 시각이 눈금의 시각과 끝자리만 달라도 그 눈금의 것으로 받는다. 눈금 밖의 시각에 닿으면 OffGrid다. 고유 모델은 경로의 순서로 공통 모델과 섞여 차례가 오고, 받은 즉시 전이한다. 그래서 입력에 곧바로 반응하는 고유 모델은 같은 차례 안에서 내고, 그것도 그 차례의 묶음에 든다. 공통 모델이 고유 모델에 보낸 것은 값 없이 전달된다.

외부 입력. inject로 넣은 입력은 값이 None인 입력이다. 엔진은 그 시각의 내부 사건보다 먼저 전달한다. 받은 공통 모델이 그 시각에 낼 차례였으면 내고 겹친 전이를 하고, 아니면 외부 전이를 한다. 같은 시각의 입력 둘은 한 묶음이 된다.

| W1 | 엔진에 더 올리는 것 | 공통 모델 기반을 쓰면 엔진의 내용이 계획과 같지 않다. 전이를 맡는 모델과 연결이 더 있다. 충실성은 그것을 뺀 나머지에 대한 것이다 |
| W2 | 엔진의 성질에 기댄 장치 | 3절의 장치는 같은 시각의 순서가 만든 순서라는 것(G6, G18), 메시지의 전달 순서(G17), 메시지를 받거나 차례를 마친 모델의 시간 전진을 엔진이 다시 묻는다는 것에 기댄다. 엔진의 보호 멤버 둘도 읽는다. 엔진이 이것을 바꾸면 실행기를 고쳐야 한다. 사실 시험과 순서 검사가 그것을 알린다 |
| W3 | 고유 모델 | 참조와 견줄 수 없다. 상태를 Python에서 읽을 수 없다. 기록에 값이 없다. 예시의 모델베이스를 고유 모델로 쓰지 않았다. 값 메시지에 실을 수 있는 것은 32바이트 이하의 단순한 타입이라 일감 같은 객체를 싣지 못한다 |
| W4 | 시각 | 공통 모델의 시각은 시간 단위의 눈금이다. 시간 전진이 시간 단위의 정수배가 아니면 OffGrid다. 눈금에서 상대 오차 1e-9 안의 값은 그 눈금으로 읽는다. 고유 모델은 엔진의 시각(long double의 누적 합)을 그대로 쓰므로 그 기록의 시각은 플랫폼에 따라 끝자리가 다를 수 있고, 시간 단위가 이진수로 정확히 적히지 않으면 같은 눈금 안에서 고유 모델과 공통 모델의 순서가 엔진의 시각이 이른 쪽부터가 된다. 17 문서의 6절 |
| W5 | 외부 입력 | 값이 없다. 지난 시각에는 넣을 수 없다 |
| W6 | 뿌리의 출력 | 값이 없다. 값은 기록과 계획의 연결에서 셈해야 한다. 기록하지 않는 고유 모델(record=False)이 낸 것은 누가 냈는지 모른다 |
| W7 | 컴파일 | C++23 컴파일러와 cevsim의 소스가 있어야 한다. 처음 한 번 30초쯤 걸린다. g++ 13.3과 리눅스 x86-64에서만 확인했다 |
| W8 | 성능 | 재지 않았다. 공통 모델 기반의 전이와 출력은 그때마다 Python으로 넘어오고, 한 차례마다 전이 신호가 모든 공통 모델에 가며 그때마다 엔진이 모든 공통 모델의 시간 전진을 다시 묻는다. 엔진이 공통 모델에 준 차례의 수는 Simulation.turns로 읽을 수 있다 |
| W9 | 쓰지 않은 엔진의 기능 | 평탄 백엔드, 비동기 실행, 실제 시간 모드, 저장과 복원, 디버깅과 수리의 API. 공통 모델의 상태는 Python에 있고 감싼 고유 모델은 저장할 필드를 내놓지 않으므로, 엔진의 저장과 복원은 이 실행기로 올린 모델에 쓸 수 없다 |
| W10 | 자원 | Simulation은 close로 닫아야 엔진이 지워진다 |
| W11 | 확인한 커밋 | 45e7fa9 하나다. a9886a6에서는 돌지 않는다. 그 커밋의 실행기는 이 저장소의 5261f91에 있다 |
| W12 | 겹치는 코드 | 병렬 DEVS의 규약을 지키는 부분(묶음의 순서, 세 가지 전이)이 pyevsim 실행기와 cevsim 실행기에 따로 적혀 있다. 같은 시험 입력으로 두 쪽을 확인하지만 한곳으로 모으지는 않았다 |
| W13 | 값 포트 | 고유 모델 사이에서만 쓸 수 있다. 공통 모델과 뿌리의 포트에는 이을 수 없다 |

## 7. 결정이 필요한 것

| 번호 | 결정 | 상태와 권고 |
|---|---|---|
| U1 | cevsim의 G2와 G3을 고칠 것인가 | 끝났다. cevsim의 main이 고쳤다. 일정은 모델마다 기억해 둔 자리에서 그 항목 하나를 빼고, 메시지는 그 메시지 하나만 뺀다. 내 제안(patches/cevsim_a9886a6_schedule_and_messages.patch)은 a9886a6에만 맞는다. cevsim 저장소의 검토 글(benchmarks/repair/coupled_feedback_20261114/patch_review/REPORT.md)은 제안의 규칙이 옳고 앞선 구현을 되살릴 때에는 쓸 만하지만, 지금의 코드에는 그대로 넣지 말라고 적는다. 그 판단에 동의한다. 파일은 기록으로만 둔다 |
| U2 | 메시지에 값을 실을 것인가 | 일부가 풀렸다. cevsim에 값 메시지가 생겼다. 다만 32바이트 이하의 단순한 타입만 싣는다. 남은 결정은 실행기가 그것을 쓸 것인가다. 수를 주고받는 포트라면 공통 모델과 고유 모델 사이에 값을 건넬 수 있다. 포트 타입마다 C++ 타입을 정해야 하고 다리에 그 타입들의 변환이 들어간다. 필요가 생길 때 한다 |
| U3 | 계층 실행기(G1) | 끝났다. cevsim의 main에서 계층 실행과 평탄 실행의 결과가 같다. 실행기는 3절의 까닭으로 여전히 평탄화한다. 고유 모델만 있는 계획을 계층 그대로 올리는 것은 만들지 않았다 |
| U4 | cevsim에 알릴 것 | 이 세션은 cevsim을 읽기 전용으로 붙였다. 알릴 만한 것은 2.1절이다. g++와 리눅스에서 시험 여섯 대상이 컴파일되지 않고 저장과 복원의 시험 열한 경우가 실패한다. 원하면 이슈로 정리하거나 쓰기 권한으로 다시 붙여 고친 것을 올릴 수 있다 |
| U5 | 플랫폼의 모델 계약 | 15 문서의 Z1과 같은 결정이다. 공통 모델 기반을 계약으로 두면 같은 모델베이스가 참조 시뮬레이터, pyevsim, cevsim에서 같은 기록을 낸다 |
| U6 | 플랫폼의 시각 | 끝났다(2026-11-15). 권고대로 계약에 시간 단위를 두었다. 바인딩에 적고, 참조 시뮬레이터와 두 실행기가 그 눈금의 정수로 시각을 센다. 시간 단위가 이진수로 정확히 적히지 않아도 세 기록이 같다. 17 문서 |
| U7 | 앞선 커밋의 지원 | 실행기는 main을 따른다. a9886a6은 cevsim의 develop과 feature/Multithreading 브랜치에 남아 있다. 그쪽이 필요하면 5261f91의 다리를 따로 되살려야 한다. 권고는 되살리지 않는 것이다. 그 커밋의 엔진에는 결과를 조용히 바꾸는 결함이 있다 |
