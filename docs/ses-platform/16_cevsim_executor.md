# cevsim 실행기

작성일: 2026-11-14

cevsim(https://github.com/eventsim/cevsim)을 pyevsim과 같은 방식으로 붙인 기록이다. cevsim은 C++20으로 쓴 이산 사건 엔진이다. 계약과 합격 기준은 15 문서와 같다. 충실성(엔진에서 다시 읽은 구조가 계획과 같다)과, 참조 시뮬레이터와 사건 기록이 같다는 것이다.

구현은 ses_core/cevsim_executor.py와 ses_core/cevsim_bridge/(C++)이고 검증은 tests/test_cevsim.py다. cevsim은 커밋 a9886a6(Test Case Update)을 읽기 전용으로 받아서 확인했다. cevsim 저장소에는 아무것도 올리지 않았다. cevsim의 소스와 C++ 컴파일러가 없으면 시험은 건너뛴다.

## 0. 판정

| 기준 | 결과 |
|---|---|
| 계약 | 같다. Executor의 conventions, build, observe를 구현했고 attach, executable, plan, realize, exec_core, analyze가 고치지 않은 채로 동작한다 |
| 충실성 | 통과. 다만 조건이 하나 붙는다. 공통 모델 기반을 올릴 때 엔진에 계획에 없는 모델 하나와 연결(공통 모델마다 둘)을 더 올린다. 그것을 뺀 나머지가 계획의 평탄화와 같고, 더 올린 것이 정확히 무엇인지도 엔진에서 읽어 확인한다. 무작위 구조 500개, 무작위 문서의 계획 346개, 두 예시의 변이 71개 |
| 사건 기록, 공통 모델베이스 | 통과. 출력 사건의 열이 순서까지 같고 모델의 마지막 상태도 같다. 무작위 구조 500개(사건 8,325개), 무작위 문서의 계획 346개(사건 820개), 처리 시스템 15개 변이, 센서 노드 56개 변이 |
| 사건 기록, cevsim 고유 모델 | 견줄 수 없다. cevsim의 메시지에는 값이 없어 예시의 모델(일감을 주고받는다)을 고유 모델로 쓸 수 없다. 고유 모델은 작은 시험용 모델로 올려 구조와 기록만 확인했다 |
| cevsim 저장소의 자체 시험 | 17개가 이 환경에서 모두 통과한다 |

꼭 알아야 할 것 넷.

- cevsim 엔진에 결과를 조용히 바꾸는 결함이 둘 있다. 다음 사건 시각이 같은 모델 둘 가운데 하나가 메시지를 받으면 다른 하나가 일정에서 사라진다. 한 번의 출력에서 메시지를 둘 내면 첫째만 전달된다. 둘 다 같은 원인이고, 작은 프로그램으로 다시 실행해 볼 수 있다(2절의 G2, G3). 고치는 방법을 고친 사본에서 확인했다(7절).
- cevsim의 계층 실행은 평탄 실행과 결과가 다르다. 같은 구조를 평탄하게 올리면 경계로 나간 출력이 30개이고 결합 모델 안에 넣으면 12개다. 그래서 실행기는 평탄화해서 올린다.
- 사건 기록을 같게 만든 것은 엔진이 아니다. 공통 모델 기반을 올릴 때 실행기가 위의 결함을 피해 가고 병렬 DEVS의 규약을 엔진의 호출 순서 위에서 지킨다. 고유 모델은 엔진의 성질을 그대로 받는다.
- cevsim의 메시지에는 값이 없다. 출처와 포트와 예약 시각뿐이다. 공통 모델 기반의 값은 Python에 두고, 받는 쪽이 메시지의 출처를 보고 찾아 읽는다.

## 1. 계약과 쓰는 법

```python
from ses_core import executor as X
from ses_core.cevsim_executor import CevsimExecutor
from examples import processing_mb

cx = CevsimExecutor(cevsim_home="/path/to/cevsim", time_step=1.0)      # 환경 변수 CEVSIM_HOME으로 주어도 된다
binding = X.load_binding("docs/ses-platform/examples/processing_system.binding.cevsim.yaml")
L, ext = X.attach(L0, cx, binding, processing_mb.LIBRARY)             # L0는 구조와 속성이 얹힌 SES
sim = X.realize(L, ext, cx, V)                                        # V는 실행 가능한 변이
log = sim.run(20.0)
sim.close()
```

cevsim은 C++ 라이브러리이고 Python에서 부르는 길이 없다. 그래서 실행기는 세 가지를 하나의 공유 라이브러리로 컴파일해 ctypes로 부른다. cevsim의 소스, 다리(ses_core/cevsim_bridge/bridge.cpp), 고유 모델을 등록하는 C++ 소스다. 컴파일은 처음 조립할 때 한 번 하고(이 환경에서 13초쯤), 소스의 내용이 같으면 앞서 만든 것을 다시 쓴다. cevsim의 소스는 고치지 않는다. 실행 가능성의 판정에는 컴파일이 필요 없다.

| 계약의 자리 | cevsim 실행기가 하는 일 |
|---|---|
| 규약 (conventions) | V1 하나. 원자의 포트 이름이 실행기가 쓰는 두 이름(__wake__, __commit__)이면 안 된다 |
| 조립 (build) | 엔진을 하나 만들고 계획의 원자마다 모델을 하나 올린다. 계획의 평탄화를 엔진의 결합으로 등록하되 길의 수만큼 등록한다. 뿌리의 포트는 엔진의 입력 포트와 출력 포트가 된다. 공통 모델 기반이 있으면 전이를 맡는 모델 하나와 그 연결을 더 올린다(3절) |
| 관찰 (observe) | 엔진의 자료(대기 목록, 실행기 표, 세 종류의 결합 표)와 모델의 포트에서 한 층짜리 구조를 다시 읽는다. 더 올린 것은 빼고 읽으며, Simulation.infrastructure가 따로 내놓는다 |

산출물 Simulation의 쓰임은 pyevsim 실행기의 것과 같다(run, log, leaves, connections, close). 다른 것은 셋이다.

| 이름 | 뜻 |
|---|---|
| infrastructure() | 계획에 없는데 엔진에 올린 모델과 연결 |
| inject(port, at) | 뿌리의 입력 포트로 밖에서 입력을 넣는다. 값은 없다 |
| outputs() | 뿌리의 출력 포트로 나간 것을 (낸 원자, 그 포트)마다 센 수. 시각과 뿌리의 포트 이름은 엔진에 남지 않는다 |

모듈의 본체는 둘 가운데 하나다.

| 본체 | 조립 | 행위의 의미 |
|---|---|---|
| cevsim 고유 모델 | 본체가 Native("이름") 또는 글자. ses_cevsim.hpp의 SES_MODULE로 등록한 C++ 공장을 그 이름으로 불러 CAtomicModel을 만든다. 만들어진 모델이 계획의 포트를 그 방향으로 가졌는지 확인한다. 매개변수는 글자로 넘긴다 | cevsim의 것. 2절의 성질을 그대로 받는다. log에는 낸 포트만 남고 값은 None이다 |
| 공통 모델 기반 | devs.Atomic의 하위 클래스. 모델은 Python에 남고 엔진에는 그것을 대신하는 모델이 오른다. 엔진이 일정과 전달을 맡고 전이는 Python에서 한다 | 병렬 DEVS의 것. 참조 시뮬레이터와 같다(3절) |

고유 모델을 등록하는 예(tests/cevsim_models.cpp).

```cpp
#include "ses_cevsim.hpp"

SES_MODULE(Tick, [](const std::string& name, const ses::Params& p) -> evsim::CAtomicModel* {
    return new CTick(name, p.time("period", 1), p.number("keep") != 0, p.number("twice") != 0);
});
```

```python
cx = CevsimExecutor(time_step=1.0, sources=["tests/cevsim_models.cpp"])
library = {"Tick": Module("Tick", ports, (), params, Native("Tick"))}
```

## 2. cevsim a9886a6에서 확인한 엔진의 성질

소스 전체(헤더 21개, 소스 15개, 1,853줄)를 읽고 성질마다 작은 C++ 프로그램으로 실행해 확인했다. 그 프로그램이 tests/cevsim_facts.cpp이고, tests/test_cevsim.py의 test_fact_engine_properties가 컴파일해 돌려 아래의 값을 견준다. 다른 커밋에서는 건너뛴다.

| 번호 | 확인한 성질 | 실행한 결과 | 실행기에 준 영향 |
|---|---|---|---|
| G1 | 결합 모델을 엔진에 올리면 계층 실행기가 맡는다. 그 결과가 같은 구조를 평탄하게 올린 것과 다르다. 계층 실행기는 사건마다 자식 하나만 처리한다 | 생성기 하나와 중계기 셋. 평탄: 경계로 나간 출력 30, 중계기가 낸 횟수 10, 10, 10. 계층: 12, 그리고 1, 1, 10 | 계획의 평탄화를 올린다. 결합 모델을 쓰지 않는다 |
| G2 | 일정 목록은 다음 사건 시각만으로 견주는 다중집합이다. 메시지를 받는 모델을 목록에서 뺄 때 열쇠로 지우므로 그 시각과 같은 모든 항목이 함께 빠진다. 받은 모델만 다시 들어간다 | 주기 5인 모델 둘 가운데 하나만 매 시각 메시지를 받는다. 시각 12까지 받는 쪽은 2번 내고, 아무것도 받지 않는 쪽은 0번 낸다(바른 값은 2) | 공통 모델 기반은 다음 사건 시각을 모델마다 아주 조금씩 다르게 준다(3절). 고유 모델은 그대로다 |
| G3 | 메시지 묶음도 예약 시각만으로 견주는 다중집합이다. 전달을 마친 메시지를 열쇠로 지우므로 예약 시각이 같은 나머지 메시지가 함께 사라진다 | 한 번의 출력에서 두 포트로 하나씩 낸다. 첫째 포트의 수신 3, 둘째 포트의 수신 0. 예약 시각이 같은 외부 입력 둘도 하나만 전달된다 | 공통 모델 기반은 메시지마다 예약 시각을 다르게 준다. 외부 입력도 그렇게 넣는다. 고유 모델은 그대로다 |
| G4 | 메시지에는 출처, 포트, 예약 시각만 있다. 값이 없다. 생성자가 비공개라 하위 클래스로 값을 실을 수도 없다 | 소스에서 읽었다 | 공통 모델 기반의 값은 Python에 두고 받는 쪽이 출처를 보고 읽는다. 고유 모델의 기록에는 값이 없다 |
| G5 | 시각은 time_resolution씩 나아가고, 다음 사건 시각이 현재 시각보다 크지 않은 모델을 처리한다. 격자 밖의 시각은 오류 없이 다음 눈금으로 올려진다 | 주기 0.5인 모델이 시간 간격 1에서 매 눈금 낸다. 주기 1처럼 움직인다 | 공통 모델 기반은 시간 전진이 간격의 배수가 아니면 OffGrid를 낸다. 고유 모델은 알릴 방법이 없다 |
| G6 | 같은 시각의 모델은 하나씩 처리된다. 출력은 받는 모델의 전이로 바로 넘어가고, 엔진은 받은 모델의 다음 사건 시각을 다시 잡는다. set_cancel_reschedule을 부르면 앞선 시각을 지킨다. 같은 시각의 모델들 사이의 순서는 눈금마다 뒤바뀐다 | 주기 3인 모델이 매 시각 입력을 받으면 0번, 표시를 쓰면 2번 낸다. 서로 잇지 않은 두 모델의 순서는 b a, a b, b a, a b | pyevsim과 같은 종류의 의미다. 3절의 규약으로 메운다. 순서는 다음 사건 시각의 아주 작은 차이로 정한다 |
| G7 | 같은 결합을 두 번 등록하면 두 번 전달된다 | 출력 2번에 수신 4번 | 길의 수만큼 등록한다 |
| G8 | simulate(t)는 현재 시각에서 t 뒤까지의 눈금을 끝을 포함해 처리한다 | 주기 1인 모델이 simulate(3)에서 3번, 이어서 simulate(2)를 부르면 모두 6번 낸다 | run은 마지막 눈금의 반 칸 뒤까지 돌린다 |
| G9 | 엔진의 경계로 나간 출력에는 시각도 경계의 포트 이름도 남지 않는다. 낸 모델과 그 포트만 남는다 | 뿌리의 출력 둘에 이은 모델의 출력 2번이 a.out으로 4개 남는다 | outputs는 (낸 원자, 포트)마다의 횟수만 준다 |
| G10 | 외부 입력은 모든 모델이 쉬고 있어도 전달된다. 엔진은 일찍 끝나지 않는다. 설정의 가상 시간 모드는 실제 시간에 맞춰 쉬는 것만 끈다. 다만 외부 입력으로 그 시각에 임박해진 모델은 다음 눈금에 처리된다 | 시각 3의 입력이 시각 3에 전달된다. 시각 2의 입력에 곧바로 반응할 중계기는 시각 3에 낸다 | 공통 모델 기반에서 이 늦음이 일어나면 오류로 알린다 |
| G11 | 자기 자신에게 이은 모델의 주기는 그대로다 | 주기 2인 모델이 시각 12까지 6번 낸다 | pyevsim의 E5는 여기에 없다 |
| G12 | 생성 시각이 0이 아닌 모델은 시간 전진이 그 시각보다 크지 않으면 만들어진 눈금에 곧바로 낸다 | 시각 3에 만든 주기 2인 모델이 3, 5, 7, 9에 낸다(바른 값은 5, 7, 9) | 실행기는 모든 모델을 시각 0에 올린다 |
| G13 | 엔진은 모델을 가상 소멸자가 없는 바탕 클래스(CModel)의 포인터로 지운다. 파생 클래스의 소멸자가 불리지 않는다. 실행을 시작하지 않은 엔진은 모델을 지우지 않는다 | 엔진을 지울 때 모델의 소멸자가 불린 횟수 0. 주소 검사기(AddressSanitizer)는 이 지우기를 new-delete-type-mismatch로 알린다 | 다리의 모델은 스스로 가진 자원이 없다. 자원은 다리가 따로 가진다 |
| G14 | 내부 결합으로 가는 메시지마다 엔진이 스레드를 하나 만들어 전달하고 끝나기를 기다린다 | 소스에서 읽었다. 재지 않았다 | 공통 모델 기반의 전이는 그 스레드에서 Python으로 넘어온다. 예외는 적어 두었다가 run에서 다시 낸다 |

G2, G3, G12, G13은 결함으로 보인다. G1은 계층 실행기가 아직 완성되지 않은 것으로 읽힌다(소스에 TODO가 있다). 저장소의 시험도 같은 차이를 담고 있다. 버퍼 100개를 평탄하게 올린 시험은 출력 10,000개를, 결합 모델 안에 넣은 시험은 100개를 기대한다. G10의 늦음도 의도한 것인지 확인이 필요하다. 나머지는 설계의 선택으로 읽힌다. 이 구분은 내 판단이다.

G2와 G3은 저장소의 자체 시험에서 드러나지 않는다. 시험의 모델들이 모두 메시지를 함께 받고, 한 번에 메시지를 하나씩만 내기 때문이다.

## 3. 공통 모델 기반을 올리는 방법

규약은 pyevsim 실행기와 같다(15 문서의 3절). 출력은 전이하기 전의 상태에서 내고, 받은 것은 묶음에 모아 두기만 하고, 그 시각에 임박한 모델이 모두 출력한 뒤에 전이를 한꺼번에 한다. 달라지는 것은 엔진에 그 순서를 지키게 하는 방법이다. cevsim에서 모델이 정할 수 있는 것은 시간 전진뿐이고, 엔진이 어떤 모델의 다음 사건 시각을 다시 계산하는 때는 그 모델이 전이했거나 메시지를 받았을 때뿐이다.

| 필요한 것 | 방법 |
|---|---|
| 값의 전달 | 값은 Python에 둔다. 낸 모델이 방금 낸 값을 포트마다 적어 두고, 받는 쪽은 메시지의 출처와 포트로 그것을 찾아 읽는다(G4) |
| 다음 사건 시각이 겹치지 않게 | 엔진에 돌려주는 시간 전진에서 모델마다 다른 아주 작은 값을 뺀다. 시간 간격의 100만분의 1을 단위로 한다. 다음 사건 시각이 모두 달라지므로 다른 모델이 함께 빠지지 않는다(G2) |
| 같은 시각의 처리 순서 | 위의 작은 값을 경로가 앞선 모델일수록 크게 한다. 엔진은 다음 사건 시각이 이른 것부터 처리하므로 경로의 순서로 처리된다. 참조 시뮬레이터의 순서다(G6) |
| 한 번의 출력에서 여러 메시지 | 메시지마다 예약 시각을 다르게 준다(G3) |
| 전이를 한꺼번에 | 전이를 맡는 모델 하나를 더 올린다. 출력한 모델은 숨은 포트로 그 모델을 깨운다. 그 모델에서 빼는 값은 가장 작아서, 그 시각에 임박한 모델이 모두 출력한 뒤에 차례가 온다. 차례가 오면 모든 공통 모델에 전이 신호를 보내고, 신호를 받은 모델이 전이한다. 신호를 받은 모델의 다음 사건 시각을 엔진이 다시 계산한다 |

그래서 엔진에는 계획에 없는 것이 오른다. 전이를 맡는 모델 하나, 공통 모델마다 숨은 포트 둘과 연결 둘(깨우는 연결, 전이 신호의 연결)이다. pyevsim 실행기는 아무것도 더 올리지 않았다. pyevsim에서는 모델이 요청 시각을 직접 내놓을 수 있어 엔진을 거치지 않고 전이할 수 있었기 때문이다. 관찰은 더 올린 것을 빼고 읽고, 시험은 더 올린 것이 정확히 이것뿐임을 엔진에서 읽어 확인한다.

명제 (15 문서의 명제와 같다). 계획의 원자가 모두 공통 모델 기반이고 모든 시간 전진이 time_step의 배수라고 하자. cevsim 실행기가 만든 엔진을 시각 T까지 돌린 사건 기록은 참조 시뮬레이터가 같은 계획의 모델을 T까지 돌린 사건 기록과 같다.

논증은 15 문서의 것과 같고 두 군데가 다르다. 꺼내는 순서는 다음 사건 시각의 작은 차이에서 나온다. 전이는 전이를 맡는 모델의 신호에서 일어나며, 그 모델의 다음 사건 시각이 그 시각의 어느 공통 모델보다 늦고 다음 눈금보다는 이르므로 그 차례는 임박한 모델이 모두 출력한 뒤에 온다. 손으로 쓴 논증이고 무작위 대조로 확인했다(4절). 15 문서와 같이 시간 간격이 2의 거듭제곱 분수인 경우만 다뤘다.

섞인 계획. 고유 모델이 공통 모델에 보낸 것은 값 없는 입력이 된다. 묶음에 그 포트가 빈 목록으로 든다. 다음 사건 시각이 격자 위에 있는 고유 모델은 같은 눈금에서 공통 모델과 전이를 맡는 모델보다 나중에 처리되므로, 그런 고유 모델이 보낸 것은 받은 즉시 외부 전이가 된다. 공통 모델이 고유 모델에 보낸 것은 값 없이 전달된다.

외부 입력. inject로 넣은 입력은 값 없는 입력이다. 그 눈금에 임박한 공통 모델이 있으면 그 차례의 묶음에 들고, 없으면 받은 즉시 외부 전이가 된다. 뒤의 경우에 그 전이의 시간 전진이 0이면 G10 때문에 엔진이 그 모델을 다음 눈금에 처리한다. 실행기는 그것을 오류로 알린다.
