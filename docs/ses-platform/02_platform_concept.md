# 공통 SES 플랫폼 구상

작성일: 2026-11-03

## 1. 목표와 비목표

목표
- 연구와 개발에서 반복 사용하는 SES(System Entity Structure, 시스템 엔티티 구조)를 하나의 코어 라이브러리와 하나의 정준 표현 형식으로 통일한다.
- SES에서 실행 가능한 시뮬레이션 모델까지의 경로(가지치기, 평탄화, 모델 생성, 실험 실행)를 자동화하고 재현 가능하게 만든다.
- 여러 실행 백엔드(pyevsim, evsimpp, 기타 DEVS 시뮬레이터, FMI 기반 도구)를 같은 SES에서 생성할 수 있게 한다.
- LLM(Large Language Model, 대규모 언어 모델)이 SES를 생성하고 플랫폼이 검증하는 경로를 연다.

비목표 (초기 단계)
- 범용 그래픽 편집기. 읽기 전용 뷰어까지만 다룬다.
- 행위(원자 모델 내부 로직)의 자동 생성. 모델베이스 구현체는 사람이 쓰거나 별도 LLM 도구가 만든다. 플랫폼은 인터페이스 계약 검증만 담당한다.
- 특정 시뮬레이터 내부 알고리즘의 변경.

## 2. 이용 시나리오

| 시나리오 | 사용자 | 입력 | 출력 |
|---|---|---|---|
| 변이 실험 | 연구자 | SES, 변수 범위, 실험 프레임 | 모든 변이(열거형 가지치기)에 대한 실행과 결과 표 |
| 설계 공간 탐색 | 연구자 | SES, 목적 함수, 제약 | 목표 지향(선택형) 가지치기로 고른 구성과 근거 기록 |
| 제품 변형 생성 | 개발자 | SES, 구성 파일, 백엔드 바인딩 | 특정 백엔드의 실행 모델 코드 또는 조립 스크립트 |
| 테스트 시나리오 생성 | 개발자 | 시스템 SES와 실험 프레임 SES | 테스트 구성 집합과 실행 결과 |
| 교육과 문서화 | 교수자, 학생 | SES 파일 | 트리와 결합 그래프 시각화, 패턴 린트 결과 |
| LLM 보조 모델링 | 연구자, 개발자 | 자연어 요구 | 검증을 통과한 SES 초안, 수정 제안 |

## 3. 요구사항

기능 요구사항
| 번호 | 요구사항 |
|---|---|
| F1 | SES의 네 노드 종류(entity, aspect, multi-aspect, specialization)와 확장 요소(변수, 속성, 포트, 결합, 규칙, 제약, 우선순위, 복제 개수)를 표현한다 |
| F2 | 여섯 공리(uniformity, strict hierarchy, alternating mode, valid brothers, attached variables, inheritance)를 자동 검증한다 |
| F3 | 가지치기 방식: 대화형, 자동, 열거형, 선택형, 반응형을 지원하고 결정 기록(trace)을 남긴다 |
| F4 | PES를 FPES로 평탄화하고, FPES를 백엔드별 모델로 생성한다 |
| F5 | 모델베이스 바인딩을 SES와 분리하여 관리하고, 포트와 생성자 인자 계약을 검증한다 |
| F6 | 실험 프레임을 SES로 기술하고 시스템 SES와 합성한다 |
| F7 | SES 병합(merge), 차이(diff), 질의(구조 질의, IO 질의)를 제공한다 |
| F8 | 다른 형식(SESToPy JSON, SESTools XML, SysML v2 변이 모델, feature model)과의 가져오기와 내보내기 |
| F9 | 작성 패턴 린트: 패턴 위반과 권장 구조를 보고한다 |
| F10 | CLI와 Python API. 읽기 전용 웹 뷰어 |

비기능 요구사항
| 번호 | 요구사항 |
|---|---|
| N1 | 정준 표현은 텍스트(YAML/JSON)이며 스키마로 검증되고 git diff가 의미 있게 읽힌다 |
| N2 | 코어는 GUI, 시뮬레이터, 네트워크에 의존하지 않는다 (순수 Python 패키지) |
| N3 | 규칙과 제약은 코드 문자열 평가(eval)를 쓰지 않는다 |
| N4 | 같은 SES와 구성과 바인딩에서 항상 같은 모델이 나온다 (결정성) |
| N5 | 확장은 플러그인(엔트리 포인트)으로 추가하고 코어를 수정하지 않는다 |
| N6 | C++ 백엔드(evsimpp)는 Python에서 코드 생성 또는 JSON 교환으로 연결한다. 코어의 C++ 재구현은 2단계 이후 과제 |

## 4. 아키텍처

계층 구조 (아래가 기반)

| 계층 | 이름 | 책임 | 의존 |
|---|---|---|---|
| L5 | 도구 | CLI, 웹 뷰어, LLM 어댑터, 편집 보조 | L0 ~ L4 |
| L4 | 실험 | 실험 프레임 합성, 실험 제어(설계점 순회, 반응형 재가지치기), 결과 수집 | L0 ~ L3 |
| L3 | 모델베이스 바인딩과 생성 | 바인딩 파일 해석, 계약 검증, 백엔드별 모델 빌더, 코드 생성 | L0 ~ L2 |
| L2 | 영속화와 교환 | 정준 YAML/JSON 입출력, 스키마 검증, 외부 형식 변환기 | L0 |
| L1 | 연산 | 가지치기 전략, 평탄화, 병합, 차이, 질의, 린트 | L0 |
| L0 | 코어 메타모델 | 노드 클래스, 엔티티 정의 테이블, 표현식 AST, 공리 검증기, 방문자(visitor) 인프라 | 없음 |

모듈 경계 원칙
- L0은 다른 어떤 계층도 모른다. 모든 상위 계층은 L0의 방문자(visitor) 인터페이스로 트리를 순회한다.
- L3의 백엔드 빌더는 공통 중간 표현인 FPES만 입력으로 받는다. 백엔드 추가는 빌더 하나를 추가하는 일이다.
- L5의 LLM 어댑터는 L2의 스키마를 구조화 출력(structured output) 스키마로 쓰고 L1의 검증과 린트 결과를 LLM에 되돌린다.

## 5. 핵심 데이터 흐름

1. SES 정준 파일을 읽어 코어 객체를 만든다. 스키마 검증과 공리 검증을 통과해야 한다.
2. 구성 파일(변수 값, 명시적 결정, 오버라이드)을 읽는다.
3. 가지치기 파이프라인이 결정 지점을 순서대로 처리한다. 각 결정은 전략(규칙 평가, 명시 결정, 대화형 질의, 탐색 알고리즘)에 위임되고 결정 기록에 쌓인다.
4. 제약 검사: 가지치기 중간과 완료 시점에 선택 제약을 검사한다. SES-X의 2단계 가지치기처럼 "검증용 가지치기"와 "실행용 가지치기"를 단계로 분리할 수 있다.
5. PES를 평탄화하여 FPES를 만든다. FPES는 리프 엔티티 인스턴스 목록, 속성 값, 결합 목록으로 이루어진 단순 구조다.
6. 바인딩 파일을 적용하여 각 리프 인스턴스를 모델베이스 구현체에 매핑하고 계약을 검증한다.
7. 백엔드 빌더가 실행 모델(객체 그래프 또는 소스 코드)을 생성한다.
8. 실험 계층이 모델을 실행하고 결과를 수집한다. 반응형 모드에서는 결과가 재가지치기 이벤트를 발생시켜 3단계로 돌아간다.

모든 단계의 산출물(SES, 구성, 결정 기록, PES, FPES, 바인딩, 생성 모델 메타데이터)은 파일로 남아 재현과 비교가 가능하다.

## 6. 아티팩트 분리

| 아티팩트 | 내용 | 변경 주체 | 수명 |
|---|---|---|---|
| SES | 타입 수준 변이 공간 | 모델러 | 길다. 버전 관리 대상 |
| 구성(configuration) | 변수 값, 명시 결정, 오버라이드 | 실험자 | 실험마다 다르다 |
| 바인딩(binding) | 엔티티와 백엔드 구현체 매핑 | 개발자 | 백엔드마다 다르다 |
| 결정 기록(trace) | 가지치기 중 내려진 결정과 근거 | 플랫폼 | 실행마다 생성 |
| PES, FPES | 가지치기와 평탄화 결과 | 플랫폼 | 파생물. 재생성 가능 |
| 실험 프레임 SES | 생성기, 수용기, 변환기 구조 | 실험자 | 시스템 SES와 독립 |

이 분리가 플랫폼의 핵심 설계 결정이다. 선행 도구는 이 가운데 SES 하나에 모든 것을 섞었다.

## 7. 백엔드 바인딩 전략

| 백엔드 | 연결 방식 | 비고 |
|---|---|---|
| pyevsim (Python) | FPES에서 직접 객체 그래프를 조립. 바인딩의 module과 class를 import | 1차 목표 |
| evsimpp (C++) | FPES와 바인딩을 JSON으로 내보내고 C++ 쪽 로더가 조립. 또는 C++ 조립 코드 생성 | 2차 목표. 빌더는 Python, 실행은 C++ |
| 기타 Python DEVS (xDEVS 등) | pyevsim과 동일 패턴의 빌더 | 플러그인 |
| FMI, Modelica | Folkerts 2021 방식. FMU 모델베이스와 조립 스크립트 생성 | 선택 |

빌더 인터페이스는 하나다. 입력은 FPES와 바인딩, 출력은 백엔드 고유 산출물과 공통 메타데이터(생성 시각, SES 버전, 구성 이름, 결정 기록 해시)다.

## 8. LLM 연계 지점

| 지점 | 역할 | 플랫폼 기능 |
|---|---|---|
| SES 초안 생성 | 자연어 요구에서 정준 YAML 생성 | JSON Schema를 구조화 출력 스키마로 제공 |
| 검증 루프 | 스키마 오류, 공리 위반, 제약 충돌, 린트 결과를 LLM에 되돌림 | 오류 메시지를 경로와 함께 구조화하여 출력 |
| 가지치기 보조 | 대화형 가지치기의 결정 지점에서 후보와 근거 제시 | 결정 지점 열거 API |
| 모델베이스 구현 생성 | 리프 엔티티의 포트와 속성 계약을 프롬프트로 제공 | 계약 추출 API (statechart 기반 생성 연구와 연결) |
| 결과 해석 | 결정 기록과 실험 결과를 요약 | 결정 기록 표준 형식 |

여기서 플랫폼이 제공하는 것은 "제약과 검증"이다. 이 부분이 선행 LLM 기반 DEVS 생성 연구에 없는 요소다.

## 9. 저장소 구성 제안과 로드맵

제안 구성 (본 저장소 기준)

```
ses_core/          L0 메타모델, 표현식, 공리 검증, 방문자
ses_ops/           L1 가지치기, 평탄화, 병합, 차이, 질의, 린트
ses_io/            L2 정준 표현 입출력, 스키마, 외부 형식 변환기
ses_build/         L3 바인딩, 빌더 인터페이스, 백엔드 플러그인
ses_exp/           L4 실험 프레임, 실험 제어
ses_cli/           L5 CLI
docs/ses-platform/ 설계 문서, 스키마, 예시
tests/
```

로드맵
| 단계 | 산출물 | 완료 기준 |
|---|---|---|
| 1 | 정준 표현 스키마, L0 메타모델, 공리 검증, YAML 입출력 | 예시 SES가 로드되고 공리 위반이 보고된다 |
| 2 | 가지치기(규칙, 명시 결정, 열거형), 평탄화, 결정 기록 | 예시 SES에서 모든 변이의 FPES가 생성된다 |
| 3 | pyevsim 빌더, 바인딩 검증 | 예시 처리 시스템이 pyevsim에서 실행된다 |
| 4 | 실험 프레임 합성, 실험 제어, 반응형 가지치기 | 변수 범위 전체 실험이 자동 실행된다 |
| 5 | evsimpp 빌더(JSON 교환), 린트, 웹 뷰어 | C++ 백엔드에서 같은 모델이 실행된다 |
| 6 | LLM 어댑터, SESToPy JSON 가져오기, SysML v2 내보내기 | 자연어에서 검증 통과 SES까지 도달한다 |

## 10. 결정이 필요한 사항

1. 정준 표현의 기본 형식: YAML(사람 친화)과 JSON(도구 친화) 가운데 저장 기본값. 제안은 YAML 저장, JSON 교환.
2. 표현식 언어 범위: 03 문서의 선언적 AST로 충분한지, 아니면 소형 식 문법(파서 필요)을 추가할지. 제안은 AST로 시작하고 식 문법은 AST로 변환하는 설탕(sugar)으로 나중에 추가.
3. evsimpp 연결 방식: JSON 교환과 코드 생성 가운데 선택. 제안은 JSON 교환 먼저.
4. 결합 패턴의 범위: fan_out_fan_in, chain, ring, broadcast 외 추가 패턴의 필요 여부.
5. 패키지 이름과 공개 범위.
