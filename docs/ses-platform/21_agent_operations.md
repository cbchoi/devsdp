# 에이전트가 부르는 연산

작성일: 2026-11-24 (첫 판 2026-11-23). 구현은 `ses_core/ops.py`, 명령은 `ses ops`와 `ses call`, 시험은 `tests/test_ops.py`다. 묶음의 계약은 `20_packs.md`에 있다.

## 0. 무엇을 정했나

연구실의 구도는 분야의 표현을 SES(System Entity Structure)로, 실행을 DEVS(Discrete Event System Specification)로 두고 그 둘을 에이전트가 엮는 것이다. 이 문서는 에이전트와 플랫폼 사이의 경계를 정한다.

- 에이전트가 하는 일. 묶음의 파일을 글로 고친다. 문서, 모델 베이스, 바인딩, 사례의 결정이다.
- 플랫폼이 하는 일. 고친 묶음을 판정한다. 무엇이 어디서 틀렸는지, 그다음에 무엇을 할지를 기계가 읽는 꼴로 돌려준다.

플랫폼은 에이전트를 갖지 않는다. 언어 모델을 부르는 코드가 플랫폼에 없다. 어떤 에이전트든 일곱 연산을 부르면 된다. 연산은 사람이 쓰는 명령 `ses pack`과 같은 계산을 하고, 결과를 글이 아니라 JSON 값으로 낸다.

파일을 고치는 연산은 두지 않았다. 까닭은 셋이다. 에이전트는 이미 파일을 고치는 도구를 가지고 있다. 문서를 자료구조로 읽어 다시 적으면 주석이 사라진다. 그리고 연구자마다 다른 것은 내용이고 같이 쓰는 것은 판정이다. 편집 모델(13 문서)의 원시 연산을 연산으로 내놓는 일은 남겨 두었다.

이 문서가 주장하지 않는 것. 에이전트가 SES와 그 검사 덕분에 일을 더 잘한다는 것은 여기서 보이지 않았다. 여기서 만든 것은 그 평가가 올라설 표면이다. 평가의 틀은 아직 없다(9절의 R1). 8절의 맡겨 본 결과는 표면의 결함을 찾으려는 것이었고 효과를 잰 것이 아니다.

## 1. 약속

1. 입력과 결과는 JSON 값이다.
2. 결과는 늘 같은 모양의 봉투다(2절). 연산이 실패해도 봉투가 온다.
3. `ops.call`은 예외를 내지 않는다. 잘못은 봉투의 `findings`에 줄로 적힌다. 묶음의 파일이 무엇이든(틀린 YAML, 별칭으로 부풀린 파일, 자기 자신을 가리키는 파일, 글이 아닌 파일) 도구의 결함(A9)이 아니라 그 파일의 줄로 알린다.
4. `ok`는 `findings`에 `error`가 없다는 뜻이다. 그것뿐이다. `ok`가 거짓이어도 `result`에는 그때까지 구한 것이 든다. 구한 것이 없으면 null이다. 그래서 `result`를 읽기 전에 `ok`와 null을 본다.
5. 연산은 작업 자리(root) 안의 디렉터리만 다룬다. 밖을 가리키는 경로는 A0로 거부한다. 묶음 안의 파일이 묶음 밖을 가리키는 링크이면 읽지 않고 P0로 알린다. 기록 파일의 자리에 링크가 있으면 링크를 지우고 묶음 안에 새로 적는다.
6. 파일을 쓰는 연산은 둘이다. `pack_new`와, `record`를 켠 `pack_check`다. 나머지는 묶음의 디렉터리에 아무것도 남기지 않는다. 바이트코드 파일도 남기지 않는다.
7. 결과의 크기에는 한도가 있다(3절의 표). 잘린 곳에는 잘렸다는 표시가 있고, 수는 전체의 것이다.
8. 묶음의 코드가 파이썬의 표준 출력에 찍는 것은 봉투의 `output`에 든다. 결과에 섞이지 않는다.
9. 줄은 사람이 읽는 글(`message`)과 함께 기계가 읽는 것을 가진다. 종류(`kind`), 자료(`data`), 그다음에 할 일(`next`)이다. 같은 부호 안에서 할 일이 다른 것은 `kind`로 가른다(4절).

약속하지 않는 것이 넷 있다.

- 묶음의 모델 베이스는 파이썬 코드이고, 검사와 실행은 그 코드를 연산을 부른 프로세스 안에서 돌린다. 연산은 그 코드를 가두지 않는다. 5번의 약속은 연산이 받는 경로와 묶음의 선언이 가리키는 파일에 대한 것이고 묶음의 코드가 하는 일에 대한 것이 아니다. 에이전트가 쓴 코드를 돌릴 때의 격리(컨테이너, 권한이 낮은 사용자, 시간 제한)는 부르는 쪽이 한다.
- 시간 제한이 없다. 끝나지 않는 모델은 걸음 수의 한도(사례의 `max_steps`, 기본 1,000,000)에서 멈추지만, 한 걸음 안에서 끝나지 않는 코드는 연산을 끝내지 않는다.
- 끼어들기(KeyboardInterrupt)는 봉투로 바꾸지 않고 그대로 내보낸다. 부르는 쪽이 연산을 멈추려는 것일 수 있기 때문이다. 묶음의 코드가 스스로 그것을 내도 같다. 묶음의 코드가 프로세스를 끝내려 하는 것(exit, SystemExit)은 그 사례의 줄(P6)이나 모델 베이스의 줄(P2)이 된다.
- 묶음의 코드가 운영체제의 호출로 프로세스를 바로 끝내면(`os._exit`) 막을 수 없다. 봉투가 나오지 않고 종료 코드는 그 코드가 준 값이다. 0일 수도 있다. 그래서 부르는 쪽은 종료 코드만 보지 말고 봉투가 없으면 실패로 본다. `ses call`에 `--out`을 주면 연산을 돌리기 전에 실패의 봉투를 그 파일에 먼저 적어 둔다. 프로세스가 중간에 끝나면 파일에 남은 것이 실패라고 말한다.

명령 `ses call`은 한 가지가 다르다. 연산의 이름을 주지 않는 것처럼 명령줄 자체가 틀리면 봉투 없이 종료 코드 2로 끝난다. 입력의 JSON이 틀렸거나 입력 파일을 읽을 수 없으면 A0의 봉투가 온다.

## 2. 봉투

```json
{
  "op": "pack_build",
  "version": "1.0",
  "ok": false,
  "findings": [
    {"severity": "error", "code": "P4", "where": "slow",
     "message": "결정이 모자라다. Line/Worker: specialization speed 의 대안이(가) 정해지지 않았다. 남은 선택지: ['Fast', 'Slow']",
     "kind": "undecided",
     "data": {"path": ["Line", "Worker"], "choice": "alternative", "group": "speed", "options": ["Fast", "Slow"], "options_count": 2},
     "next": "그 사례의 결정 집합에 결정을 더한다. ... data.path 가 자리이고 path 에 그대로 적는다. ..."}
  ],
  "result": null,
  "output": ""
}
```

| 항목 | 뜻 |
|---|---|
| `op` | 부른 연산의 이름 |
| `version` | 이 계약의 판. 지금은 1.0 |
| `ok` | `findings`에 `error`가 없으면 참 |
| `findings` | 줄들. 아래의 표 |
| `result` | 연산마다 다른 값(3절). 구하지 못했으면 null |
| `output` | 묶음의 코드가 표준 출력에 찍은 글. 4,000자를 넘으면 끝쪽만 싣고 앞에 잘렸다고 적는다 |

줄 하나가 가지는 것.

| 항목 | 뜻 |
|---|---|
| `severity` | error, warning, info 가운데 하나 |
| `code` | 4절의 부호. 어느 파일의 잘못인지를 가른다 |
| `where` | 그 줄이 가리키는 곳. 부호마다 정해져 있다(4절의 표) |
| `message` | 사람이 읽는 글. 한국어다. 2,000자를 넘으면 자르고 잘렸다고 적는다 |
| `kind` | 줄의 종류. 같은 부호 안에서 할 일이 다른 것을 가른다. 4절의 표와 `ses ops`의 `kinds`에 모두 있다 |
| `data` | 그 종류의 자료. 예: 모자란 결정의 자리와 선택지, 예외가 난 구성요소와 줄 번호 |
| `next` | 그다음에 할 일. 연산을 부르는 쪽의 말로 적었다 |

`kind`, `data`, `next`는 대부분의 줄에 있다. 입력의 스키마를 어긴 줄처럼 종류가 하나뿐인 줄에도 있다. 없을 수 있다고 보고 읽는다.

줄이 200건을 넘으면 오류를 앞세워 199건만 싣고, 마지막에 몇 건이 더 있는지를 A2의 info(종류 more_findings)로 적는다. 줄의 자료도 결과와 같은 값의 수의 한도 안에 든다. 넘는 줄은 자료를 빼고 싣는다.

수를 싣는 법. 변이의 수처럼 클 수 있는 수는 `{"value": 9000, "text": "9000", "exact": true}`의 모양이다. `text`는 늘 있고, `value`는 2의 53제곱보다 작을 때만 수이고 그 밖에는 null이다. `text`는 4,000자리까지 정확한 십진수이고 그보다 큰 수는 어림으로 적으며 그때 `exact`가 거짓이다. 유한하지 않은 수는 글 "INF", "-INF", "NaN"이 된다. 모델이 낸 값 가운데 JSON으로 옮길 수 없는 객체는 글이 된다. 100겹보다 깊이 겹친 값은 그 자리에서 글로 줄인다.

## 3. 연산

| 연산 | 언제 부르는가 | 입력 | 쓰는가 |
|---|---|---|---|
| `pack_new` | 새 분야를 시작할 때 한 번. 돌아가는 묶음을 만들고 바로 검사한다 | `dir`, 선택 `name`, `template` | 쓴다 |
| `pack_check` | 묶음의 파일을 고칠 때마다. 계약을 지키는지 본다 | `dir`, 선택 `record`, `executors` | `record`가 참일 때만 |
| `pack_show` | 묶음을 처음 볼 때. 선언, 사례와 적어 둔 기록, 파일의 목록 | `dir` | 안 쓴다 |
| `pack_choices` | 무엇을 고를 수 있는지 볼 때. 결정을 따르는 변이의 수와 선택 지점마다 남은 선택지 | `dir`, 선택 `case` 또는 `decisions` | 안 쓴다 |
| `pack_build` | 사례가 뜻한 구조인지, 값이 뜻한 대로인지 볼 때. 변이 하나의 구조, 포트, 결합, 속성과 모델이 받는 값 | `dir`, 선택 `case` 또는 `decisions`, `defaults`, `depth`, `limit` | 안 쓴다 |
| `pack_run` | 모델의 행동을 볼 때. 변이 하나를 참조 시뮬레이터로 돌린 출력 사건 | `dir`, `case` 또는 `decisions`, 선택 `defaults`, `until`, `max_steps`, `offset`, `limit` | 안 쓴다 |
| `formats` | 파일의 형식을 모를 때. 파일마다 쓸 수 있는 항목의 이름과 값의 모양 | 없다 | 안 쓴다 |

입력의 정확한 모양은 `ses ops`가 낸다. 연산마다 입력의 JSON Schema가 있고, 스키마에 없는 항목은 거부한다.

결과에 드는 것.

| 연산 | `result` |
|---|---|
| `pack_new` | `files`(만든 파일들)와 `pack_check`의 결과 |
| `pack_check` | `name`, `family`(변이의 수 `variants`, 적격인 변이의 수 `wellformed`, 그 수의 범위 `scope`), `cases`(사례마다 `built`, `ran`, `variables`, `components`. 돌린 사례는 `atoms`, `links`, `events`, `last`, `digest`, `executors`. 돌리지 않는 사례는 구조의 지문 `structure`), `errors`, `warnings`. `record`를 켰으면 `recorded`(기록이 있는 사례의 이름들) |
| `pack_show` | `name`, `title`, `document`, `profile`, `model_base`, `binding`, `executors`, `cases`(사례마다 `name`, `decisions`, `defaults`, `until`, `max_steps`, `recorded`), `experiments`, `files`, `files_count`, `files_truncated` |
| `pack_choices` | `variants`, `core_wellformed`, `points`(선택 지점마다 `owner`, `kind`, `group`, `state`, `remaining`, `remaining_count`, `options`, `options_count`, 잘렸으면 `truncated`) |
| `pack_build` | `variables`, `components`, `nodes`, `structure`(구조의 지문), `tree`(구성요소마다 `name`, `labels`, `attributes`, `ports`, `absent`, `parts`. 부분이 있으면 `couplings`, 모델에 묶였으면 `module`과 `params`, 잘렸으면 `parts_not_listed`), `truncated` |
| `pack_run` | `variables`, `atoms`, `until`, `events`, `last`, `digest`, `offset`, `log`(사건마다 `t`, `at`, `port`, `value`), `truncated` |
| `formats` | `pack`, `document`, `profile`, `attribute_types`, `decisions`, `binding`, `model`, `shapes`(항목마다 값의 모양과 본보기), `checks`(줄의 `data.check`에 오는 부호의 뜻), `templates`, `example` |

읽을 때 헷갈리기 쉬운 것.

- `pack_check`의 `family.scope`. full이면 변이를 열거해 결합, 속성, 프로파일까지 모두 검사한 수다. core이면 열거하지 않고 선택의 핵만 센 수다(큰 족). `pack_choices`의 `core_wellformed`는 늘 핵만 센 수다. 둘의 이름이 다른 것은 뜻이 다르기 때문이다.
- `pack_check`의 `cases`. `built`는 그 사례의 변이를 만들었다는 뜻이고 `ran`은 돌렸다는 뜻이다. 검사가 통과해도 `ran`이 거짓인 사례는 돌려 본 것이 아니다. 모델 베이스의 경고(P2의 warning)는 사례를 건너뛰게 하지 않는다. 건너뛰는 것은 모델 베이스나 바인딩에 오류가 있을 때뿐이다.
- `pack_check`의 `executors`. 실행기마다 reference, same, different, skipped, skipped_native, violates_convention, stopped 가운데 하나다. skipped는 그 실행기가 이 컴퓨터에 없다는 뜻이고 오류가 아니다.
- `pack_choices`의 `state`. open, decided, decided_per_place, none_left 가운데 하나다. 표는 정의마다 한 줄이다. decided_per_place는 변이가 하나로 정해졌고 그 정의가 놓인 자리마다 다른 것이 골라졌다는 뜻이다. 더 정할 것은 없다.
- `pack_choices`는 사례의 `defaults`를 쓰지 않는다. 적힌 결정만 본다. 문서의 기본값이 채우는 것까지 보려면 `pack_build`를 부른다.
- `pack_build`의 `attributes`와 `params`. `attributes`는 문서의 속성 값이다(식과 사례의 `set`을 거친 것). `params`는 묶인 모델이 실제로 받는 값이다. 속성의 이름이 모델의 매개변수 이름과 다르면 그 값은 모델에 가지 않고, 둘이 달라진다.
- `pack_build`는 조립은 되지만 실행 가능하지 않은 변이(묶이지 않은 구성요소, 시간 단위에 어긋난 값)를 오류(P5)로 알린다. 그때도 `tree`는 온다. `module`과 `params`는 구할 수 있는 구성요소에만 싣는다.
- `pack_build`의 `structure`. 구조의 지문이다. 구성요소의 이름과 정의, 빠진 부분, 속성의 값, 포트와 결합이 든다. 속성의 값만 바뀌어도 달라진다.
- `pack_run`의 `log`. 출력 사건만 있다. 모델 안의 상태는 보이지 않는다. 보려면 모델이 포트로 내게 한다.
- `pack_run`의 `decisions`. 선언에 없는 결정 집합 파일을 돌린다. 값을 바꿔 가며 여러 번 돌릴 때 쓴다. 파일을 고쳐 적고 부르기를 되풀이한다. 그때는 `until`을 꼭 준다. 긴 실행이면 `max_steps`를 함께 준다. 기록은 읽지도 적지도 않는다.
- `pack_run`이 실패했을 때의 줄은 `pack_check`가 같은 잘못에 붙이는 `kind`와 `data`를 싣는다. 결정 집합 파일로 돌릴 때는 검사가 그 파일을 보지 않으므로 이 줄이 유일한 자료다.
- 결정 집합의 `set`에서 같은 속성을 `at`으로도 `path`로도 적으면 그 자리에서는 `path`의 값이 쓰인다. `choose`는 다르다. `at`과 `path`가 둘 다 적용되고 어긋나면 변이가 남지 않는다. 같은 곳의 같은 속성을 두 번 적은 파일과 같은 열쇠를 두 번 적은 파일은 거부한다.
- 사례의 `set`은 문서가 식(`expr`)으로 정한 속성도 바꾼다. 결정 집합의 형식이 그렇게 정했다. 경고가 없다.

한도.

| 무엇 | 기본 | 최대 |
|---|---|---|
| `pack_build`가 내는 구성요소의 수(`limit`) | 200 | 2,000 |
| `pack_run`이 한 번에 내는 사건의 수(`limit`) | 50 | 1,000 |
| `pack_run`의 걸음 수의 한도(`max_steps`) | 사례의 것. 1,000,000 | 100,000,000 |
| `pack_show`가 늘어놓는 파일의 수 | 200 | 200 |
| 묶음의 문서에서 multi-aspect 하나의 복제본의 수 | 없다 | 10,000 |
| 결과에 싣는 글 하나의 글자 수 | 20,000 | 20,000 |
| 줄의 `data.options`에 싣는 선택지의 수 | 200 | 200 |
| `pack_choices`가 선택 지점 하나에 늘어놓는 선택지의 수 | 200 | 200 |
| `pack_choices`가 돌아보는 변수 값의 조합 | 200,000 | 200,000 |
| 봉투에 싣는 줄의 수 | 200 | 200 |
| 줄 하나의 글자 수 | 2,000 | 2,000 |
| 결과에 싣는 값의 수 | 200,000 | 200,000 |
| `output`의 글자 수 | 4,000 | 4,000 |

복제본의 수의 한도는 문서에 대한 것이다. 개수(cardinality)나 개수 변수의 범위가 10,000을 넘을 수 있으면 P1의 too_many_replicas로 문서를 받지 않는다. 족을 세는 계산은 더 큰 수도 받지만 묶음의 검사와 조립은 그 크기에서 끝나지 않는다. 긴 글은 20,000자에서 자르고 전체의 길이를 적는다. 잘린 목록에는 전체의 수가 함께 온다(`options_count`, `remaining_count`, `files_count`, 줄이 넘칠 때의 `data.more`).

`limit`이 최대를 넘으면 잘라서 주지 않고 A0로 거부한다. 정수를 받는 입력은 5.0처럼 소수부가 없는 수도 받는다. `pack_run`의 사건은 `offset`과 `limit`으로 나눠 읽는다. 나눠 읽은 것을 이으면 전체다. `digest`는 기록 전체의 지문이고 `pack_check`가 적어 둔 것과 견주는 값과 같다. 선택지가 200개를 넘는 선택 지점은 앞의 200개만 늘어놓고 `options_count`와 `remaining_count`에 전체의 수를 적는다.

`pack_choices`는 변이를 하나씩 만들지 않는다(`theory.md` 7절). 센서 1,000개까지의 무선 센서 네트워크 묶음에서 변이 9,000개와 선택지 1,000개짜리 선택 지점을 바로 답한다. 선택의 핵만 보므로 결합과 속성의 검사는 `pack_check`가 한다. 펼친 나무의 노드를 가리킨 결정(node)은 다루지 않는다(A2). 개수에 상한이 없는 문서는 셀 수 없다(A2의 family_unbounded).

`pack_new`의 `template`. minimal은 가장 작은 묶음이고(구성요소 넷, 사례 둘) full은 변수, 규칙, 없음 대안, 복제, 사례마다 다른 값을 모두 쓰는 묶음이다(사례 여섯). full은 안내서(`GUIDE.md`)의 걸음을 끝까지 따라간 상태와 같다. 형식의 본보기가 필요하면 full을 만들어 읽는다.

## 5. 기록을 적는 일

`record`를 켠 `pack_check`가 하는 일은 이렇다.

- 오류 없이 만들어지고 돌아간 사례의 기록을 records.yaml에 적는다. 오류가 있는 사례의 기록은 적지 않고, 전에 적어 둔 것이 있으면 그대로 둔다.
- 그래서 `ok`가 거짓이어도 다른 사례의 기록은 적혔을 수 있다. `result.recorded`는 지금 기록이 있는 사례들이다. 이번에 적은 것만이 아니라 실패해서 그대로 둔 옛 기록도 든다.
- 적을 글을 먼저 다 만들고, 다시 읽어 같은 사례들인지 보고, 옆에 적은 뒤 바꿔 놓는다. 적다가 실패하면 옛 파일이 남는다.
- 선언에서 사라진 사례의 기록은 지운다.
- records.yaml이 깨졌으면(틀린 YAML, 틀린 모양, 링크, 빈 디렉터리) 적을 사례가 하나도 없어도 새로 적는다. `record`를 켜지 않은 검사는 그것을 P6의 records_file로 알린다. 그 자리에 무엇이 든 디렉터리가 있으면 치우지 않고 P6로 알린다.
- records.yaml은 플랫폼이 적는 파일이다. 에이전트는 손으로 고치지 않는다.

## 6. 쓰는 법

명령으로.

```bash
ses ops
```

```bash
ses call pack_new --args '{"dir": "mylab", "template": "full"}'
```

```bash
ses call pack_check --args '{"dir": "mylab"}'
```

`ses call`은 봉투를 표준 출력의 마지막 줄에 JSON 한 줄로 낸다. 그 줄은 ASCII 글자로만 적는다. 한글은 `\u` 꼴이다. 받는 쪽의 글자 인코딩이 무엇이든 깨지지 않게 하려는 것이다. `--pretty`는 사람이 보라고 여러 줄로, 한글을 그대로 적는다. `--out 파일`은 봉투를 파일에도 적는다. 묶음의 코드가 파이썬 밖에서 표준 출력에 직접 찍으면 그 글이 봉투의 줄 앞에 섞일 수 있는데, 파일은 온전하다. 종료 코드는 `ok`가 참이면 0, 거짓이면 1이다. 입력은 `--args`의 글이나 `--args-file`의 파일(`-`이면 표준 입력)로 준다. 작업 자리는 `--root`로 주고, 주지 않으면 지금 디렉터리다.

파이썬에서.

```python
from ses_core import ops

env = ops.call("pack_choices", {"dir": "mylab", "case": "slow"}, root="/work")
for f in env["findings"]:
    print(f["severity"], f["code"], f.get("kind"), f["where"], f["message"])
```

도구 정의로. `ses ops --tools`와 `ops.tools()`는 연산마다 `name`, `description`, `input_schema`를 가진 목록을 낸다. 도구를 부르는 에이전트 틀에 그대로 넣을 수 있게 이름은 영문자, 숫자, 밑줄만 쓰고, 입력 스키마는 기본 타입, `enum`, `additionalProperties: false`만 쓴다. 수의 범위 같은 조건은 스키마에 두지 않고 연산이 보고 A0로 알린다. 특정 회사의 API에 올려 시험하지는 않았다(9절의 R2).

에이전트가 도는 고리는 이렇다.

1. `pack_show`로 묶음을 읽는다. 처음이면 `pack_new`로 만든다. 형식을 모르면 `formats`를 부르고 `template`을 full로 한 묶음을 읽는다.
2. 파일을 고친다.
3. `pack_check`를 부른다. error가 있으면 줄의 `kind`와 `next`를 따라 고치고 3을 되풀이한다.
4. 구조를 봐야 하면 `pack_choices`와 `pack_build`를, 행동을 봐야 하면 `pack_run`을 부른다.
5. 뜻한 변화로 기록이 달라졌으면 `record`를 켜고 `pack_check`를 부른다.

값을 바꿔 가며 여러 번 돌리는 실험은 두 길이 있다. 연산으로는 결정 집합 파일을 적고 `pack_run`을 `decisions`로 부른다. 파이썬으로는 `ses_core.pack.run`에 `change`를 준다.

```python
from ses_core import pack as P

for seed in range(5):
    log, variables, atoms = P.run("mylab", "fast", change={"set": [{"at": "Source", "attribute": "period", "value": 1.0 + seed}]})
```

`change`는 결정 집합 파일의 `variables`, `choose`, `set`과 같은 모양의 표다. 사례의 결정 위에 얹는다. 같은 변수, 같은 선택 지점, 같은 속성에 대한 것은 바꾸고 없는 것은 더한다.

## 7. 지키는지 보는 것

`tests/test_ops.py`가 본다.

- 부른 결과가 모두 봉투의 스키마에 맞고 JSON으로 오간다.
- 연산마다 사람이 쓰는 명령이나 `pack.check`와 같은 답을 낸다. 지문, 변이의 수, 사건의 수.
- 틀린 입력이 A0나 A1의 줄이 되고 아무 파일도 바뀌지 않는다.
- 묶음의 선언, 문서, 모델 베이스, 바인딩, 결정을 하나씩 깨뜨린 것이 그 자리의 부호와 종류로 알려진다.
- 묶음의 코드가 글을 찍거나, 프로세스를 끝내려 하거나, JSON으로 옮길 수 없는 값을 내도 봉투가 온다.
- 묶음의 파일이 별칭으로 부풀린 YAML이거나, 자기 자신을 가리키거나, 글이 아니거나, 묶음 밖을 가리키는 링크여도 봉투가 오고 A9가 아니다.
- 읽기만 하는 연산의 앞과 뒤에 작업 자리의 모든 파일의 내용이 같다.
- 모델 베이스의 경고가 있어도 사례를 돌리고 기록과 견준다.
- 입력의 검사가 JSON Schema의 구현(jsonschema)과 무작위 입력 4,200개에서 같은 판정을 낸다.
- 이 문서의 표(연산의 이름, 입력, 부호, 한도)가 코드와 어긋나지 않는다.

변이 검사(`tools/mutants.py`)에 약속을 깨는 변이를 두었다(이름이 O로 시작하는 것).

저장소에서 돌리는 시험은 설치의 결함을 보지 못한다. 그래서 CI가 설치된 꾸러미로 저장소 밖에서 두 뼈대를 만들고 검사한다(`.github/workflows/tests.yml`). 이 단계가 넣은 날에 결함 하나를 잡았다. 설치하면 뼈대 옆에 바이트코드 파일이 생기는데 full 뼈대를 읽는 코드가 그것을 글로 읽으려다 죽었다. 설치해서 쓰는 사람에게는 `template: full`이 처음부터 되지 않았던 것이다.

설계로 남긴 것 셋은 3절의 "헷갈리기 쉬운 것"에 적었다. 구조의 지문이 속성의 값을 포함한다는 것, 사례의 `set`이 식으로 정한 속성도 바꾼다는 것, `pack_run`이 출력 사건만 낸다는 것이다.

### 고친 표면을 다시 맡겨 본 결과

같은 날, 고친 표면을 새 에이전트에게 다시 맡겼다. 사람이 아니다. 하나는 연산만으로 새 분야의 묶음을 만들고 실험까지 하게 했고, 하나는 고쳤다는 것들이 실제로 고쳐졌는지를 깨뜨려 보게 했다.

만드는 쪽의 결과.

- 과제는 주문을 집는 창고다. 복제된 작업자 넷까지, 자리마다 다른 종류(사람과 로봇), 있을 수도 없을 수도 있는 포장대, 문서의 기본값만 쓰는 사례, 선언하지 않은 결정 집합 파일로 돌리는 실험 아홉 번이다.
- 읽은 것은 이 문서, `ses ops`, `formats`, 두 뼈대의 파일뿐이다. 안내서, 스키마, 본보기 묶음, 소스는 읽지 않았다.
- 첫 초안이 첫 `pack_check`에서 통과했다. 기록까지 끝내는 데 연산 8번쯤, 실험까지 72번쯤이 들었다. 나머지 360번쯤은 일부러 틀려 보며 줄을 살핀 것이다. 모두 433번이다.
- 줄의 `kind`, `data`, `next`만으로 움직일 수 있었던 곳이 21가지, 한국어 글을 읽어야 했던 곳이 13가지였다.
- 첫 초안이 바로 통과한 데에는 운도 있었다고 보고했다. 자리로 적는 결정과 문서의 기본값의 모양을 뼈대가 보여 주지 않아 짐작으로 맞혔다.

## 9. 한계와 남은 것

| 번호 | 내용 |
|---|---|
| R1 | 평가가 없다. 에이전트가 이 연산들로 과제를 푸는지, 검사가 없을 때보다 나은지를 재지 않았다. 과제, 기준선, 기록의 형식을 정하는 것이 다음 일이다. 8절의 두 과제는 한 번씩 해 본 것이고 비교할 기준선이 없다 |
| R2 | 실제 에이전트 틀에 올려 보지 않았다. 도구 정의의 모양은 흔한 형식을 따랐으나 어떤 API에도 보내 보지 않았다 |
| R3 | 묶음의 코드를 가두지 않는다(1절). 표준 출력은 파이썬 수준에서만 가로챈다. 파이썬 밖의 코드가 직접 찍는 글은 `ses call`의 출력 앞쪽에 섞일 수 있다. 봉투는 마지막 줄이고 `--out`의 파일은 온전하다 |
| R4 | 시간 제한이 없다(1절). 부르는 쪽이 제한을 건다 |
| R5 | 줄의 `message`는 한국어다. 기계가 읽을 것은 `code`, `kind`, `data`다. `data`가 없거나 파일 이름뿐인 종류(contradiction, misfit, document_load, decisions_load, binding_load, declaration)는 어긋난 자리와 이름이 글 속에만 있다. 문서의 틀린 줄의 번호도 글에만 있다 |
| R6 | `formats`의 `shapes`는 사람이 적은 한 줄 설명이다. 스키마에서 만든 것이 아니어서 스키마와 어긋날 수 있다. 시험은 항목의 이름이 맞는지만 본다. 스키마는 저장소에 있고 설치된 꾸러미에는 들어 있지 않다 |
