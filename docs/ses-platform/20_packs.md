# 분야 묶음: 연구자가 자기 분야를 올리는 단위

작성일: 2026-11-23. 구현은 `ses_core/pack.py`, 명령은 `ses pack`, 시험은 `tests/test_pack.py`다. 처음 쓰는 사람은 `GUIDE.md`를 먼저 읽는다.

## 0. 무엇을 정했나

연구실의 연구자마다 분야, 모델 베이스, 목표가 다르다. 그래서 공통으로 두는 것은 내용이 아니라 계약과 검사다. 이 문서는 그 계약을 정한다.

- 공통인 것. 문서의 형식과 뜻(`theory.md`), 족 수준의 검사, 모델의 계약, 실행기 계약, 묶음의 선언과 적합성 검사.
- 연구자의 것. 분야의 구조(SES 문서), 분야의 어휘(프로파일), 행동(모델 베이스), 사례, 실험.

연구자에게 하는 약속은 이것이다. 묶음을 계약대로 쓰고 `ses pack check`를 통과시키면 다음을 얻는다.

1. 족 전체의 검사. 변이의 수, 죽은 선택지, 분해를 정할 수 없는 곳, 결합의 위반. 큰 족에서도 열거하지 않는다.
2. 결정 집합으로 변이를 고르고, 고른 변이를 조립하고 돌리는 명령.
3. 같은 모델 베이스가 참조 시뮬레이터, pyevsim, cevsim에서 같은 기록을 낸다는 확인.
4. 재현되는 기록. 사례의 기록의 지문을 적어 두고, 달라지면 검사가 알린다.

## 1. 모델의 계약 (15 문서의 Z1, 16 문서의 U5)

2026-11-23에 정했다. 플랫폼의 모델 계약은 공통 모델 기반이다. `ses_core.devs.Atomic`의 하위 클래스이고 병렬 DEVS의 다섯 함수를 채운다.

| 채우는 것 | 뜻 |
|---|---|
| PORTS | 포트 이름에서 (타입, in 또는 out)으로. 문서의 포트와 같아야 한다 |
| REQUIRED | 구동되어야 하는 입력 포트 |
| PARAMS | 매개변수 이름에서 (타입, 기본값)으로. 문서의 같은 이름의 속성이 값을 준다. 시간 전진으로 쓰는 값의 타입은 time이다 |
| init | 처음 상태 |
| ta | 다음 내부 사건까지 남은 시간. 바인딩이 적은 시간 단위의 음이 아닌 정수배이거나 INF |
| output | 내부 사건 직전의 출력. 포트 이름에서 값의 목록으로 |
| internal, external, confluent | 내부 전이, 외부 전이, 둘이 겹쳤을 때의 전이 |

이 계약을 지킨 모델은 세 실행기에서 같은 사건 기록을 낸다. 15 문서와 16 문서와 17 문서의 명제가 그것이고, 묶음의 검사가 사례마다 직접 확인한다.

특정 엔진의 모델(pyevsim이나 cevsim의 고유 모델)은 쓸 수 있으나 계약 밖이다. 선언의 `model_base.native`에 이름을 적는다. 그 모듈이 든 사례는 실행기 사이의 일치를 보지 않는다. 기존 자산을 쓰는 길로 열어 둔 것이고, 새 모델은 공통 모델 기반으로 쓴다.

모델이 지켜야 할 것 가운데 검사가 잡는 것.

- 난수는 씨앗을 매개변수로 받아 모델 안에서 만든다. 전역 난수를 쓰면 같은 사례를 두 번 돌린 기록이 달라진다(P6). 전역 난수에 씨앗을 주면 두 기록이 같아 이 검사에 걸리지 않으므로, 모델 베이스의 글에서 전역 난수의 쓰임을 찾아 경고한다(P2).
- 시각은 `self.now`만 쓴다. 벽시계를 쓰면 기록이 재현되지 않는다(P6). 글에서 찾아 경고한다(P2).
- 받은 값을 고치지 않는다. 낸 값도 낸 뒤에 고치지 않는다. 참조 시뮬레이터는 같은 객체를 넘기고 pyevsim은 복사해서 넘긴다. 고치면 엔진마다 기록이 달라진다. 검사는 다른 엔진이 없어도 이것을 본다. 낸 때의 값을 베껴 두고 받는 모델마다 다시 베껴서 넘기며 한 번 더 돌린다. 받은 값이 고쳐졌으면 어느 구성요소의 어느 함수인지를 알리고, 그렇게 돌린 기록이 그냥 돌린 기록과 다르면 그것을 알린다(P6). 기록의 값은 낸 때의 값이다.
- 선언한 포트로만 낸다(P2, P6). 모델의 PORTS와 문서의 그 정의의 포트는 같다(P5).

## 2. 묶음의 모양

묶음은 디렉터리 하나다. 그 안의 `pack.yaml`이 무엇이 어디 있는지를 적는다. 모든 경로는 묶음 안의 상대 경로다. 묶음은 디렉터리째 옮겨도 같은 결과를 내야 하므로 밖을 가리키지 못한다.

```yaml
pack: "1.0"
name: wsn                          # 묶음의 이름. 글자, 숫자, 밑줄
title: 한 줄 설명                   # 선택

document: wsn.ses.yaml             # 정준 SES 문서. 그 분야의 구조의 족
profile: wsn.profile.yaml          # 선택. 분야 프로파일
model_base:                        # 선택. 없으면 구조만 가진 묶음이다
  file: model_base.py
  library: LIBRARY                 # 모듈 라이브러리의 이름. 기본값 LIBRARY
  functions: FUNCTIONS             # 선택. 문서의 식이 부르는 함수들
  native: []                       # 선택. 공통 모델 기반이 아닌 모듈의 이름들
binding: binding.yaml              # 정의를 모듈에 잇는다. 시간 단위를 적는다
executors: [devs, pyevsim, cevsim] # 선택. 같은 기록을 내야 하는 실행기들. 기본은 셋 모두

cases:                             # 사례 하나가 변이 하나다
  - name: field_9
    decisions: cases/field_9.decisions.yaml   # 결정 집합. 없으면 문서만으로 변이가 정해져야 한다
    defaults: false                # 정해지지 않은 곳에 문서의 기본값을 쓰는가
    until: 30                      # 이 시각까지 돌린다. 없으면 계획까지만 만든다
    max_steps: 1000000             # 선택. 걸음 수의 한도. 끝나지 않는 모델을 멈춘다. 기본은 1,000,000
experiments:                       # 선택. 연구자의 스크립트. 검사는 파일이 있는지만 본다
  - experiment.py
```

`records.yaml`은 도구가 적는 파일이다. 사례를 참조 시뮬레이터로 돌린 기록의 요약(시각, 사건의 수, 지문)이 든다. `ses pack check --record`가 적고 손으로 고치지 않는다. 없어진 사례의 기록은 그때 지운다. 오류가 있는 사례의 기록은 적지 않는다.

모델 베이스가 없는 묶음도 묶음이다. 시뮬레이션이 아닌 분야(교육과정, 논문, 제안요청서의 프로파일이 `domains/`에 있다)는 문서와 프로파일과 사례의 결정만으로 올라온다. 선언에 `model_base`와 `binding`을 적지 않고 사례에 `until`을 적지 않는다.

돌리지 않는 사례(`until`이 없는 사례, 구조만 가진 묶음의 모든 사례)는 만든 구조의 지문을 적어 둔다. 구성요소, 포트, 결합, 속성의 값, 변수의 값이 그 지문에 든다. 문서나 결정을 고쳐 구조가 달라지면 P6이 알린다.

## 3. 적합성 검사

`ses pack check 디렉터리`가 본다. 오류가 하나도 없으면 통과다.

| 부호 | 보는 것 | 오류가 되는 것 |
|---|---|---|
| P0 | 선언 | `pack.yaml`이 없다. 모르는 항목. 없는 파일. 묶음 밖을 가리키는 경로와 묶음 밖으로 가는 링크. 같은 이름의 사례. 사례마다의 잘못은 모아서 한 번에 알린다 |
| P1 | 문서 | 적재되지 않는다. 문서 범위의 진단이 오류다. 적격인 변이가 하나도 없다 |
| P2 | 모델 베이스 | 실리지 않는다. 공통 모델 기반이 아닌 모듈(native에 적지 않은 것). 포트와 매개변수의 선언이 틀렸다. 기본값으로 만든 처음 상태에서 ta가 수가 아니거나 output이 계약을 어긴다 |
| P3 | 바인딩 | 읽히지 않는다. 모르는 항목이 있다. executor가 devs가 아니다. target이 문서의 이름과 다르다. 문서에 없는 정의나 라이브러리에 없는 모듈을 적었다. `params`가 모듈에 없는 매개변수나 문서에 없는 속성을 가리킨다 |
| P4 | 사례의 결정 | 결정이 문서에 맞지 않는다. 없는 변수나 범위 밖의 값을 적었다. 같은 속성의 `set`이나 같은 열쇠를 두 번 적었다. 자리로 적은 `set`의 속성이 그 자리의 구성요소에 없다. 결정이 모자라 변이가 하나로 정해지지 않는다. 만들 수 있는 변이가 없다 |
| P5 | 조립과 실행 가능성 | 사례의 변이가 조립되지 않는다(핵과 결합의 위반). 실행 가능하지 않다(14 문서의 B1에서 B5). 모델의 PORTS에만 있고 문서의 그 정의에 없는 포트가 있다. 복제본마다의 값(`each`)이 모자라 값을 받지 못한 자리가 있다 |
| P6 | 실행과 기록 | 참조 시뮬레이터에서 멈춘다(모델의 예외, 시간 단위에 어긋난 시간 전진, 걸음 수의 한도). 선언하지 않은 포트로 낸다. 받은 값을 고친다. 값을 베껴서 넘기면 기록이 달라진다. 두 번 돌린 기록이 다르다. 적어 둔 기록과 다르다. `records.yaml`을 읽을 수 없다 |
| P7 | 실행기 사이의 일치 | 다른 실행기의 규약을 어긴다. 다른 실행기에서 멈춘다. 기록이 참조 시뮬레이터와 다르다 |

경고와 알림.

- 족의 어떤 변이가 규칙을 어기는 것은 경고다(P1). 족을 좁혀 가는 중에는 흔한 일이다. 사례로 고른 변이는 P5가 따로 본다.
- 쓰이지 않은 결정은 경고다(P4). 이 변이에 없는 자리나 정의를 가리킨 것이다.
- 모델 베이스의 글에서 찾은 전역 난수와 벽시계는 경고다(P2). 경고가 있어도 사례는 돌리고 기록과 견준다.
- 모델에 전해지지 않는 속성은 경고다(P5). 묶인 정의의 속성 가운데 모듈의 매개변수가 아닌 것이다. 이름을 잘못 적으면 모델은 아무 말 없이 기본값으로 돈다.
- 기록이 없는 사례는 경고다(P6). 기록에 없는 사례의 기록이 남아 있는 것도 경고다.
- 이 컴퓨터에 없는 실행기는 건너뛰고 알림으로 적는다(P7). pyevsim은 설치되어 있어야 하고, cevsim은 소스의 자리(환경 변수 CEVSIM_HOME)와 C++ 컴파일러가 있어야 한다.

검사가 보지 않는 것.

- 구조가 그 분야에 맞는지. 문서가 형식에 맞고 조립된다는 것만 본다.
- 모델의 행동이 옳은지. 계약을 지키고 재현된다는 것만 본다.
- 모델의 모든 상태. 계약의 검사는 기본값으로 만든 처음 상태와, 사례를 돌린 기록에 대한 것이다.
- 실험 스크립트. 파일이 있는지만 본다.

## 4. 명령

| 명령 | 하는 일 |
|---|---|
| `ses pack new 디렉터리 [--name 이름]` | 돌아가는 가장 작은 묶음을 만든다. 만든 것은 그대로 검사를 통과한다 |
| `ses pack check 디렉터리 [--record] [--executors 목록]` | 적합성 검사. `--record`는 사례의 기록을 적는다 |
| `ses pack show 디렉터리` | 묶음에 든 것과, 그 안에서 쓰는 명령을 보인다 |
| `ses pack run 디렉터리 사례 [--until 시각] [--log N]` | 사례 하나를 참조 시뮬레이터로 돌려 출력 사건을 보인다 |

문서 하나를 다루는 명령(`ses check`, `choices`, `variants`, `build`, `plan`, `run`)은 그대로다. 묶음 디렉터리 안에서 쓴다. `ses pack show`가 경로를 채운 명령을 보여 준다.

## 5. 저장소의 묶음

| 묶음 | 내용 | 검사 결과 |
|---|---|---|
| `packs/wsn` | 문헌 사례: 큰 무선 센서 네트워크(Nam, Kim (2021)). 사례는 센서 9개와 센서 1,000개 | 변이 9,000개 모두 적격. 센서 9개의 사례는 세 실행기의 기록이 같다(사건 103개). 센서 1,000개는 계획까지 만든다(원자 구성요소 1,003개) |
| `packs/feedback_control` | 문헌 사례: 피드포워드를 켜고 끄는 피드백 제어(Folkerts et al. (2019)). 사례 둘과 실험 제어 | 변이 2개 모두 적격. 두 사례 모두 세 실행기의 기록이 같다(사건 4,810개와 7,696개) |

둘은 앞서 `docs/ses-platform/examples`와 `examples`에 흩어져 있던 것을 옮긴 것이다. 옮기면서 핵은 고치지 않았다. 처리 시스템과 센서 노드의 예시는 플랫폼의 시험이 쓰는 자료라 그 자리에 두었다.

## 6. 이 일을 하다가 고친 것

- 적재기가 모르는 항목을 거부한다. 뼈대를 쓰다가 속성의 값을 `default`가 아니라 `value`로 적었는데 아무 경고 없이 값이 없는 속성이 되었다. 스키마는 그것을 막지만 스키마 검증은 따로 하는 일이라 빠진다. 이제 적재기가 직접 보고, 흔한 잘못에는 뜻했을 항목을 알려 준다. 적재기가 아는 항목의 표는 스키마와 같고 시험이 둘을 견준다.
- `module_of`가 공통 모델 기반이 아닌 클래스를 받으면 까닭을 적어 거부한다.

### 처음 온 연구자의 역할을 맡긴 검증에서 나와 고친 것 (2026-11-23)

에이전트 여섯에게 안내서와 설치된 도구만 주고 각자 다른 분야의 묶음을 만들게 했다. 저장소의 코드는 읽지 못하게 했다. 그 보고를 다른 에이전트가 다시 확인했다. 사람이 아니다. 나온 것 가운데 도구에서 고친 것은 다음과 같다. 안내서에서 고친 것은 `GUIDE.md`에 반영했다.

| 나온 것 | 고친 것 |
|---|---|
| 선택지 표는 남은 변이가 1개라고 하는데 조립은 결정이 모자라다고 했다. 대안을 고르면 선택 규칙이 변수 값을 정하는 경우다 | 결정 집합이 족을 변이 하나로 줄이면 규칙과 제약이 정한 나머지를 찾아 채운다(`direct.completed`). 명령과 묶음의 검사가 이것을 쓴다 |
| 받은 값을 고치는 모델이 다른 엔진 없이는 통과했다. 그리고 받은 쪽이 고치면 이미 적힌 사건의 값까지 바뀌었다 | 기록에 낸 때의 값을 베껴 적는다. 값을 베껴서 넘기는 방식으로 한 번 더 돌려 견준다(P6) |
| 모델이 예외를 내면 예외의 이름만 나왔다. 어느 모델의 어느 줄인지 알 수 없었다 | 구성요소, 함수, 시각, 파일의 줄을 적는다(`devs.ModelError`) |
| 사례를 지우거나 이름을 바꾸면 옛 기록에 대한 경고가 남고 지울 방법이 없었다 | `--record`가 없어진 사례의 기록을 지운다 |
| 속성의 이름이 모델의 매개변수와 다르면 아무 말 없이 기본값으로 돌았다 | 경고로 알린다(P5) |
| 모델의 PORTS에만 있는 포트는 그 포트로 낼 때에야 알려졌다 | 돌리기 전에 알린다(P5) |
| 문서의 열쇠를 잘못 적거나 YAML 문법이 틀리면 명령이 파이썬의 역추적을 냈다 | 적재기가 모양이 틀린 문서를 자기 오류로만 알린다. 무작위로 망가뜨린 문서 2,400개로 시험한다 |
| 복제본이 많을 때 같은 오류가 복제본마다 나왔다. 묶을 정의의 이름도 없었다 | 여덟 줄까지만 내고 나머지는 수로 알린다. 묶을 정의의 이름을 적는다 |
| 결정의 경로를 뿌리 없이 적으면 쓰이지 않은 결정이라고만 했다 | 경로는 뿌리에서 시작한다고 알린다 |
| 걸음 수의 한도 100,000에 걸리면 한도도 올리는 법도 알 수 없었다 | 한도를 1,000,000으로 올리고, 줄에 한도와 시각을 적고, 사례마다 `max_steps`로 바꾸게 했다 |
| 선택지가 1,000개이면 표가 그 수를 모두 늘어놓았다 | 이어진 정수는 처음과 끝과 개수만 적는다 |
| 기본값만 시간 단위에 어긋나고 문서가 다른 값을 줄 때도 오류라고 했다 | 실제로 쓰이는 값만 본다(P5, P6) |
| 어떤 대안만 가진 포트로 가는 결합을 적재기가 거부했다. 대안마다 포트와 결합이 다른 구조를 바로 적을 수 없었다 | 적재기를 뜻에 맞췄다. 어느 변이에도 없는 포트만 미리 거부하고 나머지는 변이마다의 검사(C1)가 본다(`theory.md`의 정의 13의 덧붙임) |
| 구조만 가진 묶음의 사례가 "만들지 못했다"고 나왔고 적어 둘 기록이 없었다 | 구성요소의 수를 보이고, 만든 구조의 지문을 기록으로 적어 견준다 |
| 결정 집합의 열쇠를 잘못 적으면 조용히 넘어가서 먼 곳에서 "결정이 모자라다"고 나왔다. 모양이 틀리면 파이썬의 예외 글이 나왔다 | 모르는 항목을 거부하고 뜻했을 항목을 알린다. 아는 항목의 표는 스키마와 같고 시험이 견준다 |
| 프로파일을 따르는 문서를 명령으로 조립할 수 없었다. 조립한 변이의 속성 값을 볼 길이 없었다 | `ses build`에 `--profile`과 `--attributes`를 더했다 |
| 프로파일의 규칙을 어긴 값만 나오고 한도가 나오지 않았다 | 규칙의 한도를 함께 적는다 |
| 모델 베이스를 같은 초 안에 같은 크기로 고치면 검사가 옛 코드를 돌렸다. 파이썬의 바이트코드 캐시가 시각(초 단위)과 크기로 낡았는지를 가리기 때문이다. 검증자가 찾았고 뼈대를 만든 직후의 편집에서 열 번에 열 번 일어났다 | 모델 베이스 파일을 캐시를 거치지 않고 원본에서 읽어 돌린다. 싣는 동안 캐시를 쓰지도 않는다 |
| 전역 난수에 씨앗을 주고 쓰는 모델은 두 번 돌린 기록이 같아 재현의 검사를 통과했다 | 모델 베이스의 글에서 전역 난수와 벽시계의 쓰임을 찾아 경고한다(P2). 글만 보는 것이라 놓칠 수 있다 |
| 사례의 선언에서 열쇠를 잘못 적으면 무엇이 틀렸는지 알리지 않았다 | 모르는 항목의 이름을 적는다 |

고치지 않고 한계로 둔 것은 7절의 K7에서 K12다.

### 고친 것이 실제로 고쳐졌는지 다시 본 결과 (2026-11-24)

같은 검증자 여섯에게 고친 도구를 주고, 첫 판에서 나온 것을 하나씩 다시 해 보게 했다. 항목은 107건이다.

| 결과 | 건수 | 뜻 |
|---|---|---|
| 다시 나지 않는다 | 90 | 고쳐졌다 |
| 여전히 난다 | 13 | 아래의 표 |
| 설계다 | 4 | 문서에 적어 둔 동작이다. K9, K11, 명령을 치는 디렉터리 |

여전히 난다고 한 13건은 서로 겹치는 것을 묶으면 여덟 가지다. 여덟을 모두 고쳤다.

| 여전히 나던 것 | 고친 것 |
|---|---|
| 모델 베이스의 경고(전역 난수, 벽시계) 하나가 모든 사례를 건너뛰게 하고 검사가 통과했다. 검증자 넷이 따로 찾았다. 앞의 판에서 글을 보는 검사를 넣으면서 내가 만든 결함이다 | 오류만 사례를 건너뛰게 한다. 경고가 있어도 돌리고 기록과 견준다. 시험을 더했다 |
| 모델의 `init`에서 난 예외는 자리 없이 예외의 이름만 나왔고, `ses run`은 역추적을 냈다 | 모델을 만드는 것도 자리를 붙여 부른다. 구성요소, 함수(init), 줄이 나온다 |
| 안내서 9절의 본보기 줄의 줄 번호가 실제와 달랐다(72와 76). 시험이 줄 번호를 지우고 견주었기 때문에 놓쳤다 | 안내서를 고치고, 시험이 줄 번호까지 견준다 |
| "결정이 모자라다"의 남은 선택지가 제약이 이미 지운 것까지 늘어놓았다. `ses choices`와 답이 달랐다 | 변이가 남는 선택지만 적는다 |
| 족의 위반(C1, R2 같은 것)의 줄이 어느 변이에서인지를 적지 않았다 | 줄의 끝에 해당하는 변이의 수와, 그 위반이 나는 선택을 적는다. 예: `(변이 4개 가운데 1개. Detector/presence=Installed, Controller/kind=FixedTime 일 때)` |
| 선언의 사례 여럿에 같은 잘못이 있어도 첫째만 알렸다 | 사례마다의 잘못을 모아 한 번에 알린다 |

### 고친 안내서로 다시 해 본 결과 (2026-11-24)

새 에이전트 둘에게 고친 안내서를 주고 첫 판에서 가장 막혔던 두 분야(교차로, 응급실)를 다시 만들게 했다. 둘 다 끝냈다. 첫 판에서 도구가 막았던 구조(대안마다 포트가 다른 제어기)는 이번에는 문서의 형식 그대로 적혔다. 플랫폼의 코드를 읽거나 고칠 필요는 없었다. 막힌 곳은 19건이고 모두 마찰이나 사소함으로 분류되었다. 거기서 나와 고친 것이다.

| 나온 것 | 고친 것 |
|---|---|
| 정의로 적은 결정(at)과 자리로 적은 결정(path)이 둘 다 적용된다는 것을 몰랐다. 안내서의 한 문장을 따르면 변이가 남지 않았고, 줄은 있지도 않은 선택 규칙을 탓했다 | 줄이 어긋난 결정들과 각각 무엇을 남기는지를 적는다. `ses choices`도 어긋난 곳을 적는다. 안내서의 걸음 6에 그 경우를 따라 해 보는 대목을 두었다 |
| 변이가 하나로 정해졌는데 선택지 표의 줄이 "열림"이었다. 복제본마다 다른 대안을 고른 경우다 | 그 줄을 "자리마다 정해짐"으로 적는다(연산에서는 decided_per_place) |
| 자리로 적은 `set`의 속성 이름이 틀리면 경고만 나오고 모델은 기본값으로 돌았다. 자리가 파이썬의 튜플로 찍혔다 | 그 자리의 구성요소가 있으면 오류(P4)이고 있는 속성을 적는다. 자리는 빗금으로 이어 적는다 |
| 대안이 가진 속성을 바탕 정의의 이름으로 적으면 속성이 없다고만 했다 | 어느 대안이 그 속성을 가지는지를 적는다 |
| 없는 선택지를 적으면 무엇이 있는지를 알리지 않았다. 개수의 결정이 변수와 어긋나면 "남는 분해가 없다"고만 했다 | 있는 선택지를 적는다. 개수가 어긋나면 문서가 주는 개수와 결정이 남기는 개수를 적는다 |
| 값을 바꿔 가며 여러 번 돌릴 길이 문서에 없었다. 명령의 글 출력을 읽어 썼다 | `pack.run`이 사례 위에 고칠 것(change)을 받는다. 연산 `pack_run`은 선언에 없는 결정 집합 파일을 받는다. 안내서 11절에 돌아가는 본보기를 두었다 |
| 제약의 적는 법이 스키마의 설명에만 있었다 | 안내서 7절에 돌아가는 본보기를 두었다. 시험이 그 글 그대로 돌린다 |
| 변수의 타입, 기본값, 자기 포트의 결합, PARAMS의 상속, 연속인 시간, 대안의 바인딩이 안내서에 없었다 | 안내서에 적었다 |
| `ses choices`가 프로파일의 규칙을 보지 않는다는 것을 명령이 말하지 않았다 | 문서가 프로파일을 가리키면 한 줄로 알린다 |

고치지 않은 것. 자리마다 다른 속성 값을 문서에 적는 길은 없다. 사례의 `set`으로만 적는다. 식으로 정해지는 속성을 `set`이 바꿔도 경고하지 않는다(K13).

연산을 에이전트에게 맡겨 본 두 차례의 검토에서 나와 묶음의 검사에서 고친 것은 `21_agent_operations.md`의 8절에 있다. 바인딩의 `params`, 묶음 밖으로 가는 링크, 깨진 기록 파일, 프로세스를 끝내려는 모델, 걸음 수의 한도에서의 자료가 거기에 든다.

## 7. 한계와 남은 것

| 번호 | 내용 |
|---|---|
| K1 | 써 본 사람이 없다. 연구자의 역할을 맡긴 에이전트 여덟이 안내서를 따라 묶음을 만들었고 거기서 나온 것을 고쳤다(6절). 에이전트는 사람이 아니다. 같은 모델이라 같은 것을 놓칠 수 있고, 낯선 형식을 읽어 내는 힘이 처음 온 대학원생과 다르다. 둘째 판의 둘은 스키마 파일까지 읽어 막힌 곳을 풀었다. 사람은 거기서 멈출 수 있다. 사람 둘의 시험 운영이 남았다 |
| K2 | 뜻에 대한 결정 셋이 열려 있다(ROADMAP의 정해야 할 것 1, 4, 5). 정해지면 우선순위를 쓴 문서와 자리를 가리킨 분해의 결정을 쓴 결정 집합의 뜻이 달라진다. 묶음의 선언에 적는 판(`pack: "1.0"`)은 그 뒤에 올린다 |
| K3 | 묶음의 모델 베이스는 파이썬 파일 하나다. 묶음 안의 다른 파일은 그 파일을 싣는 동안에만 불러 쓸 수 있다. 모델의 함수 안에서 뒤늦게 불러오면 찾지 못한다. 두 묶음이 같은 이름의 보조 파일을 가져도 섞이지 않고, 고친 파일은 다시 실을 때 읽힌다(2026-11-23에 고쳤다) |
| K4 | 실행기 사이의 일치는 사례가 지나간 길에 대해서만 확인된다. 사례가 건드리지 않은 전이는 보지 않는다 |
| K5 | 에이전트가 부르는 연산은 21 문서에 있다. 묶음에 대한 판정과 형식의 안내, 일곱 연산을 JSON으로 내놓는다 |
| K6 | 평가의 틀(과제, 기준선, 기록의 형식)은 아직 없다 |
| K7 | 조건에 따라 달라지는 결합이 없다. 있을 수도 없을 수도 있는 부분의 앞뒤를 잇는 결합은 분해를 둘로 적어야 하고, 그런 부분이 여럿이면 분해의 수가 곱으로 는다. 문서의 형식을 넓히는 일이라 뜻의 결정이 필요하다 |
| K8 | 복제된 부분 가운데 하나에만 값을 보내는 결합이 없다. 모든 복제본이 값을 받고 모델이 자기 몫을 고른다 |
| K9 | 포트 타입의 fields를 모델이 내는 값과 견주지 않는다. 서로 다른 연구자의 모델을 잇는 계약이 되려면 견줘야 한다 |
| K10 | 속성의 값은 스칼라 하나다. 목록을 값으로 가질 수 없어 시간에 따른 값의 열은 글로 적어 모델이 푼다 |
| K11 | extends의 뜻이 적재기와 족의 검사에서 다르다(ROADMAP의 정해야 할 것 5). 대안의 정의를 부분으로 직접 놓으면 바탕의 포트를 물려받지 않는다. 도구는 경고한다 |
| K12 | `ses choices`와 연산 `pack_choices`는 프로파일의 규칙을 보지 않는다. 선택의 핵만 센다. 프로파일의 규칙을 어기는 변이도 남은 변이로 센다 |
| K13 | 사례의 `set`이 구조와 맞는지는 보지 않는다. 문서가 식으로 정한 속성(복제본의 번호, 변수의 값)을 `set`이 바꾸면 구조와 어긋난 값이 모델에 간다. 결정 집합의 형식이 `set`을 그렇게 정했다. 막으려면 형식을 바꿔야 한다 |
| K14 | 복제본마다의 값(`each`)이 복제본의 수보다 적을 때의 뜻은 그대로다. 남는 복제본은 `default`를 쓰고 그것도 없으면 값이 없다. 족의 검사는 이것을 알리지 않는다. 사례로 정해진 변이에 값이 없는 자리가 있을 때만 오류(P5)다 |
| K15 | 실험(값을 바꿔 가며 돌리기)은 파이썬의 `pack.run`과 연산 `pack_run`까지다. 반복의 수, 씨앗, 결과의 표를 선언으로 적는 형식은 없다. 실험 틀(experimental frame)은 문서의 형식에 자리만 있다 |
