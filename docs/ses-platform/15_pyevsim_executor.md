# pyevsim 실행기

작성일: 2026-11-14 (2026-11-15에 시각을 다루는 부분을 시간 단위의 계약에 맞춰 고쳤다. 17 문서)

14 문서의 결정 D1을 실행한 기록이다. pyevsim 실행기를 DEVS 참조 실행기, 하드웨어 실행기와 같은 계약으로 만들었다. 합격 기준은 14 문서가 정한 둘이다. 충실성(엔진에서 다시 읽은 구조가 계획과 같다)과, 참조 시뮬레이터와 사건 기록이 같다는 것이다.

구현은 ses_core/pyevsim_executor.py, 검증은 tests/test_pyevsim.py다. pyevsim은 PyPI의 1.1.7(2026-11-14 현재 최신)을 설치해서 확인했다. 깃허브의 최신본은 확인하지 않았다. pyevsim이 없으면 이 모듈을 가져올 수 없고 시험은 건너뛴다.

## 0. 판정

| 기준 | 결과 |
|---|---|
| 계약 | 같다. Executor의 conventions, build, observe를 구현했고 attach, executable, plan, realize, exec_core, analyze가 고치지 않은 채로 동작한다 |
| 충실성 | 통과. 무작위 구조 500개, 무작위 문서의 계획 346개, 두 예시의 변이 86개(공통 모델베이스 71, 고유 모델베이스 15)에서 엔진의 모델, 포트, 연결이 계획의 평탄화와 같다. 연결은 길의 수까지 같다. 실행한 뒤에도 같다 |
| 사건 기록, 공통 모델베이스 | 통과. 참조 시뮬레이터와 같은 모델베이스를 pyevsim에 올리면 출력 사건의 열이 순서까지 같고 모델의 마지막 상태도 같다. 무작위 구조 500개(사건 8,325개), 무작위 문서의 계획 346개(사건 820개), 처리 시스템 15개 변이, 센서 노드 56개 변이 |
| 사건 기록, pyevsim 고유 모델 | 보장되지 않는다. pyevsim의 실행 의미가 병렬 DEVS와 다르기 때문이다(2절). 처리 시스템을 pyevsim 모델로 다시 쓴 모델베이스에서는 15개 변이 모두 사건의 모음과 집계가 참조와 같았고, 순서까지 같은 것은 3개였다 |

꼭 알아야 할 것 셋.

- 사건 기록을 같게 만든 것은 엔진이 아니라 어댑터다. pyevsim 1.1.7의 엔진은 같은 시각의 사건을 하나씩 처리하고 받는 쪽의 시계를 다시 잡는다. 병렬 DEVS의 의미(임박한 모델이 모두 출력한 뒤에 전이한다)는 어댑터가 엔진의 호출 순서 위에서 지킨다. pyevsim 고유 모델로 쓴 모델베이스의 행위는 모델을 쓴 사람이 pyevsim의 의미에 맞춰 책임져야 한다.
- pyevsim은 시간 격자 위의 사건만 처리한다. 격자 밖의 시각을 요청한 모델이 하나 있으면 오류 없이 시뮬레이션 전체가 멈춘다. 실행기는 이것을 오류로 바꿔 알린다.
- 이 작업 중에 내 참조 구현의 결함을 둘 찾아 고쳤다. 문서에 같은 결합을 두 번 적은 경우와 모델이 값이 없는 출력을 낸 경우에 참조 시뮬레이터의 계층 실행과 평탄 실행이 서로 달랐다. 14 문서의 "두 실행의 사건 기록이 같다"는 확인이 이 두 경우를 덮지 못하고 있었다(6절).

## 1. 계약과 쓰는 법

```python
from ses_core import executor as X
from ses_core.pyevsim_executor import PyevsimExecutor
from examples import processing_pyevsim

px = PyevsimExecutor()                                               # 시간 단위는 바인딩의 time_unit에서 온다
binding = X.load_binding("docs/ses-platform/examples/processing_system.binding.pyevsim.yaml")
L, ext = X.attach(L0, px, binding, processing_pyevsim.LIBRARY)     # L0는 구조와 속성이 얹힌 SES
sim = X.realize(L, ext, px, V)                                     # V는 실행 가능한 변이
log = sim.run(20.0)
sim.close()
```

| 계약의 자리 | pyevsim 실행기가 하는 일 |
|---|---|
| 규약 (conventions) | P1 하나. 원자의 포트 이름이 pyevsim 모델 객체의 속성 이름과 겹치면 안 되고, 뿌리의 포트 이름이 엔진 객체의 속성 이름과 겹치면 안 된다. 2절의 E6 때문이다 |
| 조립 (build) | 엔진을 하나 만들어 이름으로 등록한다. 계획의 원자마다 모델을 하나 만들어 올린다. 원자의 이름은 경로를 이은 것이다(ServerPool/server_0). 계획의 평탄화를 연결 표에 등록하되 길의 수만큼 등록한다. 뿌리의 포트는 엔진의 입력 포트와 출력 포트가 된다 |
| 관찰 (observe) | 엔진에 등록된 모델과 연결 표에서 한 층짜리 구조를 다시 읽는다. 엔진이 스스로 두는 기본 수신 모델(dc)과 그리로 가는 연결은 세지 않는다. 등록된 횟수는 Simulation.connections가 structure.flatten과 같은 꼴로 센다 |

산출물은 Simulation이다.

| 이름 | 뜻 |
|---|---|
| engine, name | pyevsim의 엔진과 그 이름. SystemSimulator.get_engine(name)으로도 찾을 수 있다 |
| models | 경로에서 pyevsim 모델 객체로 |
| run(until) | 시각 until까지 돌리고 출력 사건의 기록을 돌려준다. 그 시각의 사건도 처리한다. 이어서 다시 부를 수 있다 |
| log | 출력 사건의 열. 원소는 (시각, 원자의 경로, 포트, 값)이며 참조 시뮬레이터의 기록과 같은 꼴이다 |
| leaves() | 경로에서 모델로. 공통 모델 기반이면 감싸기 전의 모델을 준다 |
| connections() | 엔진에 등록된 연결과 그 횟수 |
| check() | 요청 시각이 지나가 버린 모델이 있으면 OffGrid를 낸다. run이 부른다 |
| close() | 엔진을 등록부에서 지운다 |

생성자의 인자는 time_unit(시간 단위. 주지 않으면 계획에 실려 온 바인딩의 것을 쓰고, 어디에도 없으면 1이다. 엔진의 시간 간격이 된다), engine_name(주지 않으면 조립할 때마다 새 이름), record(pyevsim 고유 모델의 출력도 log에 적는가. 기본은 적는다), max_rounds(한 시각에 돌 수 있는 차례의 상한. 기본 100,000)이다.

모듈의 본체는 둘 가운데 하나다.

| 본체 | 조립 | 행위의 의미 |
|---|---|---|
| pyevsim 모델 | BehaviorModelExecutor를 만드는 호출 가능 객체. pyevsim의 관례대로 body(0, Infinite, 이름, 엔진 이름, 매개변수들)로 부른다. 만들어진 모델이 준 이름을 가졌는지, 계획의 포트를 그 방향으로 가졌는지, 생성 시각이 0이고 소멸 시각이 없는지, 포트 이름이 그 클래스의 속성을 가리지 않는지 확인한다 | pyevsim의 것. 엔진이 그 모델을 그대로 돌린다 |
| 공통 모델 기반 | devs.Atomic의 하위 클래스. 어댑터(Adapted)가 감싸서 엔진에 올린다. 참조 실행기에 쓰던 모델베이스를 고치지 않고 쓴다 | 병렬 DEVS의 것. 참조 시뮬레이터와 같다(3절) |

바인딩 파일의 형식은 다른 실행기와 같다(schema/binding.schema.json). 처리 시스템의 pyevsim 바인딩(examples/processing_system.binding.pyevsim.yaml)은 04 문서 때의 초안이었던 것을 이 형식으로 바꿨다. 모듈의 이름과 인터페이스가 같으므로 같은 바인딩에 pyevsim 모델베이스(examples/processing_pyevsim.py)를 붙여도 되고 공통 모델베이스(examples/processing_mb.py)를 붙여도 된다.

실행기를 붙인 뒤의 이론은 14 문서 그대로다. 실행 가능성은 변이만으로 정해지고, 실행 가능 핵은 가지치기이며, 다른 실행기와 교환한다. 센서 노드에서 pyevsim으로 실행 가능한 변이는 참조 실행기와 같은 56개이고, 하드웨어로도 만들 수 있는 것은 어느 순서로 핵을 구해도 8개다. 그 여덟 변이 모두에서 엔진의 연결과 배선표의 연결이 같다(따름정리 18.1). 규약 P1의 위반은 13 문서의 진단으로 나온다. 포트 이름이 output인 정의에 pyevsim을 붙이면 그 정의의 주소에 P1이 달리고, 같은 문서가 참조 실행기로는 실행 가능하다.

## 2. pyevsim 1.1.7에서 확인한 엔진의 성질

설치된 소스(system_executor.py, behavior_model_executor.py, structural_model.py, definition.py)를 읽고, 성질마다 작은 실행으로 확인했다. 확인은 tests/test_pyevsim.py의 test_fact로 시작하는 시험에 남겼다. 그 시험들은 1.1.7이 아닌 판에서는 건너뛴다. 다른 판에서는 다시 확인해야 한다.

| 번호 | 확인한 성질 | 실행기에 준 영향 |
|---|---|---|
| E1 | 엔진에는 계층이 없다. 모델의 목록과 연결 표(port_map)가 전부이고, StructuralModel은 엔진이 시작할 때 풀어서 연결 표에 넣는다. StructuralModel의 외부 출력 결합은 (안쪽 모델, 포트)마다 하나만 남는다. 안쪽 출력 하나를 바깥 출력 둘에 이으면 먼저 것이 사라진다 | StructuralModel을 쓰지 않고 계획의 평탄화를 직접 등록한다 |
| E2 | 같은 연결을 두 번 등록하면 메시지가 두 번 전달된다 | 길의 수만큼 등록한다. 14 문서의 평탄화가 엔진에서 그대로 보존된다 |
| E3 | 시각은 time_step씩 나아가고, 요청 시각이 현재 시각과 같은(상대 오차 1e-9) 모델만 처리된다. 격자 밖의 시각을 요청한 모델이 있으면 그 시각이 지난 뒤로는 오류 없이 어떤 모델도 처리되지 않는다. 시각만 끝까지 간다. 등록하지 않은 상태로 간 모델도 같다(시간 전진이 -1이 된다) | 어댑터는 시간 전진을 눈금으로 바꾸고 격자 밖이면 OffGrid를 낸다. run은 실행 뒤에 지나간 요청 시각이 남아 있으면 OffGrid를 낸다 |
| E4 | 같은 시각의 모델은 (요청 시각, 객체 번호)의 순서로 하나씩 처리된다. 출력은 받는 모델의 ext_trans로 바로 넘어가고, 엔진은 받은 모델의 요청 시각을 현재 시각에 시간 전진을 더한 값으로 다시 잡는다. 그래서 같은 시각에 임박해 있던 받는 쪽은 자기 차례를 잃고, 주기가 3인 모델이 매 시각 입력을 받으면 한 번도 출력하지 못한다. ext_trans에서 cancel_rescheduling을 부르면 앞선 요청 시각을 지킨다. 그때에도 입력이 출력보다 먼저 반영된다 | 병렬 DEVS와 다른 의미다. 어댑터가 3절의 규약으로 메운다. 고유 모델은 이 의미에 맞춰 써야 한다(4.2절) |
| E5 | 자기 자신에게 이은 모델은 출력할 때마다 다음 사건이 시간 전진의 두 배 뒤로 잡힌다. 주기 2가 4가 된다 | 어댑터에서는 일어나지 않는다. 고유 모델에서는 그대로다 |
| E6 | 포트를 등록하면 같은 이름의 속성이 객체에 만들어진다(setattr). 포트 이름이 output이면 모델의 출력 함수가 문자열로 바뀐다 | 규약 P1. 조립할 때도 막는다 |
| E7 | simulate(T)는 T보다 앞선 시각만 처리한다 | run은 마지막 눈금의 반 칸 뒤까지 돌려 끝 시각의 사건을 처리한다. 참조 시뮬레이터와 같게 하기 위해서다 |
| E8 | 엔진의 경계로 나간 출력(get_generated_event)에는 시각과 값만 있고 포트 이름이 없다 | 뿌리의 출력 포트가 둘 이상이면 어느 포트로 나왔는지 엔진에서는 알 수 없다. 원자의 출력은 log에 포트와 함께 남는다 |
| E9 | 모든 모델이 쉬고 있으면 예약된 외부 입력이 남아 있어도 simulate가 끝난다 | run이 전달되지 않은 외부 입력을 오류로 알린다 |
| E10 | 받는 곳 없는 출력이 나오면 엔진이 실행 중에 기본 수신 모델(dc)로 가는 연결을 연결 표에 더한다 | 관찰은 dc와 그리로 가는 연결을 세지 않는다 |
| E11 | 생성 시각의 기본값은 무한대다. 생성 시각을 주지 않은 모델은 시작되지 않는다 | 본체를 (0, Infinite, 이름, 엔진 이름)으로 부르고, 생성 시각이 0이 아닌 모델은 거부한다 |
| E12 | 출력을 목록으로 내면 메시지가 깊은 복사되고, 하나로 내면 그대로 전달된다 | 어댑터는 늘 목록으로 낸다. 받는 쪽은 값의 사본을 받는다 |

E2, E4, E7, E10, E12는 설계의 선택으로 읽힌다. E1의 덮어쓰기, E3의 조용한 정지, E5, E6, E8, E9는 의도한 동작인지 확인이 필요하다. 이 구분은 내 판단이다. 어느 쪽이든 실행기는 1.1.7의 동작에 맞춰 만들었고, 엔진이 바뀌면 test_fact 시험이 먼저 알려 준다.

## 3. 공통 모델 기반을 올리는 어댑터

공통 모델 기반의 모델은 다섯 함수(ta, output, internal, external, confluent)로 되어 있다. 어댑터는 엔진이 부르는 세 함수(output, ext_trans, int_trans)와 요청 시각을 다음과 같이 채운다.

| 엔진이 부르는 것 | 어댑터가 하는 일 |
|---|---|
| output | 전이하기 전의 상태에서 출력을 계산해 포트의 이름 순서로 내고 log에 적는다. 값이 없는 출력은 보내지 않는다 |
| ext_trans | 받은 값을 출처와 함께 묶음에 모아 두기만 한다 |
| int_trans | 그 시각에 임박한 모델 가운데 아직 출력하지 않은 것이 없으면, 모아 둔 전이를 모두 한다. 임박했고 받은 것이 있으면 겹친 전이, 임박했을 뿐이면 내부 전이, 받기만 했으면 외부 전이(흐른 시간과 함께)다. 묶음은 (출처의 경로, 포트, 순번)의 순서로 늘어놓는다 |
| get_req_time | 낼 차례이면 엔진의 시계 값 그대로, 전이를 기다리거나 쉬고 있으면 무한대, 그 밖에는 다음 사건의 눈금에 시간 간격을 곱한 값 |

시각은 눈금의 정수로 센다. 같은 시각에 임박한 모델들이 엔진에 똑같은 요청 시각을 내놓아야 엔진이 그것들을 객체 번호의 순서로 꺼내기 때문이다. 모델은 경로의 순서로 만들므로 객체 번호의 순서가 참조 시뮬레이터의 처리 순서와 같다. 엔진에 더하는 모델이나 연결은 없다.

명제 (어댑터의 정확성). 계획의 원자가 모두 공통 모델 기반이고 모든 시간 전진이 시간 단위의 정수배라고 하자. pyevsim 실행기가 만든 엔진을 시각 T까지 돌린 사건 기록은 참조 시뮬레이터가 같은 계획의 모델을 T까지 돌린 사건 기록과 같다.

논증. 참조 시뮬레이터의 한 차례(같은 시각에 임박한 모델이 출력하고, 나르고, 전이하는 것)에 대한 귀납이다. 차례가 시작될 때 모든 모델의 상태, 마지막 전이 시각, 다음 사건 시각이 두 쪽에서 같다고 하자.
- 꺼내는 순서. 임박한 모델의 요청 시각은 엔진의 시계와 같은 값이고 나머지는 그보다 크거나 무한대다. 엔진은 임박한 모델을 번호 순서로 하나씩 꺼낸다. 번호 순서는 경로 순서다.
- 출력. 꺼낸 모델의 output은 그 차례의 어떤 전이보다 먼저 불린다. 전이는 마지막 임박 모델의 int_trans에서야 일어나기 때문이다. 그러므로 출력은 차례가 시작될 때의 상태에서 계산되고 기록의 순서는 참조와 같다.
- 나르기. 엔진은 메시지를 연결 표대로 전달한다. 연결 표는 평탄화된 연결을 길의 수만큼 가진다(충실성). 참조의 평탄 실행이 같은 표로 나르고, 평탄 실행과 계층 실행은 같다(14 문서의 명제). 받은 값을 출처의 순서로 늘어놓으므로 묶음도 같다.
- 전이. 임박했는가와 받았는가의 네 경우가 참조와 같은 함수를 같은 인자로 부른다.
- 다음 차례. 전이 뒤의 시간 전진이 0인 모델은 같은 눈금에 다시 임박하고, 엔진은 시각을 올리기 전에 그 모델들을 다시 꺼낸다. 그런 모델이 없으면 다음 눈금으로 간다. 참조가 다음 사건 시각의 최솟값으로 가는 것과 같다. 끝.

이것은 손으로 쓴 논증이다. 무작위 구조와 무작위 문서에서 기록을 대조해 확인했다(5절). 처음에는 참조 시뮬레이터가 시각을 실수로 더해 갔고 어댑터는 눈금에 간격을 곱했다. 그래서 간격이 2의 거듭제곱 분수가 아니면 시각의 마지막 자리가 다를 수 있었다. 2026-11-15에 참조 시뮬레이터도 눈금으로 세게 고쳤다(17 문서). 지금은 두 쪽이 같은 정수에 같은 시간 단위를 곱해 시각을 만들고, 시간 단위 0.1, 0.3, 0.7, 1/3, 0.001에서도 기록이 끝자리까지 같다.

섞인 계획. 한 계획에 두 종류의 본체를 섞을 수 있다. 그때의 규칙은 이렇다. pyevsim 모델이 공통 모델에 보낸 것은, 그 시각에 임박한 공통 모델이 아직 전이하지 않았으면 그 차례의 묶음에 들고, 그렇지 않으면 받은 즉시 외부 전이가 된다. 엔진이 번호 순서로 처리하므로 어느 쪽인지는 경로의 순서로 정해진다. pyevsim 모델이 값 없이 신호로 보낸 메시지도 입력이며, 묶음에 그 포트가 빈 목록으로 든다. 뜻이 정해져 있고 시험도 있지만 두 의미가 섞인 것이라 권하지 않는다.

- 버퍼는 입력을 받을 때마다 보낼 수 있는지 다시 본다. 입력이 하나씩 따로 오기 때문이다.

첫째를 빼면 어떻게 되는지도 확인했다. 서버에서 cancel_rescheduling 한 줄을 빼면 같은 SES, 같은 바인딩에서 완료 수가 달라진다.

검증하지 않은 것. pyevsim의 다른 판과 깃허브의 최신본, 실시간 모드(REAL_TIME), 큰 모델에서의 성능, evsimpp. 2의 거듭제곱 분수가 아닌 시간 단위에서의 기록 대조는 2026-11-15에 했다(17 문서의 5절).

## 6. 작업 중에 찾은 결함

내 참조 구현의 결함 둘이다.

첫째, 같은 결합을 두 번 적은 경우. 문서의 한 분해에 같은 결합을 두 번 적을 수 있고 적재기는 그것을 받는다. 그러면 실현 모델과 계획의 결합 목록에 같은 결합이 둘 들어갔다. 평탄화는 결합을 관계(집합)로 보아 길을 하나로 세는데(14 문서의 정의 24), 참조 시뮬레이터의 계층 실행은 목록을 그대로 따라가 메시지를 두 번 날랐다. 받는 쪽의 상태가 계층 실행에서는 2, 평탄 실행에서는 1이었다. 14 문서의 닫힘 확인이 이것을 놓친 까닭은 무작위 생성기가 중복 결합을 만들지 않았고, 받는 쪽이 출력이 없으면 사건 기록에 차이가 드러나지 않기 때문이다. pyevsim에 등록할 횟수를 정하려고 "같은 결합을 두 번 적으면 몇 번 전달되는가"를 따지다 드러났다.

고친 것. 결합은 관계라는 정의를 따른다. 구조를 만드는 네 곳(structure.node, 구조 확장의 해석, 참조 시뮬레이터의 결합 모델, 고전 절차)에서 같은 결합을 하나로 둔다. 회귀 시험은 tests/test_executor.py의 test_a_coupling_written_twice_is_one_coupling이다. 적재기가 중복 결합을 경고하게 하는 일은 하지 않았다.

둘째, 값이 없는 출력. 모델의 출력 함수가 어떤 포트에 값이 없는 목록을 내면 참조 시뮬레이터의 평탄 실행은 받는 쪽에 빈 묶음으로 외부 전이를 일으켰고 계층 실행은 일으키지 않았다. 시각 4까지 받는 쪽의 외부 전이가 평탄 실행에서 4번, 계층 실행에서 2번이었고 흐른 시간도 달랐다. 변이 검사에서 "어댑터가 값이 없는 출력도 메시지로 보낸다"는 변이가 살아남아 그 까닭을 따지다 드러났다. 값이 없는 출력은 보내지 않은 것으로 통일했다. 참조 시뮬레이터와 어댑터가 같다. 회귀 시험은 test_an_output_without_values_is_not_an_event다.

두 결함 모두 무작위 대조가 만들지 않던 입력에서 일어났다. 그리고 받는 쪽이 그 뒤에 출력하지 않으면 사건 기록(출력의 열)만으로는 보이지 않는다. 그래서 무작위 대조에 둘을 더했다. 출력마다 값을 0개에서 2개까지 내는 모델과, 모델의 마지막 상태의 비교다. 14 문서의 닫힘 확인과 이 문서의 대조가 모두 그렇게 강화되었다.

| Y3 | 포트 타입 | pyevsim의 포트에는 타입이 없다. 관찰한 구조의 타입은 조립할 때 계획에서 적어 둔 것이다. 엔진에서 읽은 것은 포트의 이름과 방향, 연결뿐이다 |
| Y4 | 뿌리의 출력 | 엔진의 경계로 나간 출력에는 포트 이름이 없다(E8) |
| Y5 | 외부 입력 | 뿌리의 입력 포트로 pyevsim의 외부 입력을 넣을 수 있다. 다만 모든 모델이 쉬고 있으면 예약된 입력이 전달되지 않는다(E9). 그때 run이 오류를 낸다 |
| Y6 | 고정된 구조 | 생성 시각과 소멸 시각을 쓰는 모델은 받지 않는다. 실행 중에 구조가 바뀌는 것은 SES의 범위 밖이다(14 문서의 N2) |
| Y7 | 값의 복사 | 어댑터가 낸 값은 엔진이 깊은 복사해서 전달한다. 참조 시뮬레이터는 같은 객체를 넘긴다. 받은 값을 고치는 모델은 두 쪽에서 다르게 움직일 수 있다 |
| Y8 | 성능 | 재지 않았다. 어댑터는 한 차례마다 모든 모델을 훑고, 엔진은 모델 하나를 처리할 때마다 대기열 전체를 다시 정렬한다 |
| Y9 | 확인한 판 | 1.1.7 하나다 |
| Y10 | 다른 시뮬레이터 | evsimpp는 붙이지 않았다 |

## 8. 결정이 필요한 것

|---|---|---|
| Z1 | 플랫폼의 모델 계약을 무엇으로 둘 것인가 | 정했다(2026-11-23). 권고대로 공통 모델 기반이 계약이다. 사용자가 이 권고를 조건으로 건 공통 플랫폼 작업을 진행하라고 한 것을 승인으로 읽었다. 계약의 글과 그것을 지키는지 보는 검사는 20 문서의 1절과 3절에 있다. pyevsim 고유 모델은 계약 밖이고 묶음의 선언에 native로 적는다. 아래는 정하기 전의 권고다. 행위를 실행기 사이에서 비교하려면 기준이 되는 의미가 하나여야 한다. 공통 모델 기반의 다섯 함수(병렬 DEVS)를 계약으로 두고 pyevsim은 어댑터로 붙이는 쪽을 권한다. pyevsim 고유 모델은 기존 자산을 쓰는 길로 열어 둔다. 반대로 pyevsim의 의미를 기준으로 삼으면 참조 시뮬레이터를 그 의미로 다시 써야 한다 |
| Z2 | pyevsim을 고칠 것인가 | 2절에서 확인이 필요하다고 적은 여섯 가지 가운데 E3(조용한 정지)과 E6(포트 이름이 속성을 덮어씀)이 SES에서 넘어온 모델에 바로 영향을 준다. 엔진에서 고치면 실행기의 check와 규약 P1이 필요 없어진다 |
| Z3 | 시간 간격을 어디에 적을 것인가 | 끝났다(2026-11-15). 바인딩 파일에 time_unit으로 적는다. 계획에 실려 모든 실행기로 가고, 참조 시뮬레이터와 cevsim 실행기도 같은 값의 눈금으로 센다. 17 문서 |
