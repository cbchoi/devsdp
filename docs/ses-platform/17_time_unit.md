# 시간 단위

작성일: 2026-11-15

16 문서의 결정 U6(플랫폼의 시각)을 권고대로 한 기록이다. 15 문서의 결정 Z3(시간 간격을 어디에 적을 것인가)도 함께 풀렸다. 계약에 시간 단위를 두고, 참조 시뮬레이터와 두 실행기가 시각을 그 단위의 눈금으로 세게 했다.

구현은 ses_core/executor.py(시간 단위와 눈금), ses_core/devs.py(참조 시뮬레이터), ses_core/pyevsim_executor.py, ses_core/cevsim_executor.py와 ses_core/cevsim_bridge/bridge.cpp다. 검증은 tests/test_time_unit.py와 실행기마다의 시험이다.

## 0. 판정

| 기준 | 결과 |
|---|---|
| 계약 | 바인딩에 시간 단위(time_unit)를 적는다. 공통 모델 기반의 시간 전진은 그 정수배다. 시뮬레이터는 시각을 눈금의 정수로 세고, 모델과 기록에 보이는 시각은 눈금 수에 시간 단위를 곱한 값이다 |
| 참조 시뮬레이터 | 눈금으로 세도록 고쳤다. 시각이 이진수로 정확히 적히는 경우에는 고치기 전과 기록이 같다. 무작위 구조 1,200번의 실행, 사건 21,114개에서 대조했다 |
| 세 실행기의 기록 | 같다. 시간 단위가 0.1, 0.3, 0.7, 1/3, 0.001처럼 이진수로 정확히 적히지 않아도 사건 기록과 마지막 상태가 순서와 끝자리까지 같다. 시간 단위 7가지에 무작위 구조 12개씩 84가지(사건 714개), 그리고 눈금 3,000개짜리 실행 하나 |
| 고치기 전에 달랐던 예 | 0.1마다 내는 모델을 시각 1.0까지 돌리면 참조 시뮬레이터는 10번, cevsim 실행기는 9번 냈다(16 문서). 지금은 둘 다 10번이고 시각도 같다 |
| 눈금 번호가 큰 실행 | 참조 시뮬레이터와 cevsim 실행기의 기록이 눈금 번호 5천억까지 같다. long double이 80비트인 빌드와 64비트인 빌드에서 모두 그렇다. 빌드마다 26번의 실행, 사건 2,328만 개 |
| 정적 검사 | 시간 값인 매개변수(타입 time)가 시간 단위의 정수배가 아니면 그 변이는 실행 가능하지 않다(B5). 실행 가능 핵과 편집기의 진단에 그대로 들어간다 |

꼭 알아야 할 것 여섯.

- 시간 단위는 선언이다. 모델들의 시간 전진이 모두 그 정수배라고 사람이 적는 것이고, 틀리게 적으면 실행 중에 OffGrid 오류가 난다. 매개변수로 들어오는 시간 값은 실행하기 전에 B5로 걸러지지만, 모델의 본체 안에 적힌 상수는 실행해야 드러난다.
- 같은 모델이라도 시간 단위가 다르면 기록의 시각이 끝자리에서 달라진다. 0.3마다 내는 모델의 셋째 시각은 시간 단위 0.1에서 0.9이고 0.3에서 0.8999999999999999다. 그래서 시간 단위를 실행기마다 따로 주지 않고 바인딩 한곳에 적는다.
- 값은 유효숫자 9자리로 읽는다. 값을 시간 단위로 나눈 수가 정수 n에서 n의 1e-9배 안에 있으면 눈금 n으로 본다. 부동소수점의 끝자리 차이를 받아 주기 위한 것이고, 그보다 촘촘한 시간 차이를 쓰려면 시간 단위를 더 작게 잡아야 한다. 허용 폭이 눈금 번호에 비례하므로 눈금 번호가 커질수록 판정이 느슨해진다. 눈금 100만에서 0.001눈금, 1억에서 0.1눈금이고, 5억부터는 반 눈금을 넘어서 어떤 값이든 가장 가까운 눈금으로 읽힌다. 시간 전진처럼 작은 값의 판정과 공통 모델의 사건 기록은 영향을 받지 않는다. 영향을 받는 자리는 6절의 T2에 적었다.
- 고유 모델(엔진의 언어로 쓴 모델)은 이 계약 밖에 있다. 엔진의 시각을 그대로 쓴다. cevsim에서 고유 모델의 출력이 눈금 밖의 시각에 공통 모델에 닿으면 OffGrid다. 눈금과 끝자리만 다른 시각이면 그 눈금의 사건으로 함께 처리한다.
- cevsim에서 공통 모델은 엔진에 다음 사건의 눈금의 시각에서 엔진의 지금 시각을 뺀 값을 내놓는다. 남은 눈금 수에 시간 단위를 곱한 값을 내놓으면 엔진이 그것을 더해 가면서 오차가 쌓인다. 그 식으로 만들어 돌려 보니 long double이 64비트인 빌드에서 눈금마다 사건이 있는 실행은 6,745만 번째 눈금에서 OffGrid로 멈췄고(시간 단위 0.1), 걸음이 큰 실행은 눈금 번호 2천억 근처에서 멈췄다. 쓰는 식으로는 같은 빌드에서 1억 눈금과 눈금 번호 5천억까지 갔다. cevsim 저장소가 검증한 환경(MSVC, Windows x64)은 long double이 8바이트다. 이 실행기는 g++로만 지어 보았으므로, 그 환경으로 옮길 때 드러났을 차이다(3.1절).
- 쓰는 법이 바뀌었다. 실행기의 인자 이름이 time_unit으로 통일되었다(pyevsim 실행기의 time_step). 인자를 주지 않으면 바인딩의 것을 쓰고, 둘 다 있으면 같아야 한다. 어디에도 없으면 1이다. 그래서 시간 전진이 정수가 아닌 모델을 시간 단위 없이 돌리던 코드는 이제 OffGrid가 된다.

## 1. 계약

정의 (시간 단위, 눈금). 시간 단위 u는 0보다 큰 유한한 수다. 시각 t가 눈금 n 위에 있다는 것은 t가 n과 u의 곱이라는 뜻이다. 부동소수점 값 x에 대해서는 x를 u로 나눈 값 k와 가장 가까운 정수 n의 차가 1e-9와 max(1, |k|)의 곱 이하일 때 x를 눈금 n으로 읽고, 아니면 눈금 위에 없다고 본다(executor.grid). 유효숫자 9자리의 판정이다.

정의 (끝 시각의 눈금). 시각 T까지 돌린다는 것은 T가 어떤 눈금으로 읽히면 그 눈금까지, 아니면 T를 넘지 않는 마지막 눈금까지 처리한다는 뜻이다(executor.last_tick). 참조 시뮬레이터와 두 실행기가 이 함수 하나를 쓴다.

모델의 계약. 공통 모델 기반(devs.Atomic)의 모델이 돌려주는 시간 전진은 u의 음이 아닌 정수배이거나 무한대다. 시뮬레이터가 모델에 주는 값은 다음과 같다.

| 값 | 식 |
|---|---|
| 지금 시각(now) | 눈금 n에 u를 곱한 값 |
| 흐른 시간(외부 전이의 elapsed) | 지금의 눈금에서 마지막 전이의 눈금을 뺀 수에 u를 곱한 값 |
| 기록의 시각 | 눈금 n에 u를 곱한 값 |

시간 전진이 정수배가 아니면 OffGrid이고, 음수이거나 수가 아니면 ValueError다. 어느 시뮬레이터에서나 같다. 값을 눈금으로 바꾸는 함수가 하나이기 때문이다(executor.ticks).

시간 단위를 적는 자리.

| 자리 | 뜻 |
|---|---|
| 바인딩의 time_unit | 선언하는 자리다. 정의 이름을 모듈에 잇는 그 파일에 적는다. 적지 않으면 1이다. 시간이 없는 실행기(하드웨어)의 바인딩에는 적지 않는다 |
| 계획의 구성요소 | 바인딩이 적은 값이 계획의 모든 구성요소에 실려 간다(time_unit). 실행기는 계획에서 읽는다. 그래서 세 실행기가 같은 값을 쓴다 |
| 실행기의 인자 time_unit | 바인딩 없이 계획을 직접 넘길 때 쓴다. 계획에 실린 값이 있으면 같아야 하고 다르면 조립하지 않는다 |
| simulate의 인자 unit | 손으로 만든 모델을 참조 시뮬레이터에 바로 넘길 때 쓴다. DevsExecutor가 만든 모델에는 시간 단위가 적혀 있다 |
| 매개변수의 타입 time | 모듈의 매개변수가 시간 값이라는 선언이다. 4절의 검사에 쓰인다 |

```yaml
binding: "1.0"
executor: cevsim
target: ProcessingSystem
time_unit: 0.1          # 도착 간격과 서비스 시간이 모두 이 값의 정수배다
map:
  Generator: {module: Generator}
```

```python
binding = X.load_binding("processing_system.binding.cevsim.yaml")
cx = CevsimExecutor()                                   # 시간 단위는 바인딩에서 온다
L, ext = X.attach(L0, cx, binding, library)
sim = X.realize(L, ext, cx, V)
```

## 2. 왜 눈금으로 세는가

고치기 전에는 세 곳이 시각을 서로 다르게 다뤘다.

| 곳 | 시각 | 같은 시각의 판정 |
|---|---|---|
| 참조 시뮬레이터 | 배정밀도 실수를 더해 감 | 더한 값이 정확히 같은가 |
| pyevsim 실행기 | 눈금의 정수 | 정수가 같은가 |
| cevsim 실행기 | 엔진의 long double을 더해 감 | 더한 값이 정확히 같은가 |

시간 전진이 2의 거듭제곱 분수의 배수이면 덧셈이 정확해서 셋이 같았다. 그렇지 않으면 달랐다. 0.1과 0.2를 더한 값은 0.3과 다른 실수다. 그래서 0.1 뒤에 내고 다시 0.2 뒤에 내는 모델과 0.3 뒤에 내는 모델은 참조 시뮬레이터에서 같은 시각이 아니었고, 받는 쪽은 두 번에 나눠 받았다. 덧셈의 자릿수가 다른 cevsim에서는 끝 시각 근처의 사건 수까지 달랐고, long double의 폭이 다른 플랫폼에서는 또 달라질 수 있었다.

눈금으로 세면 이 문제가 없다. 같은 시각인지는 정수의 비교이고, 실수가 쓰이는 곳은 눈금 수에 시간 단위를 한 번 곱하는 자리뿐이다. 그 곱셈은 어느 실행기에서나 같은 두 수의 곱이므로 결과도 같다. 엔진이 안에서 시각을 어떻게 더하든 기록에 들어오지 않는다.

다른 길을 택하지 않은 까닭. 유리수로 정확히 더하는 길은 참조 시뮬레이터에서는 되지만 엔진의 시계를 바꿀 수 없다. 모델이 눈금의 정수를 직접 돌려주게 하는 길은 가장 깔끔하지만 모든 모델과 SES의 속성 값을 고쳐 써야 한다. 지금의 길은 모델을 고치지 않는다. 모델은 종전처럼 시간을 실수로 적고, 그 값들이 어떤 단위의 정수배인지만 선언한다.

## 3. 눈금을 엔진의 시각에 맞추는 방법

| 실행기 | 엔진의 시각 | 맞추는 방법 |
|---|---|---|
| 참조 시뮬레이터 | 없다 | 눈금의 정수만 가진다. 가장 이른 눈금을 고르고, 그 눈금의 모델들이 내고, 전이하고, 다음 눈금을 더한다 |
| pyevsim | 시간 간격씩 나아가는 격자 | 엔진의 시간 간격을 시간 단위로 둔다. 어댑터가 눈금으로 세고, 낼 차례에는 엔진의 시계 값을 그대로 요청 시각으로 내놓는다(15 문서). 종전과 같고 시간 단위를 계획에서 읽는 것만 달라졌다 |
| cevsim | 격자가 없다. 모델이 준 시간 전진을 long double로 더한다 | 아래에 적는다 |

cevsim에서의 방법. 엔진의 시계는 모델의 시간을 그대로 쓴다. 고유 모델을 건드리지 않기 위해서다.

| 필요한 것 | 방법 |
|---|---|
| 공통 모델의 다음 사건 | 엔진에는 그 눈금의 시각(눈금 수와 시간 단위의 곱)에서 엔진의 지금 시각을 뺀 값을 시간 전진으로 내놓는다. 이 눈금에 낼 차례이면 0이다. 눈금 자체는 Python 쪽이 정수로 가진다. 남은 눈금 수에 시간 단위를 곱한 값을 내놓지 않는 까닭은 3.1절에 적었다 |
| 지금이 어느 눈금인가 | 엔진의 시각을 시간 단위로 나눠 읽는다(executor.grid). 공통 모델의 사건에서 엔진의 시각은 눈금의 시각에서 배정밀도의 끝자리 하나 안에 있다 |
| 같은 눈금의 모델이 엔진에서도 같은 시각에 | 전이 신호는 모든 공통 모델에 가고, 엔진은 신호를 받은 모델마다 시간 전진을 다시 묻는다. 그래서 전이했든 아니든 모든 공통 모델의 다음 사건 시각이 그 시각을 기준으로 다시 잡힌다. 같은 기준에서 같은 값을 받으므로 같은 눈금의 모델들은 엔진에서 정확히 같은 시각에 잡히고, 차례가 경로의 순서로 온다 |
| 끝 시각 | 엔진을 until까지 돌린 뒤, 눈금으로는 until 안인데 엔진의 시각으로는 끝자리만큼 뒤에 잡힌 사건이 남아 있으면 엔진의 다음 사건을 하나씩 더 처리한다. 시간 단위 0.1에서 눈금 3의 시각은 0.30000000000000004이고 끝 시각 0.3보다 크다 |
| 밖에서 넣는 입력 | 입력의 시각이 엔진의 시각과 같은 눈금이면 지금의 입력으로 넣는다. 엔진의 시계가 끝자리만큼 앞서 있어도 지난 시각으로 거절되지 않는다 |
| 고유 모델과 끝자리가 다를 때 | 고유 모델은 제 방식으로 시각을 더한다. 그 값이 공통 모델의 것과 끝자리만 다르면 같은 눈금에 엔진의 시각이 둘 생긴다. 전이를 맡는 모델은 차례가 왔을 때 그 눈금에 낼 공통 모델이 아직 내지 않았으면 먼저 그 모델들에 차례를 주고, 그 뒤에 전이 신호를 보낸다. 그래서 같은 눈금의 것은 한 묶음으로 받는다 |
| 눈금 밖의 입력 | 고유 모델이나 밖에서 온 입력이 눈금 위에 없는 시각에 공통 모델에 닿으면 OffGrid다. 공통 모델의 계약으로는 그 흐른 시간을 적을 수 없다 |

명제. 계획의 원자가 모두 공통 모델 기반이고 모든 시간 전진이 시간 단위의 정수배라고 하자. 그러면 참조 시뮬레이터, pyevsim 실행기, cevsim 실행기가 같은 계획을 시각 T까지 돌린 사건 기록과 원자들의 마지막 상태가 같다. 시간 단위가 이진수로 정확히 적히는지와 상관없다.

논증. 세 구현이 같은 함수로 시간 전진을 눈금으로 바꾸므로 모델마다 다음 사건의 눈금이 같다. 어느 구현이나 가장 이른 눈금을 고르고, 그 눈금에 낼 모델을 경로의 순서로 내게 하고, 낸 것을 묶음에 모아 출처의 순서로 늘어놓고, 출력했거나 받은 모델을 전이시킨다. 15 문서와 16 문서의 논증이 이 순서를 엔진 위에서 지킨다는 것을 보였고, 거기서 "시각이 같다"를 "눈금이 같다"로 바꿔 읽으면 된다. 모델에 주는 시각과 흐른 시간은 세 구현이 같은 정수에 같은 수를 곱해 만든다. cevsim에서 더 필요한 것은 엔진이 눈금의 순서대로 사건을 꺼낸다는 것이다. 엔진의 시각은 기준 시각에, 눈금의 시각에서 기준 시각을 뺀 값을 더한 것이다. 반올림은 순서를 뒤집지 않으므로 눈금이 크면 그 값도 크고, 같은 눈금의 공통 모델은 위의 방법으로 같은 시각에 잡힌다. 손으로 쓴 논증이고 대조로 확인했다(5절).

### 3.1 엔진의 시계에 쌓이는 오차

엔진은 모델이 내놓은 시간 전진을 제 시계에 더한다. 공통 모델이 남은 눈금 수에 시간 단위를 곱한 값을 내놓으면, 덧셈마다 생기는 끝자리의 오차가 쌓여서 엔진의 시각이 눈금의 시각에서 조금씩 멀어진다. 실행기는 엔진의 시각을 시간 단위로 나눠 눈금을 읽으므로, 그 차이가 허용 폭을 넘으면 OffGrid가 나고 반 눈금에 닿으면 눈금을 잘못 읽는다. 이 식으로도 만들어 재 보았고 실제로 그랬다.

그래서 쓰는 식은 이렇다. 다음 사건의 눈금의 시각에서 엔진의 지금 시각을 뺀 값을 내놓는다. 엔진이 그 값을 지금 시각에 더하면 눈금의 시각으로 돌아온다. 오차는 사건마다 새로 생길 뿐 쌓이지 않는다.

측정. 엔진의 시각을 시간 단위로 나눈 값과 가장 가까운 정수의 차를 눈금 단위로 재고, 실행 중 가장 큰 값을 적었다. long double이 64비트인 빌드는 g++의 선택 사항 -mlong-double-64로 만들었다(5절).

| long double | 시간 전진의 식 | 시간 단위 0.1, 눈금 50만 개 (눈금마다 사건) | 시간 단위 0.1, 눈금 번호 20억 (걸음이 큼) | 시간 단위 0.001, 눈금 번호 5천억 (걸음이 큼) |
|---|---|---|---|---|
| 80비트 | 남은 눈금 수와 시간 단위의 곱 (쓰지 않는 식) | 1.6e-9 | 2.6e-6 | 9.8e-4 |
| 64비트 | 같은 식 | 4.5e-6 | 7.2e-3 | 눈금 번호 2,065억에서 0.5에 닿아 오류로 멈췄다 |
| 80비트 | 눈금의 시각에서 지금 시각을 뺀 값 (쓰는 식) | 5.8e-11 | 2.4e-7 | 3.1e-5 |
| 64비트 | 같은 식 | 5.8e-11 | 2.4e-7 | 3.1e-5 |

시각에 대한 비율로 보면, 쓰지 않는 식에서는 눈금 50만 개에서 80비트 3.3e-15, 64비트 8.9e-12였고 실행이 길수록 커졌다. 쓰는 식에서는 두 빌드 모두 1.8e-16 이하이고 실행의 길이와 상관이 없다. 배정밀도의 끝자리 하나다.

쌓이는 속도를 엔진 없이 같은 덧셈만 따로 계산해 보았다. 시계가 64비트일 때 0.1을 더해 가는 값은 6,745만 번째 덧셈에서 허용 폭을 벗어나고 2억 3,093만 번째에서 반 눈금에 닿는다. 시간 단위 0.1에서 0.3을 더해 가는 값은 5,507만 번째와 9,999만 번째, 0.001을 더해 가는 값은 4,878만 번째와 1억 9,133만 번째다. 80비트일 때는 20억 번을 더해도 벗어나지 않았다(비율 1.8e-11 이하). 2.5처럼 이진수로 정확히 적히는 값은 쌓이지 않는다.

엔진에서도 같은 자리에서 멈췄다. long double이 64비트인 빌드에서, 0.1마다 내는 모델과 그것을 받는 모델로 된 계획을 끊지 않고 1억 눈금까지 돌렸다. 쓰지 않는 식으로는 받는 모델이 6,745만 989번째 묶음을 받은 뒤 OffGrid로 멈췄다. 위에서 따로 계산한 자리(6,745만 990번째 덧셈)다. 쓰는 식으로는 1억 눈금까지 갔다. 받는 모델이 묶음마다 견준 시각과 흐른 시간과 값이 모두 셈한 값과 같았고, 1천만 눈금마다 읽은 엔진의 시각이 눈금의 시각과 정확히 같았다. 이 확인은 끊지 않고 한 번에 돌려야 한다. run을 끊어 부르면 엔진의 시계가 끝 시각에 정확히 서서 쌓인 오차가 지워진다.

남는 것. 고유 모델은 제 시간 전진을 엔진이 그대로 더해 가므로 위의 계산이 고유 모델에는 그대로 적용된다(6절의 T6). 고유 모델의 사건이 눈금에서 허용 폭 안으로 벗어난 시각에 공통 모델에 닿으면 그 눈금의 것으로 받고, 공통 모델의 다음 사건은 다시 눈금의 시각에 잡힌다. 벗어난 만큼이 뒤로 이어지지 않는다.

논증. 눈금의 시각을 D, 엔진의 지금 시각을 t라 하자. 내놓는 값은 D에서 t를 뺀 값을 배정밀도로 반올림한 것이고, 엔진이 t에 그것을 더한 값은 D에서 배정밀도의 끝자리 하나 안에 있다. 엔진의 시각이 그보다 더 벗어나면 그 차이가 다음 번에 읽는 t에 드러나고 뺄셈에서 빠진다. 이 눈금에 낼 차례일 때에는 뺄셈을 하지 않고 0을 내놓는다. 그 밖에는 다음 사건의 눈금이 지금 눈금보다 하나 이상 뒤이고 t가 지금 눈금에서 반 눈금 안에 있으므로 내놓는 값이 0보다 크다. 손으로 쓴 논증이고 위의 측정으로 확인했다.

## 4. 시간 값의 검사 (B5)

모듈은 매개변수의 타입을 time으로 적어 그 값이 시간 전진으로 쓰인다고 선언할 수 있다. 예시의 모델베이스에서는 도착 간격, 서비스 시간, 측정 주기가 그렇다. 14 문서의 정의 32에 조건 하나가 더해진다.

| 부호 | 조건 |
|---|---|
| B5 | 타입이 time인 매개변수의 값은 시간 단위의 음이 아닌 정수배이거나 무한대다. 값은 병합된 속성에서 오고 없으면 모듈의 기본값이다 |

B4와 같은 자리의 검사다. 전선의 구성요소 하나와 그 병합된 속성, 바인딩, 라이브러리만 본다. 그래서 14 문서의 정리 18(실현의 존재, 유일성, 충실성), 따름정리 18.1(실행기 사이의 대응), 정리 19(실행 가능성의 대수)의 증명이 그대로 선다. 그 증명들은 정의 32의 조건이 변이의 주석과 고정된 바인딩과 라이브러리의 함수라는 것만 쓴다. 정리 22(고전 SES/MB의 포섭)는 구조에 대한 것이라 상관이 없다.

뜻. 속성 값이 시간 단위와 맞지 않는 변이는 실행하기 전에 걸러진다. 주기가 1.5인 대안과 0.3인 대안이 있고 시간 단위가 0.5이면, 0.3을 고른 변이는 실행 가능하지 않고 실행 가능 핵에서 빠지며 편집기의 진단에 B5로 나온다. 시간 단위를 0.1로 적으면 둘 다 실행 가능하다. 적지 않으면 1이므로 둘 다 실행 가능하지 않다.

검사에 쓰는 시간 단위는 바인딩의 것이다. 바인딩에 없고 실행기를 만들 때 준 값이 있으면 그것을 쓴다. 둘이 다르면 붙일 때(attach) 오류가 난다.

변이 검사. 구현을 일부러 틀리게 고친 변이 181가지를 만들어 시험이 실패하는지 보았다. 계약(executor.py) 31가지, 참조 시뮬레이터 14가지, pyevsim 실행기 6가지, cevsim 실행기 91가지, 다리 39가지다. 181가지가 모두 잡혔다. 170가지는 시험의 실패로, 7가지는 시간 초과로(끝나지 않는 실행이 된다), 4가지는 프로세스의 비정상 종료로 잡혔다. 처음 돌렸을 때에는 5가지가 살아남았고, 그것이 시험의 빈 자리를 알려 주었다. pyevsim 실행기가 끝 시각의 눈금을 읽는 식을 틀리게 고친 둘은 견줄 시험이 없었다. 세 실행기가 끝 시각을 같은 눈금으로 읽는지 보는 시험을 더했다. 다리가 고유 모델의 매개변수를 읽는 자리의 둘(무한대와 기본값)도 시험이 없었다. 읽은 값을 알려 주는 시험용 모듈을 더했다. 다리의 번호 검사를 지운 하나는 검사가 없어도 우연히 죽지 않고 지나갔다. 멀리 벗어난 번호로 부르게 고쳐서 검사가 없으면 반드시 죽게 했다. 다섯을 다시 돌려 모두 잡았다.

검증하지 않은 것. MSVC와 Windows, 그리고 g++가 아닌 컴파일러에서의 cevsim 실행기. long double이 64비트인 경우는 g++의 선택 사항으로 만든 빌드에서만 보았고, 그 빌드의 한계는 16 문서의 4절에 적었다. 눈금 6,000개를 넘는 실행에서의 pyevsim 실행기. 눈금 번호가 5천억을 넘는 실행. 고유 모델이 주기를 더해 가다 허용 폭을 벗어나는 일은 계산으로만 보았고 엔진에서 돌려 보지 않았다. 허용 폭의 경계에 걸친 값이 여러 번 더해지는 모델.

## 6. 한계

| 번호 | 한계 | 뜻 |
|---|---|---|
| T1 | 선언은 사람이 한다 | 시간 단위가 모든 시간 전진의 약수라는 것을 플랫폼이 찾아 주지 않는다. 틀리면 B5나 OffGrid로 드러난다 |
| T2 | 허용 폭 | 값은 유효숫자 9자리로 읽는다. 눈금 n에서 n의 1e-9배(n이 1보다 작으면 1e-9) 안의 값은 눈금 n이다. 그보다 가까운 서로 다른 시각을 쓰는 모델은 시간 단위를 더 작게 잡아야 한다. 허용 폭은 눈금 번호에 비례해서 커진다. 눈금 100만에서 0.001눈금, 1억에서 0.1눈금이고, 5억부터는 0.5눈금을 넘어서 판정이 어떤 값이든 받는다. 영향을 받는 것은 큰 값을 읽는 세 자리다. 첫째는 끝 시각이다. 눈금에 조금 못 미치는 끝 시각이 그 눈금까지로 읽히고, 5억 눈금부터는 반 눈금까지 뒤의 눈금이 될 수 있다. 둘째는 cevsim 실행기가 엔진의 시각에서 눈금을 읽는 자리다. 실행이 길어질수록 눈금 밖의 고유 모델 사건이 OffGrid로 걸리지 않고 가까운 눈금에 묶인다. 셋째는 5억 눈금 이상인 시간 전진과 시간 값이다. 공통 모델의 눈금은 정수로 세므로 사건 기록은 영향을 받지 않고, 보통 크기의 시간 전진을 판정하는 일도 영향을 받지 않는다. 폭의 크기는 코드에 고정되어 있다 |
| T3 | 본체 안의 시간 | B5는 타입이 time인 매개변수만 본다. 모델의 본체에 적힌 상수나 계산해서 나온 시간 전진은 실행해야 드러난다 |
| T4 | 시간 단위와 기록의 끝자리 | 같은 모델이라도 시간 단위가 다르면 기록의 시각이 끝자리에서 다를 수 있다. 두 기록을 견줄 때에는 시간 단위가 같아야 한다 |
| T5 | 작은 시간 단위와 pyevsim | pyevsim의 엔진은 시간 간격마다 한 걸음씩 나아간다. 시간 단위를 작게 잡으면 그만큼 느려진다. 사건 50개짜리 같은 실행이 시간 단위 1에서 2밀리초, 0.0001에서 1.4초 걸렸다. 참조 시뮬레이터와 cevsim은 사건이 있는 눈금만 지나므로 달라지지 않는다. pyevsim의 시계는 시간 간격을 배정밀도로 더해 가고, 어댑터는 그 값을 가장 가까운 눈금으로 읽는다. 그래서 쌓인 오차가 반 눈금에 닿기 전까지만 맞게 읽는다. 3.1절의 계산으로는 시간 단위에 따라 1억 7천만에서 2억 3천만 걸음 뒤다. 돌려 보지는 않았다. pyevsim 자신도 시각을 상대 오차 1e-9로 견주므로 10억 걸음 근처에서는 이웃한 눈금을 가리지 못한다 |
| T6 | 고유 모델 | 계약 밖이다. 엔진의 시각을 그대로 쓴다. cevsim에서 시간 단위가 이진수로 정확히 적히지 않으면 고유 모델과 공통 모델의 사건 시각이 끝자리에서 어긋날 수 있고, 그때 같은 눈금 안의 순서는 경로의 순서가 아니라 엔진의 시각이 이른 쪽이 먼저다. 한 묶음으로 받는 것은 지켜진다. 고유 모델의 주기가 시간 단위의 정수배이더라도 엔진이 그 주기를 더해 가므로 오차가 쌓인다. long double이 64비트인 플랫폼에서는 주기에 따라 4,900만에서 8,300만 번 더한 뒤에 허용 폭을 벗어나고, 그 뒤로 그 사건이 공통 모델에 닿으면 OffGrid다(3.1절의 계산). 80비트에서는 20억 번까지 벗어나지 않았다 |
| T7 | 실행기 사이의 시각 맞춤 | 한 변이를 여러 실행기에 나눠 실현할 때(14 문서의 N8) 실행기 사이의 시각을 맞추는 일은 여전히 다루지 않았다. 시간 단위가 같다는 것은 그 일의 전제일 뿐이다 |
| T8 | 눈금의 크기 | 눈금은 Python의 정수라 한도가 없지만, 눈금 수에 시간 단위를 곱한 값과 엔진의 시각은 실수다. 먼저 닿는 한계는 T2다(5억 눈금부터 판정이 느슨하다). 사건 기록은 그 뒤로도 눈금 번호 5천억까지 참조 시뮬레이터와 cevsim 실행기에서 같았다(5절). 눈금 수가 2의 53제곱에 가까워지면 곱한 값이 이웃한 눈금을 가리지 못한다 |

## 7. 결정이 필요한 것

| 번호 | 결정 | 권고 |
|---|---|---|
| V1 | 시간 단위를 적지 않았을 때 | 지금은 1로 본다. 반드시 적게 하는 길도 있다. 권고는 지금대로다. 틀린 기본값은 조용히 넘어가지 않고 B5나 OffGrid로 드러난다 |
| V2 | SES 문서에도 둘 것인가 | 지금은 바인딩에만 있다. 예시의 SES는 속성에 측정 단위(unit: s)를 적는데 플랫폼은 그것을 읽지 않는다. 시간 단위는 속성 값과 모듈이 만나는 자리의 일이라 바인딩에 두었다. 한 SES에 바인딩이 여럿이면 값을 여러 번 적게 되므로, 그것이 불편해지면 프로파일이나 SES 문서로 올린다 |
| V3 | 모델이 눈금을 직접 다루게 할 것인가 | 시간 전진을 정수로 돌려주게 하면 허용 오차가 필요 없어진다. 모든 모델과 속성 값을 고쳐야 한다. 권고는 지금대로 두는 것이다 |
| V4 | 허용 폭을 어떻게 둘 것인가 | 지금은 값의 1e-9배로 고정이다. 그래서 5억 눈금부터 판정이 느슨하다(T2). 공통 모델의 엔진 시각은 눈금의 시각에서 끝자리 하나 안에 있으므로, 공통 모델만 보면 폭을 훨씬 좁게 잡거나 상한을 둘 수 있다. 폭이 필요한 쪽은 고유 모델이다. 엔진이 고유 모델의 주기를 더해 가며 쌓는 오차를 받아 주는 것이 이 폭이고, 좁히면 눈금 위에 있으려던 고유 모델의 사건이 더 일찍 OffGrid가 된다. 권고는 그대로 두는 것이다. 5억 눈금을 넘는 실행에서 눈금 밖의 값을 잡아내야 할 필요가 생기면 그때 상한을 둔다 |
