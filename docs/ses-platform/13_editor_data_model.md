# 편집기를 고려한 자료구조

작성일: 2026-11-14

나중에 편집기를 만든다는 전제로 자료구조를 다시 본 결과다. 지금까지의 자료구조(정준 문서, 적재기, 펼친 나무)는 "완성된 문서를 읽어 분석한다"는 쓰임에 맞춰져 있었고, 편집기가 필요로 하는 성질 대부분을 갖지 못했다. 이 문서는 무엇이 모자랐는지, 무엇을 더했는지, 무엇이 검증되었고 무엇이 남았는지를 적는다.

참조 구현은 ses_core/edit.py, ses_core/decisions.py, ses_core/diagnose.py이고 검증은 tests/test_edit.py, tests/test_decisions.py, tests/test_diagnose.py이다.

## 0. 요약

| 무엇 | 결정 |
|---|---|
| 편집 대상 | 정준 문서(YAML)를 직접 고치지 않는다. 식별자 기반의 편집 모델을 따로 두고 정준 문서와 분석 모델은 거기서 만들어 낸다 |
| 식별 | 요소마다 이름과 별개의 식별자. 참조는 식별자로 한다. 파일에는 식별자를 남기지 않고 주소(이름 경로)로 대신한다 |
| 틀린 문서 | 저장소는 구조만 지키고 의미는 지키지 않는다. 틀린 상태를 그대로 담고, 문제는 예외가 아니라 진단으로 알린다 |
| 변경 | 원시 연산 네 가지(넣기, 빼기, 바꾸기, 옮기기). 연산은 자료이고 각각 역연산을 가진다. 되돌리기, 다시 하기, 변경 이력이 여기서 나온다 |
| 진단 | 글자가 아니라 요소를 가리킨다. 변이에 따라 달라지는 문제에는 해당 변이의 수, 재현하는 결정 집합, 원인이 되는 결정이 붙는다 |
| 변이 고르기 | 결정 집합. 가지치기를 자료로 적은 것이며 순서가 없는 집합이다. 선택 지점 표가 화면의 자료다 |
| 분야별 화면 | 표시 정보(제목, UI 힌트)는 프로파일에 둔다. 팔레트(둘 수 있는 부분, 관계, 필드)는 프로파일에서 계산한다 |
| 다른 언어의 편집기 | 스냅숏과 변경 이력을 JSON으로 정했고 스키마가 있다. 구현해야 할 핵심은 연산 네 개와 불변식 다섯 개다 |

해결하지 못한 것 가운데 편집기 설계에 직접 영향을 주는 것은 셋이다. 저장할 때 YAML 주석이 사라진다. 포트와 결합은 요소가 아니어서 이름을 바꿔도 따라오지 않는다(끊어진 곳은 진단이 짚는다). 변이에 따른 진단은 전수 열거에 의존한다. 12절에 적었다.

## 1. 편집기가 자료구조에 요구하는 것

요구를 먼저 적고 기존 구조가 그것을 만족하는지 탐침으로 확인했다. 아래 표의 "기존 상태"는 모두 실제로 실행해 본 결과다.

| 번호 | 편집기의 요구 | 기존 상태 | 대응 | 절 |
|---|---|---|---|---|
| E1 | 틀리거나 덜 된 문서를 열어 둔 채 일한다 | 적재기는 무결성 오류에서 예외를 내고 아무것도 돌려주지 않는다 | 허용적 저장소, 예외 대신 진단 | 3.3, 6 |
| E2 | 문제를 화면의 요소 위에 표시한다 | 오류는 요소를 가리키지 않는 글자다. 변이 위반은 펼친 나무의 경로(프로그래밍입문/구성/LO4)를 가리킨다 | 요소 식별자가 붙은 진단, 펼친 나무에서 요소로 되돌리기 | 6 |
| E3 | 이름을 바꿔도 연결이 유지된다 | 이름이 곧 참조다. "함수"라는 이름이 한 문서에 5번 적힌다(정의 1번, 참조 4번) | 식별자 참조. 편집 모델에서는 1번만 적힌다 | 3.2 |
| E4 | 모든 변경을 되돌린다 | 자료구조가 불변 값이고 변경의 단위가 없다 | 역연산을 가진 원시 연산 | 3.4 |
| E5 | 화면의 순서가 문서의 순서다 | 분석 결과에서 자식의 순서가 이름순으로 정렬되어 있었다 | 순서 보존. algebra.py를 고쳤다 | 2 |
| E6 | 저장해도 사람이 쓴 것이 유지된다 | YAML을 읽고 다시 쓰면 주석 6개가 0개가 된다 | 해결하지 못했다 | 12 |
| E7 | 변이를 골라 보는 화면 | 가지치기 SES 파일은 변수 값과 복제본별 결정을 적지 못한다(09 문서 1.3) | 결정 집합, 선택 지점 표 | 7 |
| E8 | 분야에 맞는 입력 화면 | 프로파일에 표시 정보가 없다 | 제목, UI 힌트, 팔레트 | 8 |
| E9 | 큰 문서에서도 반응이 빠르다 | 모든 검사가 전체를 다시 계산한다 | 개정 번호와 사용 관계를 두었다. 증분 계산 자체는 구현하지 않았다 | 9 |

## 2. 세 개의 모형

같은 SES를 세 가지 모양으로 가진다. 편집 모델만 고친다. 나머지 둘은 편집 모델에서 만들어지는 파생물이다.

| 모형 | 무엇으로 찾는가 | 틀린 상태 | 쓰임 | 구현 |
|---|---|---|---|---|
| 정준 문서 | 이름 | 담지 못한다(적재기가 거부) | 저장, 교환, 사람이 읽고 쓰기 | model.py, loader.py |
| 편집 모델 | 식별자 | 담는다 | 편집, 되돌리기, 진단의 대상 | edit.py |
| 분석 모델 | 이름 경로(펼친 나무) | 해당 없음. 막는 오류가 없는 문서에서만 만든다 | 변이 열거, 적격성, 가지치기 | unfold.py, algebra.py, extension.py |

모형 사이의 사상은 다음과 같다.

| 사상 | 방향 | 성질 |
|---|---|---|
| from_dict | 정준 문서에서 편집 모델로 | 전역. 의미가 틀린 문서로 실패하지 않는다 |
| to_dict | 편집 모델에서 정준 문서로 | 부분. 이름이 있고 겹치지 않아야 한다 |
| load_ses_dict, unfold_layered | 정준 문서에서 분석 모델로 | 부분. 엄격하다 |
| provenance | 분석 모델의 노드에서 편집 모델의 요소로 | 정의 표지와 부분 이름으로 찾는다 |
| 결정 집합의 번역 | 문서의 이름에서 분석 모델의 노드 집합으로 | 7절 |

분석 모델이 편집기의 화면과 어긋나지 않도록 한 가지를 고쳤다. algebra.py의 Tree가 자식을 이름순으로 정렬하던 것을 문서에 적은 순서로 바꿨다. 이 순서가 선택 지점 표와 문서 조립 확장의 출력 순서가 된다. 기존 테스트 7,610개는 그대로 통과한다.

## 3. 편집 모델

### 3.1 요소

편집 모델은 요소의 평평한 표다. 요소 하나는 식별자, 유형, 부모, 부모 안에서의 역할, 속성(JSON 값), 역할별 자식 목록(순서 있음), 개정 번호를 가진다.

무엇을 요소로 둘지는 한 가지 기준으로 정했다. 다른 곳에서 가리킬 수 있거나, 자식을 가지거나, 화면에서 따로 골라 옮기는 것은 요소다. 그 밖의 내용은 요소의 속성이며 경로로 고친다.

| 유형 | 이름 | 참조 속성(대상) | 자식 역할(자식 유형) | 주요 속성 |
|---|---|---|---|---|
| document | name | 없음 | variables(variable), entities(entity) | ses, version, description, profile, port_types, constraints, experimental_frames, metadata |
| variable | name | 없음 | 없음 | spec |
| entity | name | extends(entity) | links(link), aspects(aspect), multi_aspects(multi_aspect), specializations(specialization) | root, kind, fields, ports, attributes, stereotype, doc, metadata |
| aspect | name | 없음 | parts(part) | couplings, rule, priority, doc |
| part | 없음 | def(entity) | 없음 | alias |
| multi_aspect | name | part(entity) | 없음 | cardinality, naming, couplings, rule, priority, doc |
| specialization | name | default(entity) | alternatives(alternative) | select, doc |
| alternative | 없음 | def(entity) | 없음 | 없음 |
| link | 없음 | target(entity) | 없음 | type |

이 표가 편집 모델 자체의 스키마이며 코드에서는 등록부(TYPES) 하나다. 커리큘럼 예시 문서는 요소 65개가 된다(엔티티 21, 부분 17, 관계 17, aspect 4, 대안 2, 그 밖 4).

이 기준에서 벗어난 곳이 하나 있다. 포트는 결합이 가리키므로 기준대로면 요소여야 하지만 이번 판에서는 속성으로 두었다. 결과와 대안은 12절에 적었다.

### 3.2 참조

참조는 Ref(target, name) 값이다.
- target이 있으면 연결된 참조다. 이름은 대상의 현재 이름에서 읽는다. 대상의 이름을 바꿔도 고칠 것이 없다.
- target이 없으면 끊어진 참조다. name은 사용자가 적은 이름이다. 가리키던 엔티티를 지우면 참조는 이름을 가진 채 끊어진 참조로 남고, 같은 이름의 엔티티가 다시 생기면 이을 수 있다(reconnect).

끊어진 참조는 저장소가 담는 정상적인 상태다. 문제라는 사실은 진단(부호 REF)이 알린다.

### 3.3 저장소가 지키는 것과 지키지 않는 것

저장소는 구조의 불변식 다섯 개만 지킨다. 원시 연산은 이것을 깨는 요청을 거부한다.

| 번호 | 불변식 |
|---|---|
| S1 | 부모 없는 요소는 문서 하나뿐이다. 모든 요소는 문서에서 닿는다 |
| S2 | 자식은 부모의 유형이 허용하는 역할과 유형으로만 놓인다. 요소는 부모의 자식 목록에 정확히 한 번 나타난다 |
| S3 | 참조 속성의 값은 Ref다. 연결된 참조의 대상은 저장소에 있고 유형이 맞다 |
| S4 | 자식이 있는 요소와 다른 요소가 가리키는 요소는 뺄 수 없다 |
| S5 | 역참조 색인(누가 이 요소를 가리키는가)은 참조 속성과 일치한다 |

의미의 규칙은 저장소가 지키지 않는다. 뿌리가 없거나 둘인 문서, 이름이 겹치는 엔티티, 자기 자신을 extends 하는 엔티티, 끊어진 참조가 모두 담긴다. 편집 도중의 문서는 대부분의 시간 동안 틀린 상태이기 때문이다. 이름의 유일성 같은 규칙은 명령(3.6절)이 지키고, 나머지는 진단이 알린다.

구분의 기준은 이것이다. 깨지면 저장소 자체가 뜻을 잃는 것은 불변식, 깨져도 저장소는 멀쩡하고 문서만 틀린 것은 진단이다.

### 3.4 원시 연산

모든 변경은 네 가지 연산으로 이루어진다. 연산은 실행할 코드가 아니라 자료다.

| 연산 | 하는 일 | 거부되는 경우 | 역연산 |
|---|---|---|---|
| Insert(id, type, parent, role, index, props) | 자식 없는 요소를 넣는다 | 식별자 중복, 허용되지 않는 자리, 없는 대상의 참조 | Remove(id) |
| Remove(id) | 자식 없는 요소를 뺀다 | 자식이 있다, 다른 요소가 가리킨다 | 같은 자리에 같은 속성으로 Insert |
| Set(id, path, old, new, at) | 속성 경로의 값을 바꾼다. 없음은 표지 MISSING으로 적는다 | 지금 값이 old와 다르다(충돌), 중간 경로가 없다 | Set(id, path, new, old, 원래 자리) |
| Move(id, parent, role, index) | 다른 부모나 다른 자리로 옮긴다 | 허용되지 않는 자리 | 원래 부모와 자리로 Move |

성질은 다섯 가지이고 모두 무작위 연산으로 검증했다.

| 번호 | 성질 |
|---|---|
| P1 | 역연산은 상태를 정확히 되돌린다. 사상 안의 열쇠 순서까지 같다 |
| P2 | 거부된 연산은 저장소에 흔적을 남기지 않는다 |
| P3 | 받아들여진 연산 뒤에 불변식 S1에서 S5가 성립한다 |
| P4 | 변경 이력을 처음 상태의 다른 저장소에 차례로 적용하면 같은 상태가 된다 |
| P5 | 연산은 JSON으로 적었다 읽어도 같다 |

설계에서 두 가지를 짚어 둔다.

값의 비교는 JSON의 값 구분을 따른다. 1과 True, 1과 1.0은 다른 값이다. Python의 등호를 그대로 쓰면 "값이 1인 필드를 True로 바꾸기"가 아무 일도 하지 않는다.

Set의 at은 테스트가 잡아낸 결함에서 나왔다. 필드를 지웠다가 되돌리면 값은 돌아오지만 열쇠가 맨 끝에 붙어, 되돌린 뒤 저장한 파일이 원본과 달라졌다. 열쇠를 지우는 연산의 역연산이 원래 자리를 기억하도록 고쳤다.

목록 안에서는 있는 항목을 바꾸거나, 끝에 붙이거나, 마지막 항목을 지울 수 있다. 가운데에 끼워 넣으려면 목록 전체를 Set으로 바꾼다.

### 3.5 거래, 되돌리기, 변경 이력

연산은 거래로 묶인다. 거래 하나가 되돌리기 한 단계다. 거래 안에서 연산이 거부되면 그 거래의 연산을 모두 되돌린다.

되돌리기는 거래의 연산을 역순으로 역연산하는 것이고, 그때 돌려받은 역연산이 다시 하기의 재료가 된다. 따로 저장하는 "이전 상태"는 없다.

변경 이력(log)은 지금까지의 거래를 JSON으로 낸 것이다. 예를 들어 "함수를 선택 사항으로 만들기" 명령 하나는 다음 거래가 된다.

```json
{"label": "함수 을 선택 사항으로", "ops": [
  {"op": "insert", "id": "s66", "type": "specialization", "parent": "e7", "role": "specializations", "index": 0, "props": {"name": "개설"}},
  {"op": "insert", "id": "e67", "type": "entity", "parent": "d1", "role": "entities", "index": 21, "props": {"name": "함수개설"}},
  {"op": "insert", "id": "e68", "type": "entity", "parent": "d1", "role": "entities", "index": 22, "props": {"name": "함수미개설", "stereotype": "void"}},
  {"op": "insert", "id": "o69", "type": "alternative", "parent": "s66", "role": "alternatives", "index": 0, "props": {"def": {"$ref": "e67", "name": null}}},
  {"op": "set", "id": "e67", "path": ["extends"], "old": {"$missing": true}, "new": {"$ref": "e7", "name": null}},
  {"op": "insert", "id": "o70", "type": "alternative", "parent": "s66", "role": "alternatives", "index": 1, "props": {"def": {"$ref": "e68", "name": null}}},
  {"op": "set", "id": "e68", "path": ["extends"], "old": {"$missing": true}, "new": {"$ref": "e7", "name": null}}
]}
```

### 3.6 명령

명령은 SES의 뜻을 아는 편집이다. 원시 연산의 거래 하나로 풀린다. 명령은 저장소가 지키지 않는 규칙 가운데 "새로 만드는 순간에 지키기 쉬운 것"을 지킨다. 이름이 식별자 규칙에 맞고 겹치지 않아야 한다는 것이 그렇다. 규칙에 맞지 않는 이름은 파일에서 들어올 수는 있어도(진단 NAME) 명령으로 만들 수는 없다.

| 명령 | 한 거래에서 하는 일 |
|---|---|
| add_entity, add_variable, add_aspect, add_multi_aspect, add_specialization | 요소를 넣는다. 이름이 규칙에 맞지 않거나 겹치면 거부한다 |
| add_part, add_alternative, add_link | 참조를 가진 요소를 넣는다. add_alternative는 대안이 될 엔티티가 extends를 갖지 않으면 소유 엔티티를 extends 하게 한다 |
| rename | 이름을 바꾼다. 이름이 글자로 적힌 곳을 함께 고친다(아래) |
| remove | 요소와 그 아래를 뺀다. 가리키던 참조는 이름을 가진 끊어진 참조로 남긴다. cascade이면 가리키던 부분, 대안, 관계를 함께 뺀다 |
| move, reorder | 다른 부모로 옮기거나 순서를 바꾼다 |
| make_optional | specialization 하나, 있음 대안과 없음 대안을 만든다 |
| duplicate | 엔티티 정의를 그 아래의 구조와 함께 복사한다 |
| set_root | 뿌리를 정하고 다른 엔티티의 뿌리 표시를 지운다 |
| set_alias | 부분의 별칭을 정하고 그 이름으로 적힌 결합의 끝점을 고친다 |
| set, set_kind, set_field, remove_field | 속성을 고친다 |
| relink, reconnect | 참조를 다른 대상으로 잇는다. 끊어진 참조 가운데 그 이름의 엔티티가 지금 있는 것을 다시 잇는다 |

이름 바꾸기에서 참조는 식별자로 이어져 있어 고칠 것이 없다. 그러나 정준 문서에는 이름이 글자로 적힌 곳이 남아 있고 rename이 같은 거래에서 고친다.

| 바뀐 것 | 함께 고치는 곳 |
|---|---|
| 엔티티 | 선택 규칙의 then과 else, 별칭 없는 부분의 결합 끝점, 실험 프레임의 attach_to |
| 변수 | 규칙, 선택 규칙, 개수, 선택 제약, 속성의 유도식 안의 var |
| aspect | 문서 조립 확장의 구분자 표(metadata.text.separators)의 열쇠 |

rename은 Renamed(type, old, new, owner, addresses)를 돌려준다. 편집기 바깥의 파일(결정 집합, 곁자료)이 이름을 따라가는 데 쓴다.

검증한 것: 다섯 문서의 모든 엔티티, 변수, aspect, multi-aspect, specialization의 이름을 차례로 바꾼 뒤에도 문서가 적재되고 분석 결과(변이 수, 적격이 아닌 변이 수, 위반 부호별 건수)가 같다. 옛 이름은 문서에 하나도 남지 않는다.

고치지 못하는 곳: 식의 selected 표현(노드와 선택지를 글자로 적는다)과 포트 이름. 12절.

### 3.7 편집이 변이 공간에 주는 영향

편집기가 "이 변경으로 변이가 얼마나 늘거나 주는가"를 보여 주려면 다시 분석하는 수밖에 없다. 아래 표는 방향만 적은 것이며 이름 바꾸기 줄만 검증했다. 나머지는 정의에서 따라 나오는 판단이다.

| 편집 | 변이 공간 |
|---|---|
| 이름 바꾸기, 순서 바꾸기, 곁자료 | 그대로다(이름 바꾸기는 검증함) |
| 대안, aspect 추가, 개수 범위 넓히기, 변수 값 추가 | 커지거나 그대로다 |
| 대안, aspect 삭제, 선택 규칙과 선택 제약 추가 | 작아지거나 그대로다 |
| 선택 사항으로 만들기 | 그 구성요소가 나타나는 변이마다 둘이 된다 |
| 필드, 관계, 포트, 결합 고치기 | 변이 공간은 그대로이고 적격인 변이가 달라진다 |

### 3.8 화면의 나무는 출현의 나무다

편집 모델은 정의의 표다. 그런데 SES를 보는 화면은 보통 나무이고, 그 나무에서 같은 정의는 쓰인 곳마다 나타난다. 이 차이를 자료구조에서 분명히 해 둔다.

- 정의는 하나이고 출현은 여럿이다. 한 출현에서 고치면 그 정의의 모든 출현이 바뀐다. 편집기는 이것을 화면에서 알려야 한다(같은 정의의 다른 출현을 함께 표시하는 식으로).
- 출현은 뿌리에서부터 지나온 쓴 자리(부분, multi-aspect, 대안)의 식별자 열로 식별한다. 화면의 선택 상태와 펼침 상태는 요소가 아니라 출현에 붙는다. multi-aspect의 복제본들은 쓴 자리 하나의 출현이다.
- 전부 펼친 나무는 문서보다 지수적으로 클 수 있다(9절). 그래서 한 층씩 계산한다. Model.outline(엔티티)이 그 엔티티의 분해와 specialization, 그 아래의 쓴 자리와 가리키는 엔티티를 돌려준다.

검증한 것: 다섯 문서에서 펼친 나무의 모든 엔티티 노드에 outline을 따라 내려가 닿을 수 있고, 닿은 엔티티가 그 노드의 정의 표지와 같다. 쓴 자리의 열 하나는 정의 하나만 가리킨다.

## 4. 정준 문서와의 왕복

### 4.1 가져오기

from_dict는 어떤 입력에도 실패하지 않는다. 의미가 틀린 문서(끊어진 이름, 뿌리 없음, 빠진 열쇠)는 그대로 담는다. 모양이 틀려 담을 수 없는 곳(사상이 있어야 할 자리의 목록 등)은 건너뛰고 import_issues에 위치와 함께 적는다. 조용히 버리는 것은 없다. 모르는 열쇠는 extra에 담아 두었다가 그대로 내보낸다.

검증한 것: 다섯 문서의 임의의 자리를 지우거나 엉뚱한 값으로 바꾼 300개의 손상 문서에서 예외가 한 번도 나지 않았고, import_issues가 비어 있으면 문서에 적힌 값이 하나도 사라지지 않았다.

### 4.2 내보내기와 정준 순서

to_dict는 열쇠를 고정된 순서로 쓴다. 저장한 파일이 편집 이력과 무관하게 내용만으로 정해지도록 하기 위해서다.

| 자리 | 순서 |
|---|---|
| 문서 | ses, name, version, description, profile, variables, port_types, entities, constraints, experimental_frames, metadata |
| 엔티티 | root, kind, extends, fields, links, ports, attributes, stereotype, doc, aspects, multi_aspects, specializations, metadata |
| aspect | parts, couplings, rule, priority, doc |
| multi-aspect | part, cardinality, naming, couplings, rule, priority, doc |
| specialization | alternatives, select, default, doc |

이 순서는 저장소의 예시 문서들이 이미 쓰던 순서에 맞춰 정했다. 그래서 다섯 문서는 열고 저장해도 내용과 열쇠 순서가 모두 그대로다. 다른 순서로 손으로 쓴 문서는 처음 저장할 때 순서가 바뀐다.

필드, 포트, 속성처럼 사용자가 정한 열쇠들의 순서는 적힌 대로 유지된다.

### 4.3 정규화되는 것과 사라지는 것

덜 된 문서를 열고 저장하면 다음이 정규화된다. 한 번 저장한 뒤로는 바뀌지 않는다(다시 열고 저장해도 같다).

| 번호 | 입력 | 저장 결과 |
|---|---|---|
| N1 | 본문이 비어 있는 엔티티, aspect, multi-aspect, specialization (값이 null) | 빈 사상 |
| N2 | 별칭 없이 {def: X}로 적은 부분 | X |
| N3 | parts 없는 aspect, alternatives 없는 specialization | 빈 목록을 가진 열쇠 |
| N4 | 대상이 없는 관계 유형 (선수: []) | 그 유형이 사라진다 |
| N5 | 비어 있는 variables, aspects, multi_aspects, specializations, links | 열쇠가 사라진다. entities는 늘 쓴다 |

사라지는 것은 YAML의 주석, 흐름 표기와 블록 표기의 구분, 따옴표, 빈 줄이다. 한 사상 안에 같은 열쇠가 두 번 적힌 파일은 YAML 처리기가 뒤의 것만 남기므로 편집 모델에 닿기 전에 앞의 것이 사라진다.

### 4.4 저장할 수 있는 조건

정준 문서는 이름으로 찾는 형식이다. 이름이 없거나 겹치는 요소가 있으면 to_dict는 실패한다. 그런 상태는 스냅숏(10절)으로 저장한다. 끊어진 참조는 문제없이 저장된다. 적힌 이름이 그대로 나가고, 다시 열 때 그 이름의 엔티티가 있으면 이어진다.

정리하면 저장 형식은 둘이다. 정준 문서는 교환과 사람을 위한 것이고 덜 된 문서도 대부분 담는다. 스냅숏은 편집기의 작업 상태를 위한 것이고 무엇이든 담는다.

## 5. 주소와 곁자료

식별자는 세션 안에서만 뜻이 있다. 파일에 남겨야 하는 식별에는 주소를 쓴다. 주소는 문서에서 그 요소까지의 역할과 이름을 이은 것이다.

```text
entities/응용영역
entities/응용영역/aspects/웹트랙
entities/응용영역/aspects/웹트랙/parts/웹기초
entities/심화알고리즘/specializations/개설여부/alternatives/심화미개설
entities/함수/links/선수:제어구조
variables/실습주수
```

이름 없는 요소의 이름 자리에는 부분은 별칭 또는 정의 이름, 대안은 정의 이름, 관계는 유형과 대상을 쓴다. 형제 사이에 같은 이름이 있으면 #0, #1을 붙인다. 주소는 요소마다 다르고 주소로 요소를 다시 찾을 수 있다(검증함).

곁자료는 문서의 뜻이 아닌 것이다. 화면 위치, 접힘 상태, 검토 주석이 그렇다. 규칙은 하나다. 편집하는 동안은 식별자로 들고, 파일에는 주소로 적는다. 그래서 이름을 바꾸거나 옮기는 동안에는 곁자료를 고칠 일이 없고, 주소는 저장하는 순간에만 계산한다. save_sidecar와 load_sidecar가 이 변환이다. 다시 열 때 주소를 찾지 못한 곁자료는 버리지 않고 따로 돌려준다.

편집기 바깥에서 문서의 이름이 바뀌면 주소가 달라져 곁자료가 떨어진다. 이것이 식별자를 파일에 남기지 않기로 한 결정의 대가다(12절의 결정 D1).

## 6. 진단

### 6.1 자료

진단 하나는 다음을 가진다.

| 필드 | 뜻 |
|---|---|
| severity | error, warning, info |
| code | 부호 (6.3절) |
| message | 사람이 읽는 설명 |
| element, address | 가리키는 요소의 식별자와 주소 |
| path | 요소 안의 속성 경로. 예: fields/시수, couplings/2/to |
| related | 관련된 다른 요소. 겹친 이름의 상대, 그 구성요소를 부분으로 쓴 자리 |
| scope | document 또는 family |
| blocking | 이 문제가 있으면 변이 분석을 할 수 없다 |
| layer | 족 범위 위반의 계층. core 또는 확장 이름 |
| affected | (해당 변이 수, 전체 변이 수) |
| witness | 문제가 생기는 변이 하나를 재현하는 결정 집합 |
| cause, cause_covers | 원인이 되는 결정들과 그것을 따르는 변이의 수 |
| data | 부호마다 정해진 구조화된 세부. 지금은 REF, VAR, COUP, DEAD에만 있다 |

### 6.2 두 범위

문서 범위(check_document)는 변이를 세지 않고 알 수 있는 것이다. 고칠 때마다 바로 계산할 수 있고 어떤 상태의 문서에도 답한다.

족 범위(analyze)는 변이를 열거해야 알 수 있는 것이다. 막는 오류가 없을 때만 한다. 순서는 다음과 같다.

1. 문서 범위의 진단을 낸다. 막는 오류가 있으면 여기서 멈춘다(SKIP).
2. 펼친 나무의 크기를 펼치지 않고 센다. 한도(기본 200,000 노드)를 넘으면 멈춘다(LIMIT).
3. 편집 모델을 정준 문서로 내보내 엄격한 적재기에 넣는다. 적재기가 거부하면 그 내용을 진단으로 바꾼다(LOAD).
4. 분석 모델을 만든다. 실패하면 ANALYZE, 구조상 변이 수가 한도(기본 5,000)를 넘으면 LIMIT.
5. 변이를 열거하고 변이마다 위반을 구한다.
6. 위반을 (계층, 부호, 요소, 메시지)로 모아 진단 하나로 만들고 해당 변이 수, 증거, 원인을 붙인다.
7. 죽은 선택지를 구한다(DEAD).

2단계는 작업 중에 드러난 문제 때문에 넣었다. 두 부분이 같은 정의를 쓰는 층이 40개인 문서는 요소가 160개 남짓이지만 펼친 나무는 3조 개가 넘는 노드를 가진다. 크기를 미리 세지 않으면 분석은 변이 수의 한도에 닿기도 전에 적재기에서 끝나지 않는다.

분석 도중에 나는 예외는 모두 진단으로 바꾼다. 분석이 편집기를 멈추게 하지 않는다.

### 6.3 부호

문서 범위의 부호다. 표시가 없으면 오류이고 변이 분석을 막는다.

| 부호 | 뜻 |
|---|---|
| ROOT | 뿌리가 없거나 둘 이상이다 |
| NAME | 이름이 식별자 규칙에 맞지 않는다 |
| DUP | 이름이 겹친다 (엔티티, 변수, 한 엔티티 안의 분해와 specialization, 한 aspect 안의 부분, 대안) |
| REF | 끊어진 참조 |
| EXT | extends가 순환한다. 대안이 소유 엔티티를 extends 하지 않는다 |
| SPEC | 기본값이나 선택 규칙이 고르는 것이 대안이 아니다 |
| VAR | 식이 정의되지 않은 변수를 쓴다 |
| CYCLE | 정의가 자기 자신을 포함한다 (strict hierarchy) |
| VOID | 없음 대안이 내용을 가지거나, 뿌리이거나, 부분으로 쓰인다 |
| ATOMIC | atomic인데 분해를 가진다 |
| MISS | 필수 내용이 없다. 부분 없는 aspect는 경고, 대안 없는 specialization과 복제 대상이나 개수가 없는 multi-aspect는 오류 |
| COUP | 결합의 끝점이 가리키는 부분이나 포트가 없다 |
| SHAPE | 속성의 모양이 틀리다 (모르는 stereotype, type 없는 변수, 이름이 아닌 유형 등) |
| DEPTH | 포함 관계가 너무 깊어(수천 층) 검사하지 못했다 |
| PROFILE | 문서가 따르는 프로파일이 주어지지 않았거나 다르다 |
| UNUSED | 뿌리에서 닿지 않는 엔티티. 경고. extends의 바탕으로만 쓰이는 엔티티는 쓰이는 것으로 본다 |
| T1, F1, F3, L0, L2, T2 | 프로파일 위반 가운데 정의만 보고 알 수 있는 것. 오류이지만 분석을 막지 않는다 |

족 범위와 분석 과정의 부호다.

| 부호 | 뜻 |
|---|---|
| K0, K1 | 핵 적격성 위반 (11 문서) |
| 확장의 부호 | 확장이 낸 위반. 프로파일 확장이면 T0, F2, L1, L3, R1, R2, M 등 (12 문서) |
| DEAD | 죽은 선택지. 경고 |
| NOWF | 적격인 변이가 하나도 없다 |
| EMPTY | 제약을 만족하는 변이가 없다 |
| SKIP, LIMIT | 분석을 하지 않았다는 알림 |
| LOAD, ANALYZE | 엄격한 경로가 문서를 받지 못했다. 문서 범위 검사가 미리 잡지 못한 문제다 |

프로파일 위반을 두 범위에서 모두 다루는 이유는 다음과 같다. 필드의 타입이 틀렸다는 사실은 변이와 무관하므로 입력하는 순간에 그 필드를 짚어 알려야 한다. 한편 그 오류 하나 때문에 다른 분석이 모두 가려지면 안 된다. 그래서 문서 범위에서 알리되 분석은 막지 않고, 같은 내용을 족 범위에서 되풀이하지 않는다.

### 6.4 펼친 나무에서 요소로

족 범위의 위반은 펼친 나무의 구성 노드를 가리킨다. 이것을 문서의 요소로 되돌리는 규칙은 다음과 같다.

- 노드의 정의 표지가 정의 엔티티를 정한다. 복제본 실습_1의 표지는 실습이고, 별칭 부분의 표지는 그 정의의 이름이다.
- 그 구성요소를 부분으로 쓴 자리는 부모 노드로 찾는다. 부모가 aspect이면 그 aspect의 부분, multi-aspect의 전개(실습들[2])이면 그 multi-aspect, specialization이면 그 대안이다.

정의 엔티티가 진단의 element가 되고 쓴 자리가 related가 된다. 정의 표지는 09 문서의 결함 1.1을 고치려고 넣은 것인데 여기서 다시 쓰인다.

### 6.5 증거와 원인

커리큘럼 예시에서 나오는 진단 하나를 그대로 옮긴다.

```json
{"severity": "error", "code": "R1", "scope": "family", "layer": "curriculum",
 "message": "성취기준은 다뤄지고 평가된다: 들어오는 관계 달성 이 0개다",
 "element": "e21", "address": "entities/LO4", "related": ["p31"],
 "affected": [6, 12],
 "witness": {"decisions": "1.0", "variables": {"실습주수": 1}, "choose": [
   {"at": "심화알고리즘", "specialization": "개설여부", "alternative": "심화미개설"},
   {"at": "응용영역", "aspect": "자료처리트랙"},
   {"at": "실습영역", "multi_aspect": "실습들", "count": 1}]},
 "cause": {"decisions": "1.0", "choose": [
   {"at": "심화알고리즘", "specialization": "개설여부", "alternative": "심화미개설"}]},
 "cause_covers": 6}
```

읽는 법: 성취기준 LO4는 변이 12개 가운데 6개에서 어떤 단원으로도 다뤄지지 않는다. 증거의 결정 집합을 적용하면 그런 변이 하나가 정확히 재현된다. 원인은 "심화알고리즘을 개설하지 않는다"는 결정 하나이고, 이 결정을 따르는 변이 6개가 해당 변이 6개 전부다.

증거(witness)는 변이 하나를 정확히 재현하는 결정 집합이다. 선택지가 둘 이상인 선택 지점마다 그 변이가 고른 것을 적는다.

원인(cause)은 증거에서 빼도 되는 결정을 뺀 것이다. 성질은 둘이다. 원인을 따르는 변이는 모두 그 문제를 가진다. 원인에서 결정을 하나라도 더 빼면 그렇지 않게 된다. 탐욕적으로 줄이므로 더 뺄 수 없는 원인이지 가장 작은 원인이라는 보장은 없다. 원인은 하나만 구한다. cause_covers가 affected의 앞 수보다 작으면 다른 원인이 더 있다는 뜻이다. 문제가 모든 변이에서 생기면 원인은 빈 결정 집합이다.

### 6.6 죽은 선택지

선택지가 있는데 적격인 변이는 아무도 그것을 고르지 않으면 죽은 선택지다. 편집기에서는 고를 수 있어 보이지만 고르면 반드시 무엇인가 깨지는 선택지다. 커리큘럼 예시에서는 셋이 나온다: 심화미개설, 실습들의 개수 3, 변수 실습주수의 값 3.

선택 지점 자체가 적격인 변이에 나타나지 않으면 그 지점의 선택지들은 알리지 않는다. 그 지점을 죽게 만든 위쪽의 선택지가 알려지기 때문이다.

### 6.7 진단과 엄격한 도구의 관계

검증한 관계는 둘이다.

- 문서 범위의 오류 25가지를 하나씩 일부러 만들었을 때, 진단은 정해진 요소와 속성 경로를 짚고, 엄격한 도구(정준 문서 쓰기, 적재기, 스키마) 가운데 적어도 하나가 그 문서를 거부한다. 진단이 엉뚱한 것을 문제 삼지 않는다는 뜻이다.
- 무작위 편집 세션의 상태 가운데 문서 범위의 진단이 하나도 없는(UNUSED 제외) 상태는 모두 정준 문서로 쓸 수 있고, 적재기가 받아들이고, 스키마를 통과한다. 진단이 놓치는 것이 없다는 뜻이다. 다만 이것은 편집 명령이 만드는 상태에 대한 것이다. 손상된 파일에서 온 상태에서는 LOAD가 남는다(12절).

## 7. 결정 집합과 선택 지점 표

### 7.1 형식

```yaml
decisions: "1.0"
name: 웹트랙_실습2
target: 프로그래밍입문
variables:
  실습주수: 2
choose:
  - {at: 응용영역, aspect: 웹트랙}
  - {at: 심화알고리즘, specialization: 개설여부, alternative: 심화개설}
  - {at: 실습영역, multi_aspect: 실습들, count: [1, 2]}
  - {path: [Pool, server_0], specialization: kind, alternative: Fast}
```

결정 하나는 가리키는 곳 하나와 내용 하나를 가진다.

가리키는 곳은 세 가지 방식으로 적는다. 아래로 갈수록 좁다.

| 방식 | 가리키는 것 | 쓰임 |
|---|---|---|
| at | 정의 이름. 그 정의가 출현하는 모든 곳 | 보통의 결정. 접힌 형태의 가지치기 SES와 같다 |
| path | 구성요소 경로(뿌리에서부터 부분 이름들). 그 구성요소의 병합체 전체 | 복제본마다 다르게 고를 때 |
| node | 펼친 나무의 엔티티 노드 하나 | 기계가 만든다. 언제나 정확하지만 aspect 이름과 개수가 경로에 들어 있어 편집에 약하다 |

내용은 세 가지 가운데 하나다.

| 내용 | 뜻 |
|---|---|
| aspect | 남길 분해. aspect 이름 또는 multi-aspect 이름으로 적는다 |
| multi_aspect와 count | 그 multi-aspect에서 남길 개수. 다른 분해는 건드리지 않는다 |
| specialization과 alternative | 그 specialization에서 남길 대안 |

값은 하나 또는 목록이다. 목록이면 부분 가지치기다. 변수 값은 variables에 적는다.

### 7.2 뜻

세 방식에 같은 규칙 하나를 쓴다. 결정은 가리키는 엔티티 노드들에서, 해당 선택 지점의 선택지 가운데 남기지 않는 것을 배제한다. 결정 집합의 뜻은 "배제된 선택지를 하나도 고르지 않는 변이들"이다.

구현은 결정 하나를 가지치기 SES 하나로 번역하고 07 문서의 가지치기 연산을 적용한다. 따라서 그 정리들이 그대로 성립한다.

- 결정 집합은 집합이다. 적용 순서와 결과가 무관하다(정리 5). 무작위 문서 300개에서 번역된 가지치기 SES를 임의의 순서로 하나씩 적용한 결과가 위의 뜻과 같았다.
- 정의 수준과 경로 수준의 결정은 모두 적용된다. 덮어쓰지 않는다. 서로 모순이면 남는 변이가 없다. 04 문서의 수정 사항과 같다.
- 되돌리기는 결정 하나를 빼는 일이다. 이력이 필요 없다.

경로 수준의 분해 결정에는 주의할 점이 하나 있다. path는 병합체 전체를 가리키므로 "이 구성요소의 분해는 이것"이라는 뜻이 된다. 바탕 정의와 대안이 각자 분해를 가질 때 대안의 분해만 남기면 바탕 정의의 분해가 배제되어 그 구성요소가 나타날 수 없게 된다. 테스트에 이 경우를 적어 두었다.

결정은 원래의 SES를 기준으로 해석한다. 편집기의 상태는 (SES, 결정 집합)이고 가지치기된 SES는 그때마다 다시 계산하는 파생물이다.

### 7.3 낡은 결정

문서가 바뀌면 결정이 가리키는 곳이나 남기려는 선택지가 사라질 수 있다. 그런 결정은 조용히 넘기지 않는다. problems가 (열쇠, 설명)의 목록으로 알려 주고, 엄격한 적용은 실패하며, skip_invalid로 건너뛰고 적용할 수 있다.

문서에서 이름을 바꾸면 rename이 돌려준 Renamed로 결정 집합을 따라 고친다(renamed). 정의 수준의 결정은 모두 따라간다. 경로 수준과 노드 수준의 결정은 엔티티 이름만 따라가고 aspect나 specialization의 이름은 따라가지 못해 낡은 결정으로 보고된다.

### 7.4 선택 지점 표

대화형 가지치기 화면의 자료다. 선택 지점마다 한 줄이고 줄마다 선택지와 그 상태를 가진다.

| 필드 | 뜻 |
|---|---|
| owner | 정의 이름. 변수이면 변수 이름 |
| kind | variable, aspect, count, alternative |
| group | specialization 이름 또는 multi-aspect 이름 |
| options | (선택지, 남아 있는가)의 목록. 문서에 적힌 순서 |

"남아 있다"의 뜻은 정확히 이것이다. 지금의 결정 집합을 적용한 뒤에 남은 변이 가운데 어떤 것이 어떤 출현에서 그 선택지를 고른다. 무작위 문서에서 이 뜻대로 검증했다.

커리큘럼 예시의 표는 네 줄이다: 변수 실습주수(1, 2, 3), 심화알고리즘의 개설여부, 응용영역의 분해(자료처리트랙, 웹트랙), 실습영역의 실습들 개수(1, 2, 3). 웹트랙을 고르고 실습주수를 2로 정하면 실습들의 개수 줄도 2로 정해진다. 개수가 변수를 따르기 때문이다.

분석 결과(Analysis.table)는 적격인 변이를 기준으로 한 표다. 죽은 선택지가 여기서 "남아 있지 않음"으로 나온다.

### 7.5 이전 형식과의 관계

| 이전 것 | 관계 |
|---|---|
| 가지치기 SES 파일 (07 문서) | 처리 시스템 예시에서 결정 집합과 가지치기 SES 파일이 같은 결과를 낸다(검증함). 결정 집합은 변수 값을 적을 수 있고 대상의 정의를 다시 선언하지 않아도 된다 |
| Configuration (04 문서) | values와 decisions가 결정 집합의 variables와 choose에 해당한다. overrides(속성 재정의)는 결정 집합에 없다 |
| 09 문서의 결함 1.3 | 변수 값 지정과 복제본별 결정은 해결되었다. 선택에 대한 제약(selected 표현)은 2026-11-15에 18 문서에서 해결되었다 |

## 8. 프로파일의 표시 정보와 팔레트

분야에 따라 달라지는 표시 방식도 분야의 낱말이다. 그래서 코드가 아니라 프로파일에 둔다.

```yaml
kinds:
  단원:
    title: 단원
    ui: {icon: book, color: "#4477aa"}
    fields:
      시수: {type: int, required: true, title: 수업 시수, ui: {unit: 시간, widget: number, min: 1}}
links:
  선수: {from: [단원], to: [단원], title: 선수 단원, ui: {line: dashed}}
```

title은 화면에 보일 이름이고 ui는 편집기가 해석하는 자유로운 힌트다. 유형, 필드, 관계에 붙일 수 있다. 핵과 검사는 둘을 읽지 않는다. ui 안의 낱말(icon, widget 등)은 정하지 않았다. 편집기를 만들 때 정할 일이다.

팔레트(Profile.palette)는 어떤 유형의 엔티티를 편집할 때 편집기가 내놓을 것이다: 입력 폼의 필드, 부분으로 둘 수 있는 유형, 나가는 관계와 들어오는 관계. 팔레트는 검사와 같은 답을 내야 한다. 세 프로파일의 모든 유형 쌍과 관계에 대해, 팔레트에 있는 것은 오류 없이 놓이고 없는 것은 T2나 L2로 진단됨을 확인했다.

## 9. 증분 분석을 위한 자료

구현한 것은 자료뿐이고 증분 계산 자체는 구현하지 않았다.

| 자료 | 뜻 |
|---|---|
| 개정 번호 | 저장소는 연산마다 번호를 올리고 건드린 요소에 그 번호를 적는다 |
| changed_entities(since) | 그 번호 뒤에 바뀐 요소가 속한 엔티티들 |
| users(entity) | 그 엔티티를 부분, 복제 대상, 대안으로 쓰는 엔티티들 |
| dependents(entities) | 그 엔티티들이 바뀌면 영향을 받는 엔티티들. 쓰는 쪽으로 닫은 것 |
| 역참조 색인 | 어떤 요소를 누가 가리키는가. 연산마다 갱신한다 |

이것으로 할 수 있는 일은 문서 범위 검사의 결과를 엔티티별로 보관했다가 바뀐 엔티티와 그 영향 범위만 다시 계산하는 것이다. 족 범위의 분석은 전체에 대한 계산이라 이 자료만으로는 나눌 수 없다.

비용에 대해 확인한 것과 확인하지 않은 것은 다음과 같다.

- 펼친 나무는 문서보다 지수적으로 클 수 있다. 문서 범위 검사는 펼치지 않는다. strict hierarchy 검사는 정의마다 한 번만 내려가므로 위의 40층 문서에서도 바로 끝난다. 적재기의 같은 검사는 경로를 모두 따라가므로 그런 문서에서는 끝나지 않는다.
- 펼친 나무의 노드 수는 펼치지 않고 정의마다 한 번씩 계산해 구한다(unfolded_size). 저장소의 다섯 문서와 무작위 문서 145개에서 실제로 펼친 나무의 노드 수와 같았다.
- 주소 찾기(find)와 문서 범위 검사 전체는 문서 크기에 비례하거나 그보다 느리다. 예시 크기에서는 문제가 없지만 큰 문서에서 시간을 재 보지는 않았다.

## 10. 언어와 무관한 형식

편집기를 Python이 아닌 언어로 만들 수 있도록 작업 상태의 형식을 JSON으로 정했다.

스냅숏(형식 이름 ses-edit/1)은 요소 저장소 전체다. 요소 하나는 다음과 같다.

```json
{"e8": {"type": "entity", "parent": "d1", "role": "entities",
        "props": {"name": "심화알고리즘", "kind": "단원", "fields": {"시수": 6, "수준": "심화"}},
        "children": {"links": ["l44", "l45"], "aspects": [], "multi_aspects": [], "specializations": ["s46"]}},
 "l44": {"type": "link", "parent": "e8", "role": "links",
         "props": {"type": "선수", "target": {"$ref": "e7", "name": null}}, "children": {}}}
```

참조는 {"$ref": 식별자 또는 null, "name": 적힌 이름}으로 적는다. 요소는 문서 순서로 나오므로 같은 상태의 스냅숏은 편집 이력과 무관하게 같다. 스냅숏을 읽을 때는 불변식을 처음부터 검사하고 어기면 거부한다.

변경 이력은 3.5절의 거래의 열이다.

스키마는 schema/edit.schema.json(스냅숏과 변경 이력)과 schema/decisions.schema.json(결정 집합)이다. 무작위 세션의 스냅숏과 변경 이력, 무작위 결정 집합과 증거가 스키마를 통과함을 확인했다.

다른 언어로 옮길 때 구현해야 하는 핵심은 3.1절의 유형 표, 3.3절의 불변식 다섯 개, 3.4절의 연산 네 개다. 참조 구현에서 연산의 적용은 105줄이다. 명령과 진단은 그 위에 쌓인다. 진단과 변이 분석까지 다른 언어로 옮길지, Python 구현을 서비스로 둘지는 편집기의 형태에 달려 있다(12절의 결정 D4).

크기에 대해: 커리큘럼 예시는 정준 YAML이 약 2,200자, 스냅숏 JSON이 약 10,900자다. 스냅숏은 작업 형식이지 교환 형식이 아니다.

## 12. 한계와 결정이 필요한 것

### 12.1 한계

| 번호 | 한계 | 영향 |
|---|---|---|
| L1 | 저장하면 YAML의 주석과 서식이 사라진다 | 손으로 쓴 문서를 편집기로 한 번 저장하면 주석을 잃는다. 주석을 보존하려면 구문 나무를 유지하는 YAML 처리기 위에 내보내기를 다시 만들어야 한다. 검토하지 않았다. 지금 할 수 있는 것은 설명을 주석이 아니라 doc 필드에 적는 것이다 |
| L2 | 포트, 결합, 필드, 속성, 식은 요소가 아니라 속성이다 | 포트 이름을 바꿔도 결합이 따라오지 않는다. 끊어진 곳은 COUP 진단이 결합의 자리까지 짚지만 고치는 것은 사람이다. 식의 selected 표현은 이름을 글자로 가지며 이름을 바꿔도 고쳐지지 않는다 |
| L3 | 족 범위의 위반은 확장이 낸 메시지 글자로 구분된다 | 같은 문제라도 숫자가 다르면 다른 진단이 된다(총시수 48과 51). 구조화된 세부가 없어 자동 고침을 붙이기 어렵다. 고치려면 확장 계약의 검사가 글자 대신 자료를 돌려주어야 한다 |
| L4 | 족 범위의 진단은 펼친 나무와 변이의 전수 열거에 의존한다 | 펼친 나무의 노드가 한도(기본 200,000)를 넘거나 구조상 변이 수가 한도(기본 5,000)를 넘으면 분석하지 않는다. 그런 문서에서는 문서 범위의 진단만 나온다. 솔버가 없다. 09 문서가 적은 한계 그대로다 |
| L5 | 증분 분석을 구현하지 않았다 | 큰 문서에서 고칠 때마다 전체를 다시 검사한다 |
| L6 | 동시 편집을 다루지 않는다 | Set의 old 검사는 충돌을 알아챌 뿐 합치지 못한다 |
| L7 | 여러 문서를 묶는 구조가 없다 | 프로파일, SES 문서, 결정 집합 여러 개, 곁자료를 한 작업 공간으로 다루는 자료구조와 문서 사이의 참조(실험 프레임의 ref)를 정하지 않았다 |
| L8 | 글자 위치가 없다 | 진단은 요소를 가리키지 YAML의 줄과 칸을 가리키지 않는다. 텍스트 편집기와 나란히 쓰려면 주소에서 위치로 가는 표가 필요하다 |
| L9 | 스키마와 모양이 다른 파일에서 적재기는 일반 예외를 낸다 | analyze가 LOAD 진단으로 바꾸지만 요소를 가리키지 못한다. 포트의 방향과 타입 오류도 LOAD로 나오며 요소는 메시지 앞의 이름으로 추정한다 |
| L10 | 원인은 하나만 구한다 | cause_covers가 affected보다 작을 때 나머지 변이의 원인은 알려 주지 않는다 |
| L11 | 속성 재정의가 결정 집합에 없다 | 04 문서의 overrides에 해당하는 것이 없다. 속성은 11 문서에서도 일부만 다룬다 |
| L12 | model.py의 Configuration, PruningTrace, PES, FPES, Binding은 쓰이지 않는 초안으로 남아 있다 | 결정 집합이 Configuration의 values와 decisions를 대신한다. 나머지는 손대지 않았다 |

L2에 대해 덧붙인다. 요소 유형의 등록부가 확장점이다. 포트와 결합을 요소로 올리면(port 요소, 끝점이 포트를 Ref로 가리키는 coupling 요소) 이름 바꾸기가 결합까지 따라가고 결합을 화면에서 따로 골라 옮길 수 있다. 정준 문서와의 왕복과 유형 표가 그만큼 커진다. 편집기의 주된 쓰임이 DEVS 결합 편집이라면 해야 하는 일이고, 커리큘럼이나 RFP 같은 분야가 주된 쓰임이라면 지금 구조로 충분하다. 분야 쪽에서 가리킴을 받는 것(관계의 대상)은 이미 식별자 참조다.
